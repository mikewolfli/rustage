# 资源、主题图标与鸿蒙桌面打包：问题及解决路径

日期：2026-10-13
状态：待实施；本文记录问题和推进顺序，不代表相关功能已经完成。

## 1. 原则与当前边界

依照 [项目原则](../plan/principle.md)、[路线图](../plan/roadmap.md)和[资源计划](../plan/resources.md)，
将资源生成、GUI 接入与平台验收分开推进，不能仅把 `blocked` 改成 `ok`。
只有具备真实执行和验收证据的能力才可声明支持。

当前已提供资源源文件、图标设计、生成和校验工具，以及四平台打包资源定义。
但尚未接入真实 GUI 消费者；鸿蒙目录是清单与资源模板，不是完整可运行的 DevEco 应用。
已有执行记录见 [第一次资源记录](../log/log-20261013-1.md)和
[主题图标与鸿蒙资源记录](../log/log-20261013-2.md)。

## 2. 先修资源流水线

### 2.1 已确认的实现缺口

1. [鸿蒙应用模板](../../packaging/harmonyos/AppScope/app.json5)将 `versionCode`
   占位符放在引号里，替换后可能成为字符串。生成结果必须为平台要求的整数。
2. [生成器](../../tools/resources/generate-resources.mjs)没有输出全部已声明的鸿蒙模板：
   缺少分层图标定义、模块清单、明暗颜色和页面路由等静态文件。
   应以[鸿蒙资源定义](../../packaging/harmonyos/app.json)中的模板清单为依据，
   完整输出需要替换和无需替换的文件，避免配置、校验与生成逻辑漂移。

这些是实现缺口，不需要先确定应用身份或发行策略即可修复。

### 2.2 修复后的验收

增加“身份已配置”的端到端测试，使用测试夹具，不擅自修改实际产品决策：

- 检查完整输出文件集合和目录结构。
- 检查 `versionCode` 等字段的类型，以及生成清单的结构可解析性。
- 检查资源引用对应的资源文件齐全。
- 检查没有残留占位符。
- 补齐非法路径、缺文件和损坏 JSON 的显式错误诊断。
- 身份未配置时继续明确报告阻塞，不输出假成功状态。

资源层测试通过只证明资源生成契约成立，不等同于平台构建、安装或 GUI 支持通过。

## 3. 确定应用身份与发行策略

[身份配置](../../packaging/identity.json)中的空值不能随意填写。
以下决策应分项确认并记录；这四项连同 `.ai/` 材料策略在
[决策登记](../../docs/plan/decisions.md) 的「待项目方决定项」表中登记为 `open`，
归属项目方，任何实现不得以推测值代替：

| 决策 | 确定方式 | 路线图关联 |
|---|---|---|
| 应用 ID | 选择有权使用、同时符合四平台约束的稳定标识 | T00.04 |
| 最低系统版本 | 固定 GUI 依赖后，以各平台构建和运行小样验证，再锁定支持范围 | T01.08、T25.01 |
| 发行形态与安装布局 | 按平台确定包形式、安装位置及适用的签名流程 | T25.02 |
| 品牌与主题取值 | 对当前提案进行视觉审核，明确批准或修改结果 | T05.02、T24.02 |

共享应用 ID 还需满足鸿蒙 bundle name 约束，不能只通过普通反域名格式检查。
签名凭据不得入库。

某个平台未就绪，不应阻止其他已验证平台生成；但未就绪平台必须继续明确报告阻塞。
不能为了让生成报告全部通过而虚构最低版本、发行形式或验证环境。

## 4. 让界面图标真正随主题变化

**状态（2026-10-13）：已实施到控件层，未到窗口层。**
[Cargo.toml](../../Cargo.toml)已接入固定修订的 GUI 依赖（见
[资源计划 §7.5](../plan/resources.md)），`src/resources/` 接缝与 `src/app/shell/toolbar.rs`
的真实控件小样已建立，八角色已映射到依赖自己的主题字段，四个真实控件渲染基线
（明/暗/禁用/强制对比）已提交并被测试逐字节把关。完整证据、命令与仍然缺的项见
[图标接入真实控件记录](../log/log-20261013-3.md)。

仍然**没有**的部分，不要按已解决理解：没有真实窗口显示过图标、没有交互态绘制证据、
没有窗口级 DPI 缩放、`rtl_mirror` 数据没有消费点、其余消费入口（Button 像素通道、菜单、
树）未探测、Rust 侧检查尚未进 CI。

实施顺序：

1. 固定 `rust-widgets` 依赖修订，发布构建不依赖个人本地目录。
2. 做一个真实工具栏小样，同时接入内置图标和自有静态几何。
3. 将八种图标语义角色映射到真实主题，而不是把评审色板当作生产主题。
4. 主题变化时刷新颜色，并使相关缓存失效。
5. 验证明暗主题、禁用状态、缩放和高对比显示后，再建立真实后端截图基线。
6. 验证实际几何消费、容量边界、状态和 RTL 语义，不以 SVG 预览替代控件验收。

**界面图标随主题换色；桌面品牌图标保持识别一致。**
鸿蒙启动背景可通过明暗资源限定符变化，两者不要混为一谈。

## 5. 鸿蒙先做可运行小样，再做正式包

[鸿蒙资源定义](../../packaging/harmonyos/app.json)目前不是完整 DevEco 工程。
安装 Rust OHOS 编译目标不足以证明 GUI 可运行。

推进路径：

```text
DevEco / HarmonyOS SDK 工程
 -> ArkTS 启动入口
 -> 原生模块边界
 -> Rust GUI 窗口、绘制和输入探针
 -> 签名与安装
 -> 2in1 设备验收
```

先验证固定 GUI 栈能否承载窗口、绘制与事件循环，再补齐应用入口和正式打包环节。
如果窗口或渲染后端不支持，应明确记录上游适配工作和能力缺口：

- 不用空壳页面冒充 Rust GUI 支持完成。
- 不未经决策更换项目 GUI 技术栈。
- 未通过承载小样前，不声明鸿蒙桌面正式支持。

真机验收应覆盖桌面分层图标、启动页图标与明暗背景、应用名称、安装身份，
以及脱离开发目录和网络的安装启动行为。

## 6. 四平台显示与发布验收

当前 macOS 可优先进行本机验收；Windows、Linux 和鸿蒙的安装、系统图标与启动表现，
需要对应环境补充证据。

| 平台 | 重点验收入口 |
|---|---|
| Windows | Explorer、快捷方式、任务栏、Alt-Tab、干净用户环境安装启动 |
| macOS | Finder、Dock、应用包结构、适用的签名/公证流程、安装启动 |
| Linux | GNOME/KDE 启动器、桌面入口、图标安装位置、干净环境安装启动 |
| HarmonyOS | 2in1 桌面、启动窗口、应用列表身份、签名包安装启动 |

缺少 SDK、设备或签名环境时，记录具体阻塞与未验证范围，不能改为通过。

## 7. 推荐执行顺序与完成标准

1. **修复资源流水线**：完整生成鸿蒙模板，保证字段类型，补齐端到端与错误诊断测试。
2. **接入桌面 GUI 小样**：验证真实图标消费和运行时主题切换。
3. **分项确认产品决策**：应用 ID、最低版本、发行策略、品牌与主题。
4. **独立推进鸿蒙承载关卡**：先证明固定 GUI 栈可运行，再做正式包。
5. **补齐目标平台验收**：保存构建、安装、系统显示及真实控件回归证据。

每个阶段单独报告结果。资源阶段完成不代表 GUI 阶段完成，
GUI 小样通过也不代表四平台发行验收完成。
本文的完成情况按节分别报告：第 4 节的图标问题已实施到控件层（证据见
[log-20261013-3.md](../log/log-20261013-3.md)），第 2 节的资源流水线缺口与第 3、5、6 节的
决策与平台验收仍未执行。任何一节都不能因为另一节完成而视为通过。
