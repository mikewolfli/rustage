## 2. 前后置与波次

`Task` 新增 `pre` / `post`：

- `pre`：在这个任务**之前**必须完成的任​​务（边：pre → task）。
- `post`：在这个任务**之后**运行的任务（边：task → post）。
- 与 `depends_on` 的区别只是语义：`pre` 是“先跑一下”，`depends_on` 是“依赖它的产物”；排序上
  两者都是先后约束，所以共用同一张图。

`schedule(tasks)` 做分层拓扑：每一波里的任务**彼此没有边**，所以同一波可以并发；`order()` 仍然
返回扁平的确定顺序（波内按名字排序），既有行为不变。

默认任务也跟着改准：候选是“既不是别人的 `depends_on`/`pre`，也不是别人的 `post`”的任务 ——
`pre` 由主任务带起来，`post` 在主任务之后跑，两者都不是你“运行”的那个。

真实输出：

```text
$ rustage --tasks task:lint:lint task:build:cargo task:test:cargo task:report:report \
      pre:build:lint after:test:build post:test:report
default: test
lint: lint
build: cargo (after lint)
test: cargo (after build) (then report)
report: report
wave 1: lint
wave 2: build
wave 3: test
wave 4: report
```

## 3. 定向清理：先展示，再删

`cleanup_plan(root, tasks, names)` 返回一份**计划**（不是动作）：

| 字段 | 说明 |
|---|---|
| `task` / `path` | 谁声明的、声明的相对路径 |
| `exists` / `bytes` | 现在是否存在、多大 |
| `refused` | 不删的原因（空路径、绝对路径、含 `..`、解析到工程外、是目录、就是工程根） |

`Cleanup::apply()` **只删计划允许的条目**、只删文件、逐条报告失败，不会因为一个失败停下其余。

真正的“确认”落在命令行顺序上：`clean:<task>` 要求**同一次调用里先有** `clean-preview:<task>`，
否则拒绝。这样“展示范围”不是建议，而是执行的前置条件。

真实证据：

```text
$ rustage --tasks root:/tmp/rustage-t16-05 task:build:cargo \
      output:build:out/demo output:build:dist output:build:/tmp/elsewhere \
      output:build:keep.txt clean-preview:build
build: out/demo (5 byte(s))
build: dist — kept (a directory is not removed by a task cleanup)
build: /tmp/elsewhere — kept (an absolute path is outside the project)
build: keep.txt (4 byte(s))
cleanup scope: 4 path(s), 2 removable, 9 byte(s)

$ rustage --tasks root:/tmp/rustage-t16-05 task:build:cargo output:build:out/demo clean:build
rustage: clean build needs clean-preview:build first, so the scope is shown before anything is removed
（exit 4）

$ rustage --tasks root:/tmp/rustage-t16-05 task:build:cargo output:build:out/demo \
      output:build:dist output:build:keep.txt clean-preview:build clean:build
…
removed out/demo
removed keep.txt
（dist 仍在：它是目录，被计划拒绝）
```
