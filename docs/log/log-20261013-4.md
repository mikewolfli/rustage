## 1. 范围与原则取舍

| 决策 | 依据 | 理由 |
|---|---|---|
| 本轮做 T00.01–T00.03，不做窗口承载 | principle #25/#26；blue1 | 设计器要复用依赖的布局、生成、事件、解绑与编辑语义；在这些契约被**可运行探针**证实或被明确列为缺口前，任何下游结论都只是假设。窗口承载需要显示会话，属另一证据层 |
| 探针返回 `Verified` / `Gap` 两态 | principle #22/#39/#61 | 当前每项探针在能编译的环境里都可运行，"无法运行"这一态没有产生者；等第一个依赖显示/设备的探针出现时再连同产生者一起加 |
| 有 `Gap` 时 `--probe-apis` 退出码为 1 | principle #22/#24 | 缺口不是通过。把"未满足"以退出码表达，调用方不能只看报告就误以为全绿 |
| 发现库层缺口即写入 `docs/rw-feedback/`，并在主机侧写明绕行 | 用户要求 #1；principle #60 | 结论必须有可复核证据；缺口要分类到库层/宿主层，不能只写成"注意一下" |
| 支持矩阵在路线图三级之外增加 `build-verified` | blue1 T00.03；principle #24/#25 | 构建通过不等于运行通过：并入 `certified` 会虚报，并入 `unverified` 会丢掉真实证据。四级都在文档中给出定义 |
| 矩阵用 `support-matrix.json` + 逐行校验的 Markdown | resources.md §16.1 的同一手法 | "表格与数据一致"必须由检查保证，而不是靠人记得同步；改一处漏一处应当失败 |
| 矩阵不为 HarmonyOS 增设宿主行 | blue1 T00.03（三宿主）；principle #2 | 路线图的三宿主是 macOS/Windows/Linux；鸿蒙 2in1 是既有打包目标，验收项单独跟踪在 issue 文档，不混入三宿主矩阵 |
| 探针报告的修订版本用常量 + **漂移测试** | principle #22/#59 | 运行期读到的锁文件可能不是二进制构建时用的那份；常量被测试钉在 `Cargo.lock` 上，报告不可能"把过期结果当当前结果" |
| Rust 工具链**精确固定**为 1.98.1 | blue1 T00.01（固定 Rust 版本） | 证据要可复现："探针通过"必须带上跑它的编译器，否则下次 stable 前移该结论就失效 |
| 所有 `mod.rs` 仅保留模块声明与再导出 | principle #63（`mod.rs` 薄职责） | 边界文件里不应长出实现；`app` 与 `cli` 因此拆出 `run.rs` 与 `command.rs` |
| 不创建 `docs/plan/capability-reference.md` | principle #26；scope | 该文件是 T00.05/T00.09 的交付物（能力补充与协议依据），不是 T00.03 的支持矩阵；本轮写它只会是占位文档。`check-docs` 因此仍有 4 处既有断链，见 §8 |
| 不修既有 clippy 警告 | 变更纪律（不改无关既有问题） | 8 处警告全部在 log-2/log-3 的 `resources/` 与 `app/toolbar.rs`；本轮新增代码零警告 |
| Q1–Q6 与四项策略登记为 `ratified`，而不是继续挂着"建议" | principle #23/#25/#38；blue1 T00.04（验收＝决策、备选、兼容影响同步白皮书） | 白皮书 §17.7 自己写着 Q2/Q3"首轮开发前应确认"；以"建议"身份长期挂着会让 T02.01/T15.01/T13.03/T12.04 无法判断能否依赖它，直接写成"已实现"则是虚报。因此登记为**策略**：一条决策一条条目，带备选、拒绝理由、兼容影响、复核触发、责任人与受影响任务 |
| 决策登记放在 `decisions.json` + 逐行校验的 Markdown + 白皮书交叉校验 | resources.md §16.1 与 T00.03 的同一手法；principle #59 | 结论出现在三处（数据源、登记文档、白皮书 §17.7），只靠人记得同步必然漂移；检查脚本同时钉住三者，另加一条"悬置问题必须有归宿"的规则 |
| 应用身份与发行取值记为 `open` 而不是代填 | issue-20261013.md §3；principle #22/#26 | 应用 ID、最低系统版本、发行形态、品牌取值（以及 `.ai/` 材料策略）只有项目方能给；代填等于伪造身份，并会让 `identity.json` 的"待决定"状态失去意义 |
| 决策登记明确写出"登记 ≠ 实现" | principle #22/#25 | T00.04 的产物是策略；把 `ratified` 读成"功能已存在"是最可能的误读，因此在数据、文档与白皮书三处都写出边界 |
| T00.05 的契约写成**可执行类型 + 检查脚本**，而不是一份设计文档 | principle #6/#59；blue1 T00.05 | 路线图要求"跨视图/服务没有第二份可写模型"，这是一条结构性质：写成散文只能被相信，写成类型 + 枚举检查才能被拒绝。检查脚本会拒绝未声明的写入入口、公开字段、以及点名了不存在用例的不变量 |
| 权限表由代码、数据文件与白皮书三处互相校验 | principle #22/#59 | 这是全项目唯一"代码照文档抄"的表，也是唯一决定 agent 能不能写文件/执行构建的表；只让人记得同步必然漂移 |
| 契约树整体 `#![allow(dead_code)]`，并写明理由 | 变更纪律 + principle #26 | T00.05 的契约消费方（T02.01/T03.01/T12.04/T15.03）尚不存在，绝大多数入口只被测试使用；删掉未消费的契约等于删掉本任务的交付物，所以按"沉默一次并写明原因"处理，而不是逐条加 `#[allow]` 或删代码 |
| 视图不携带固定修订 | principle #25（不做过强声明） | 视图借用模型时永远是当前状态，声称"视图可能过期"是类型不保证的承诺；需要记住读取时刻的是快照，它带 stamp 且可判过期 |
| 模式按路线图 §2.1 的七个（欢迎/工程/设计/代码/运行与调试/测试/发布），而不是按 T00.06 任务描述里的五个 | 路线图是总规划；principle #38 | 任务描述写的是其中五个；按七个执行只会多覆盖，不会少覆盖，并把这个差异写在 journeys.md 里 |
| 旅程走查把"入口"定义成**已声明分组通配之下的叶项**或**已声明面板** | principle #59（不得漂移的平行实现） | 走查可以细化菜单，但不能凭空新增菜单分支；入口必须落在 `resources/host/icons/manifest.json` 已声明的组里，检查脚本据此拒绝"发明出来的入口" |
| 走查声明 `implementation: none`，并由检查强制 | principle #22/#25 | 170 个步骤有入口设计不等于有界面；把这个状态写进数据文件并由检查冻结，避免把设计读成实现 |
| 每个步骤都要有归属任务，无入口的步骤还要写理由 | blue1 T00.06 验收（缺入口有任务归属） | 归属必须是在 `roadmap.md` 中真实存在的任务 id，检查脚本逐条核对，防止写出不存在的归属 |
| 面板可发现性可检查：旅程用到的面板必须至少出现在一个模式的默认面板里 | principle #25（结论需可核对） | "用户找得到"如果不写下来就只能靠感觉；把面板→模式的映射写成数据后，找不到的面板会让检查失败 |

## 4. T00.01 实测事实

**四族契约（固定修订 c957fdec，`--probe-apis` 原始输出）。**

| 族 | API | 读回的观测 |
|---|---|---|
| layout | `FlexLayout::add_widget` / `child_ids` | `child_ids -> [11, 22, 33]`，`item_count == 3` |
| layout | `Layout::update` | 100×40 行内两个等权子项 `1 -> (0,0,50,40)`、`2 -> (50,0,50,40)`，两次运行一致 |
| layout | `Layout::arrange` | `Hints::fixed(30,20)` 两项主轴 `1 -> x=0,w=30`、`2 -> x=30,w=30` |
| generation | `designer::availability` | `button -> Local`；`definitely_not_a_widget -> Unknown` |
| generation | `platform::profile` | `profile_name -> "desktop"`、`ProfileClass::Device`、full widget set、OS runtime 存在 |
| generation | `designer::generate`（Default） | `Ok`，4772 字节，报告洁净，含 `fn probe_ui`，两次字节一致 |
| generation | `designer::generate`（Stripped） | `Ok`，1803 字节，0 unsupported、0 超容量、1 项跨 profile 提示 |
| generation | `validate_function_name` | `ui_root` 接受，`123bad` 拒绝并给出原因 |
| event | `Signal::connect_with_priority` | 连接顺序 low→normal→high，派发顺序 `["high","normal","low"]` |
| event | `Signal::emit`（同优先级） | 按连接顺序 `["first","second","third"]` |
| event | `Signal::connect_once` / `slot_count` | once 槽两次 emit 只触发 1 次；触发后 `slot_count` 回到 1 |
| unbind | `Signal::disconnect` | 有效句柄返回 `true` 且槽不再触发；重复 disconnect 返回 `false` |
| unbind | `ConnectionScope` | 作用域 drop 后槽自动解绑，`slot_count == 0` |
| unbind | `Signal::disconnect_all` | 一次清空 3 个槽，之后 emit 不再触发 |

**确定性。** 同一修订、同一主机连跑两次 `--probe-apis`，`api-probes.json` 摘要一致
（`a2660917…`）。探针不读时钟、文件系统或网络。

**上游修订被钉住。** `probe::report` 的漂移测试重新解析 `Cargo.lock` 中 `rust_widgets`
的 `version` 与 `source` 段，任何与 `DEPENDENCY_VERSION` / `DEPENDENCY_REVISION` 的不一致都会
失败。

**需注意的库行为（非缺陷）。** 桌面宿主为 `Stripped`（mini/embedded）生成时，
`Availability::CrossProfileCaveat` 会被记入 `cross_profile_caveats`：宿主 profile 与目标不同，
答案对目标并不权威。设计器必须把该提示呈现给用户（原则 #8/#13）。

## 5. T00.02 实测事实（编辑 widget）

**按关注点的库层/宿主层划分：**

| 关注点 | 库层（rust_widgets）提供 | 宿主层（rustage）仍需做 |
|---|---|---|
| 编辑原语 | `insert` / `backspace` / `delete_forward`、`undo` / `redo`、`revision` 单调推进 | 决定哪些区域允许编辑、把生成区映射为只读跨度 |
| 受控编辑 | `replace_range` + `EditRejection`（`ReadOnly` / `StaleRevision`）在写入前拒绝 | 版本比较的来源（工程模型修订号）与冲突呈现 |
| 高亮状态 | `tokens_on_line` / `token_kind_at` / `line_state`、可插拔 `SyntaxHighlighter` | 每文档语言选择；内置词法器不足时提供真实语法 |
| 线程 | 高亮器 trait 要求 `Send + Sync`；编辑器本身**线程亲缘**（`Rc<RefCell<..>>` + `Cell`） | 编辑器固定在 UI 线程；后台分析结果回主线程 |
| 缓存 | `DocumentScale` 分级（50 000 行 `Reduced`、2 000 000 行 `ViewOnly`）在设置文本时定档 | 每个档位下保持逐帧工作量与视口成比例 |
| 坐标 | `select_word_at_point`（点→位置）、`viewport_snapshot` / `apply_viewport`、`visible_row_range` | 叠加层命中测试、DPI 策略 |

**逐项观测（8 项探针）：**

| API | 读回的观测 |
|---|---|
| `insert` / `backspace` / `delete_forward` | 光标置于 (0,1) 后 `insert("X")` → `"aXb"`；`backspace` → `"ab"`；(0,1) 处 `delete_forward` → `"a"` |
| `undo` / `redo` / `revision` | 编辑推进 `revision`；`undo` 还原 `"ab"`，`redo` 恢复 `"aXb"`；`can_undo` / `can_redo` 一致 |
| `replace_range` | 只读行 → `Err(ReadOnly)` 且文本不变；`revision+1000` → `Err(StaleRevision)` 且不写入；当前修订下的合法编辑成功 |
| 高亮（入口态为 Clean 的行） | `fn main() {` 含 `Keyword` 记号；行注释内位置 → `TokenKind::Comment`；开构造的行报 `Clean` |
| 多行高亮状态 | **缺口**，见下 |
| `SyntaxHighlighter` | `Box<dyn SyntaxHighlighter>` 成功移入工作线程并返回行末状态（编译期证明 `Send + Sync`） |
| `DocumentScale` | `for_lines` 在 50 000 / 2 000 000 行阈值给出 `Reduced` / `ViewOnly`；真实 50 000 行文档由编辑器报 `Reduced` |
| 视口与坐标 | `visible_row_range` 有序、`visible_rows > 0`；滚动改变快照，`apply_viewport` 精确往返；文本区内点位选中 120 字符的词 |

**唯一记录在案的缺口（库层，T00.02 交付物的核心结论）：**

`CodeEditor` 的每行「入口状态」缓存由**绘制路径**推进（`prepare_visible_line_cache` →
`ensure_line_states`，内部记录已证明到的 `walked_lines`）。绘制未到达的行，公共访问器一律
读回 `LineState::Clean`（`Default`）；`tokens_on_line` 又以该未证明的状态为入口对该行单独
分词。实测：`set_text("/* open\nstill\n*/\n…")` 后 `line_state(1)` 为 `Clean`，且该行分词
不含 `BlockComment` 记号。

这构成缺口而非边界：`LineState` 没有「未知」变体，也没有「该行状态是否已知」的谓词，调用方
**无法区分「不在多行结构中」与「尚未词法分析」**——原则 #22 禁止的"用成功形状的默认值掩盖
失败"。设计器需要任意行的语法状态（折叠、缩进推断、结构大纲都会问到屏幕外的行）。

- 库层建议：为 `LineState` 增加 `Unknown`，或增加 `line_state_is_known` / 公共推进入口。
- 宿主层绕行（已采用）：把高亮状态查询限制在绘制路径覆盖的行；屏幕外的行按"状态未知"处理。
- 完整复现步骤与建议见 [上游反馈](../rw-feedback/feedback-20261013.md) 第三节。

`C-SOURCEMAP`（节点 ↔ 源码区间）、`C-STORE`（唯一可写模型与只读视图）。

**"跨视图/服务没有第二份可写模型"是怎么成立的**：

| 层次 | 事实 | 证据强度 |
|---|---|---|
| 类型 | 文档只在 `DocumentStore` 里；节点写入方法是 `pub(crate)`；`DocumentView` 只借用模型且没有任何写入方法；`DocumentSnapshot` 字段私有、无 `&mut` 方法 | 结构（编译器） |
| 入口枚举 | `src/contracts/` 中所有 `pub fn`/`pub(crate) fn` 且带 `&mut self` 的方法被 `writers` 逐条声明；多一个就失败 | 检查脚本 |
| 公开字段 | 被声明的文件不得出现公开字段（公开字段会绕过所有入口） | 检查脚本 |
| 行为 | 变更集原子生效、陈旧 base 被拒、身份不复用、过期快照被标记、诊断过期不提供当前条目 | Rust 测试 |

**`apply` 的原子性怎么做到的**：校验与暂存发生在只含有本次被触及节点的 overlay 上，全部操作
通过后才提交；任一操作失败即整体拒绝，版本不动。代价是每个被触及节点一次 clone，开销与变更
规模成正比而非与文档规模成正比（whitepaper §17.9 第 6 条）；真实开销属于 T00.07/T03.01 的测量
问题，本记录不声称已测量。

**权限表的三方闭环**：白皮书 §12.5（出处）↔ `contracts.json`（数据，检查脚本逐行比对操作类别与
默认权限两列并校验行序）↔ `Capability::default_grant`（代码，`src/contracts/permission.rs` 里
一条测试从代码一侧读数据文件，逐条核对"操作 → 授权 → 拒绝原因"三元组）。

**本项的未覆盖项**：

1. **契约不是格式。** 没有 `designer-project.json` 的字段定义、没有磁盘布局、没有迁移器——那是
   T02.01 与决策 `Q6`；本项只固定内存中的形状。

   也不能判断某条不变量是否足够强。这一层留在复核，contracts.md 的"证据强度怎么读"一节写明
