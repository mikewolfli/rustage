## 3. 文件对话框：上游没有可用的选择器，宿主拿到的是"框"，以及我们如何接线

**核对结论（可复跑，见 §9）**：固定修订上 `rust_widgets::create_file_dialog(0, 0, 0, 640, 420)` 返回 `0`
（"未创建控件"）。源码与本机运行结果一致，且三个桌面后端都没有 override（上游反馈 8.1 给了逐行位置）。
自绘的 `FileDialog` 是一个**框**：标题、模式、起始目录、过滤器、`accepted`/`rejected`/`files_selected`
信号，**没有文件列表**。

因此本轮交付的是宿主的**一半**，并且明确写出另一半属于 F26 的界面工作（不造假实现）：

* `DialogMode`（open file / open files / save file / select directory）→ 一一映射到上游 `FileDialogMode`，
  映射函数是 `const fn`，两种词汇不可能各自漂移。
* `DialogRequest`：模式、标题、起始目录、过滤器（直接用上游的 `FileFilter` 类型，不另立一份同名概念）、
  **宿主自有列表当前的选择**、几何。
* `show()` **不阻塞**。这是本轮第一个设计决定：框必须挂载在驱动 UI 的线程上，而该线程要一直跑循环让用户
  操作；一个阻塞的 `choose()` 会把它刚打开的窗口冻住。所以返回 `PendingChoice`，宿主轮询。
* `PendingChoice::accept()`/`cancel()` 派发的是**用户按 Return / Escape 时走的同一事件路径**
  （`runtime::dispatch_event(id, &Event::key_press(ENTER|ESCAPE, 0))`），脚本化宿主因此不是绕过机制，
  而是走同一个机制。`PendingChoice` 的 `Drop` 会取消并注销，未答复的请求不会把模态栈留着。
* **接线的关键细节**：信号必须在 `register(Box::new(frame))` **之前**连接（注册表拿走所有权之后宿主只有
  `ObjectId`，而 `Widget` 没有 `as_any_mut`，无法下转型回 `FileDialog`）。上游信号内部是引用计数，
  所以连接跨移动仍然有效——这一点由 `the_frame_chooser_shows_a_frame_a_host_can_answer_and_clean_up`
  实测而不是假设。这是上游反馈 8.2 记录的可判定性建议。
* **选择校验**（`check_selection`）：这是"文件对话框"里真正属于宿主的另一半，也是在库没有列表时唯一能
  完整做完的一半。规则逐条对应蓝图 T01.02 的验收词：Unicode（原样保留）、符号链接（报告**链本身**与
  解析后的目标，而不是悄悄改写用户的选择）、权限（真去打开读一次，不用权限位猜）、类型（文件/目录选错
  即 `WrongKind`）、保存目标的父目录（不存在/不是目录/写不进去分别报告，写不进去用"创建一个探针文件再删掉"
  来回答，因为权限位不反映只读挂载与 ACL）、**空选择被接受 = `NothingChosen`**（不是"成功但结果为空"）、
  取消是 `Cancelled`（不是空列表）。

`DialogOutcome` 因此有 `Accepted`/`Cancelled`/`Refused`/`Unsupported`/`Failed` 五态，没有"成功形状的默认值"。

## 4. 剪贴板：把"空""不是文本""被拒绝"三件事分开

上游提供 `set_clipboard_text -> bool` 与 `get_clipboard_text -> String`，另有 rich 后端。本轮把宿主侧的
答案分层：

* 写入：`bool` 为假即 `ClipboardWrite::Refused { reason }`，不静默。
* 读取：先问 rich 后端（`Some(Text)`/`Some(其它 MIME)`/`None`），没有 rich 后端才退回文本访问器。
  `ClipboardRead` 保留 `Text`/`NotText{content_type}`/`Empty`/`Unavailable{reason}` 四态；退回文本访问器时
  "空"与"非文本"会合并——模块文档写明**合并发生在哪里**，而不是假装能区分（上游反馈 8.6 提了建议）。
* 本机实测：写入并读回 35 个字符（含中文与 `—`、`✓`）成功；`platform_clipboard()` 为 `None`，
  所以走的是"文本访问器"这条路，且报告里注明了这是状态后端、与桌面剪贴板无关。

## 5. 系统路径与宿主目录：把"能不能用"变成结构化答案

`paths.rs` 原有 `ProjectRoot`（决策 F1 的越根拒绝，含符号链接逃逸）与 `SystemPaths`（config/cache/data/temp，
OS 未指明时返回 `Err` 而不是回退到工作目录）。本轮补的是 T01.02 要的"系统路径服务"：

* `HostDirectories`：四个目录**一次解析**（不是每次调用重读环境变量——那会出现"一半文件在这、一半在那"，
  与原则 #6 的唯一事实来源冲突）。`with_roots` 供检查与测试使用，避免"为了证明缓存目录能用而写进开发者真实缓存目录"。
* `DirectoryState`/`ensure`：`Usable`/`Absent`/`NotADirectory`/`Unusable{reason}`；`ensure` 创建后**回读一次**，
  因为 `create_dir_all` 成功是关于调用的断言，不是关于目录的断言。文件挡路时报 `NotADirectory` 且**不覆盖**它。

## 6. URL 打开：宿主自己实现，因为上游没有；并把两类答案分开

上游没有任何把目标交给系统处理器的 API（上游反馈 8.3）。本轮的宿主实现要点：

* `accept()` 先判形状再判含义：以 `-` 开头 **拒绝**（`open`/`xdg-open` 会把它当自己的选项；实测
  `xdg-open -- <path>` 也是 "unexpected option"，所以转义不是出路）、含控制字符拒绝、无 scheme 拒绝、
  scheme 不在 `http`/`https`/`file` 内拒绝、路径不存在拒绝。每条都有独立变体与句子。
* 启动后区分三种事实：`HandedOver`（处理器退出 0）/ `HandlerFailed`（带它自己的退出码与 stderr）
  / `HandlerMissing`（根本没能启动），另有 `StillRunning`（超过超时仍在跑，**不杀**用户要求打开的
  应用，转入后台回收避免僵尸）。原则 #45 要的"命令可启动≠命令成功完成"就落在这些变体上。
* 平台程序名映射放在一处（`program_for`），`cfg!` 写成值而不是 `#[cfg]`，所以 macOS/Windows 的映射
  在同一台机器上也被测试检查，而不是"只有非运行平台的分支看不见"。
* 测试用**宿主自己控制的处理器脚本**（`exit 0` / `echo … >&2; exit 3` / `sleep 30`）真实跑进程，
  因此这条路径不需要打开任何用户的浏览器。

## 7. 平台文件事件适配：给 T03.05 用的有界轮询

* `DirectoryWatch::start` 把上游 `AssetWatcher` 包成可轮询对象；**启动失败是错误**（路径不存在/不可读），

### 15.1 交付物一览

| blue2 交付项 | 实现 | 真实调用路径 |
|---|---|---|

### 15.2 设计决定（每条都对应一处"否则会造假"的地方）

1. **提交返回，运行不在调用者线程上。** `submit` 只入队；调用者（即 UI 线程）用 `record`/`wait`/`snapshot`
   自己决定等多久。就绪检查实测：`submit returned in 16.9µs while the job ran`。
2. **`Cancelling` 是状态，不是 `Cancelled` 的同义词。** 取消运行中的任务只把记录推进到
   [`TaskState::Cancelling`] 并置位 token；只有 job 真正返回才落 `Cancelled`。这是路线图验收词
   "取消中状态真实"的落点，测试 `a_running_task_is_cancelling_until_the_job_actually_stops` 在 job
   尚未返回时断言 `Cancelling` 且 `outcome.is_none()`。
3. **杀不掉的 job 要报告，不能假装停住。** 宿主无法 kill 线程，所以期限只能"请求"：期限到达 → 请求取消
   （状态 `Cancelling`，记 WARN）；宽限期过后仍未返回 → `TaskOutcome::Abandoned { deadline, job_still_running: true }`，
   宿主停止等待；job 之后返回时把 `job_still_running` 置 false 并记 WARN，**结果一律丢弃**。
4. **取消请求输给成功要如实记录。** job 在收到取消请求后仍然成功返回时记 `Succeeded` 并保留
   `cancel_requested`：工作确实发生了，报成 `cancelled` 会误述磁盘上的结果。
5. **job 自称"被取消"但没人请求过 → 记失败。** 这是 job 缺陷，不是事实。
6. **job panic 不会带走 worker。** `catch_unwind` 把 panic 变成该任务的 `Failed`，worker 继续服务其他任务
   （否则一个坏 job 会让后续所有任务永远排队）。测试 `a_panicking_job_does_not_take_the_executor_down`。
7. **队列有界且会说不。** 满则 `QueueFull { capacity }`，理由里写清容量。
8. **所有权只做作用域，不做权限。** `SubmitRequest` 记录 `principal`/`capability`，但**不执行**权限判定
   （T01.05 的契约）；模块文档明说这一点，避免被读成已有权限检查。
9. **`JobControl` 按值传递。** 它只是两个引用计数句柄加一个 `Option`，按值传让调用方写
   `|control| { … }` 即可；按引用会让每个闭包都必须写成 `|control: &JobControl|` 才是 higher-ranked。

### 15.5 本轮发现并修的测试不稳定（ETXTBSY）——属于 T01.02 的修复

跑全量时发现 `host::open_url` 有约 1/6 概率失败，报
`HandlerMissing { reason: "Text file busy (os error 26)" }`。定位与处理：

* **原因不是权限也不是路径**，而是 `ETXTBSY`：内核拒绝执行"任何进程仍以写方式打开"的文件。
  多线程进程里这是**瞬时**的——某个线程 `fork`（`Command::spawn`）时，另一个线程正写那个脚本，
  子进程在 exec 之前继承着那个写描述符，于是 exec 被拒。测试并行 spawn 时窗口被撞上。
* **修复 1（产品代码）**：`ProgramOpener::spawn` 对 `ErrorKind::ExecutableFileBusy` 做**有界重试**

## 17. T01.04 子进程、日志、退出与定向树清理

依据：[MS01 实施步骤](../plan/blue2.md) T01.04（前置 T01.03，已完成）。
产物：[`src/host/subprocess.rs`](../../src/host/subprocess.rs)，接入 `--probe-host`；新增一个**仅 unix** 的依赖 `libc`（见 §17.3）。

### 17.1 交付物与验收落点

| blue2 交付项 | 实现 |
|---|---|
| 子进程启动 | `ProcessSpec` / `OwnedProcess::spawn`：程序与参数逐项传递（不经 shell 解析），可设工作目录、环境变量 |
| 日志 | 两个流各一条读取线程 → 有界缓冲；`output_so_far`（运行中快照）与 `ProcessOutcome.output`（结束后定稿） |
| 退出 | `ExitInfo { code, signal }`；`wait` / `wait_for(limit)`；`ProcessOutcome::summary()` |
| 定向树清理 | `terminate(grace)`：给**本会话创建的进程组**发 `SIGTERM` → 宽限期内收尸 → 仍不退出则 `SIGKILL` 整组 |
| 平台信号策略 | unix 走进程组；无该机制的平台返回 `Termination::DirectOnly { exit, reason }`，明说后代未被处理 |

**验收词"仅清理本会话拥有进程，不误杀外部进程"** 的判据是一个结构性事实，而不是启发式：
子进程用 `Command::process_group(0)` 建自己的进程组（组长即子进程），终止只对**这个组**发信号。
不扫描进程表、不匹配程序名、不读 pid 文件——因此一个同名、同父、同用户但与本次启动无关的进程
不可能被命中。`ownership_evidence()` 把这条判据作为**值**输出，报告与日志都能带上它。

### 17.2 设计决定

1. **"已经结束"和"被我们终止"分开。** `Termination::{AlreadyExited, Stopped, Killed, DirectOnly, SignalFailed}`
   五态；`Stopped` 与 `Killed` 各自带耗时，`DirectOnly` 必须带原因。不给"清理完成"这种笼统结论。
2. **礼貌信号 → 期限 → 强制。** 只有限期内没停才升级为 `SIGKILL`；调用方能从结果看出走了哪一步。
3. **有界日志不静默丢弃。** 超过 `capture_limit` 的字节被丢弃并**计数**（`dropped_bytes`），
   `summary()` 会写"dropped N bytes"。UI 因此可以说"日志被截断"，而不是把前缀当日志全文显示。
4. **Drop 不杀进程。** 释放句柄不等于要求进程结束；静默 kill 会让"进程仍在运行"无法被报告。
   要它停就显式 `terminate`。
5. **会话标记是证据，不是判据。** 每个子进程带 `RUSTAGE_SESSION=<pid>`，供人看进程表时回答"谁启动的"；
   终止**不**依据这个变量——否则任何设了同名变量的进程都会被杀，正是本模块要避免的错误。
6. **无该能力的平台说清楚。** 非 unix 上没有进程组信号，`DirectOnly` 报出"直接子进程已结束、后代未处理"
   并附原因；把"清理完成"写在没有能力的地方，就是原则 #22 禁止的占位成功。
7. **`presence(pid)`（零信号存活查询）** 单独提供：报告和测试要的是"它真的没了吗"，
   而不是"我们发过信号所以大概没了"。`EPERM` 记为"仍在运行"（存在但不属于我们），不记为"已消失"。

### 17.3 依赖与平台边界

* 新增 `[target.'cfg(unix)'.dependencies] libc = "0.2"`：`kill(2)` 的进程组信号与存活查询标准库不暴露。
  按原则 #47 声明在目标配置里，而不是所有目标；解析结果就是 `Cargo.lock` 里已有的 `0.2.190`（由 widget
  依赖传递引入），因此**没有新增下载**，`cargo build --offline` 通过。
* `cfg(unix)` 只出现在 `subprocess.rs` 的 `presence`、`command_group`、`signal_group` 与 `terminate`
  内部；公共 API 只有一个形状，能力差异用 `Termination::DirectOnly` 的**值**表达（原则 #37）。

### 17.4 验收证据（`--probe-host` 第 9 项检查）

```
process-trees     ready   termination: stopped after 5.23ms; the polite signal ended it (killed by signal 15);
                          59836 leads process group 59836, created by this session; termination signals the group,
                          so only processes started in it can be reached (marker RUSTAGE_SESSION=rustage-59571);
```

### 17.5 未覆盖项（T01.04）

1. **非 unix 平台没有进程组清理。** `DirectOnly` 是当前在非 unix 上的真实结论；Windows 要做到同等
   语义需要 Job Object（或等价机制），本轮没有实现，也没有在任何非 Linux 平台上运行过。
2. **没有 PTY、没有 stdin 通道、没有交互式终端的窗口尺寸/信号转发**（终端面板是 T16.x/T06.x）。
3. **没有资源限制与隔离**：不设 CPU/内存/文件描述符上限，不做 cgroup/沙箱；失控进程只能被终止，
   不能被隔离（§15.6 第 6 条同样如此）。
4. **宿主崩溃后的孤儿进程无人回收**：`Drop` 不杀，也没有"下次启动时清理上一会话遗留"的机制。
   标记 `RUSTAGE_SESSION=<pid>` 是为此预留的证据，但清理策略未实现。
5. **日志没有汇入输出面板/通知中心**（T01.06）；本轮只提供 `CapturedOutput` 与摘要文本。
6. **没有把子进程纳入项目作用域**（T01.07）：执行器给了 `OwnerId`，子进程本身还没有归属字段，
   关闭工程时"随工程结束的子进程"目前要靠调用方自己关联。
7. **库内自行启动的进程不在本会话归属范围内**（上游观察 8.8）：库的打印 spooler 用
   `Command::new` 直接启动并只 `kill()` 直接子进程，既不在我们创建的组里，也没有整组清理。

### 17.6 写测试时踩到的一个真实竞态（记录在案，因为它影响正确性判断）

最初把"不理会礼貌信号的进程"写成 `sh -c "trap '' TERM; sleep 30"`，然后立刻 `terminate`，
结果稳定得到 `Stopped`（5ms 内被 `SIGTERM` 结束），看起来像"trap 不生效"。
实际原因是**信号在 shell 安装 trap 之前到达**——此时进程还没有忽略处理，被 `SIGTERM` 结束是正确行为。
用 `kill`/`os.killpg` 手工复现（延迟 300ms 再发信号）时 shell 确实存活着，验证了这个解释。
测试因此改为让脚本在装好 trap 后打印 `ready`，等它出现再终止（脚本里那行注释与本节都写了原因）。
这不是测试技巧问题：它说明"宿主的宽限期"必须容忍"进程还没来得及安装处理程序"这一窗口，
而这正是宽限期存在的意义——先礼貌、再强制。

### 17.7 上游反馈（T01.04）

它既不在宿主创建的进程组里，超时也只 `kill()` 直接子进程，因此宿主的"仅清理本会话拥有进程"
无法覆盖它。建议（不急）是库内启动子进程时也建独立进程组并按组清理，或提供库级进程注册表。

这条检查做四件可观察的事，而不是读返回值：

1. 在一个真的含有 `build.rs` 的临时工程目录上，**未信任**时申请命令许可 → 被拒，且作为副作用标志的
   `ran` 文件**不存在**（"没跑代码"是文件系统事实，不是返回值）。
2. 信任该工程后，**仍然被拒**（`scope-not-authorized`）→ 说明"信任"与"授权"是两件事。

4. **撤销授权**后再申请 → 再次被拒，且删掉的 `ran` **没有被重建**。

产物里同时打印了**整份授权记录**（7 条，见上），因为"7 条记录"是主张，把 7 条打出来才是证据。

### 19.3 从检查里读出来的一个语义事实：信任管住所有人，授权范围管住 agent

第一版用例把"信任之后仍需要授权"写成了对**人**的断言，跑出来是**红的**——这不是实现错，是我读表读错。
`PermissionGate::decide` 的语义来自白皮书 §12.5 的原文：`运行 cargo check` 那一行的授权条件是
"**工程已信任且执行范围获授权后 agent 可触发**"，而 §12.5 整张表描述的是 **agent 的自主边界**；
人在自己信任的工程里本来就可以运行命令。所以本轮真正成立的表述是：

* **未信任** → 人和 agent **都**拒绝（`untrusted-project`），这是验收词"未信任工程不执行代码"的字面含义；
* **已信任但未授权范围** → 人可运行（表里没有限制人），**agent 被拒**（`scope-not-authorized`）；
* **撤销授权** → agent 再次被拒。这正是验收词"授权范围可撤销"的可观察形式。

这条差异写进 §19.3 而不是悄悄改测试，因为它决定 T05.01 命令可用性怎么算、T05.07 权限解释怎么说：
如果把"需要授权"套在人身上，菜单会把合法的操作显示成禁用。

### 19.4 "未信任工程不执行代码"是靠类型而不靠记性

`ExecutionPermit` 的五个字段全部私有，全项目只有一个铸造点 `PermissionService::permit`，而
`OwnedProcess::spawn` 要求 `&ExecutionPermit`。于是"忘了检查"这个失败模式在**编译期**就不成立：
没有许可，就没有可以传进 `spawn` 的值。生产代码里启动程序的位置一共两处（`grep -rn "Command::new" src/`）：

| 位置 | 是否受许可约束 | 说明 |
|---|---|---|
| `src/host/subprocess.rs:447` | **是** | 宿主自己拥有的命令；`spawn` 另校验许可的 `EffectClass` 必须是 `Command`，否则报 `SpawnError::PermitForAnotherEffect` |
| `src/host/open_url.rs:341` | 否 | 交外部处理程序（见 §19.7 第 3 条，本轮记为未覆盖并说明理由） |

另外两处 `std::process::Command::new`（`readiness.rs` 与 `subprocess.rs` 的测试）是**故意**不受约束的"外部进程"，
它们存在的意义正是证明宿主的清理不会碰到本会话之外的进程（§17.4）。

`--probe-host` 的 `process-trees` 检查现在也走同一条路：它先申请会话范围的命令许可，再把许可写进证据
（`command permitted in session for Human via authorized-when-trusted (record entry #1)`）。一个绕过许可自己
`spawn` 的检查会是在演练一条调用方走不到的路。

### 19.5 设计决定

1. **许可按效果类别，不按调用点。** 调用方声明"我要做哪一类外部效果"，而不是"我是哪个服务"。
   这是 `EffectClass` 存在的理由：服务会改名、会拆分，效果分类来自路线图标题本身。
2. **未决定就是拒绝，并说明缺少哪条决定。** `Network`/`Deploy` 在 §12.5 里没有行，因此返回
   `PermissionRefusal::Undecided`，附上"决策表没有这一行，网络授权是 T01.09 的契约"。默认放行会是
   权限表唯一禁止的答案（原则 #22）；悄悄当成 `Command` 则等于凭空发明一条授权。
3. **不给未信任工程记录任何授权。** 对未信任工程调用 `authorize`/`approve` 会被**拒绝并记录**，而不是
   先存下来等信任后再生效。否则会出现"看起来已授权、其实没有"的状态，而人要到构建不跑的时候才知道。
4. **撤销信任会连坐，并且说明连坐了哪些。** `distrust` 返回并记录被一并撤销的批准/授权清单
   （路线图 §3.2 要求设置页"作用域、覆盖来源和重置可见"；只清空状态的话，重置就是静默的）。
5. **未知工程与未信任工程是同一种东西。** 没有人做过的决定就是没有决定；不设第三种"未知"答案，
   免得它被读成放行。
6. **会话范围不是漏洞，是一次显式判断。** 宿主自己的工具（探针、图标渲染、用户要求的构建）不是从别处
   取来的工程代码，§12.5 的信任规则针对的是工程。会话门禁在服务构造时即信任，但它**不授予任何能力**：
   agent 要跑会话范围的命令仍然需要 `authorize`（`an_agent_needs_the_session_scope_authorized_too`）。
7. **决策也记账。** 记录里既有信任与授权，也有每一次允许/拒绝。只记状态的记录回答不了"当时为什么允许"，
   而这一轮之后 T05.07 的权限解释、T01.06 的错误详情都要引用它。
8. **时间来自唯一的时钟。** `PermissionService` 用 `host::log::Clock`（与日志同一个），测试用 `FixedClock`
   把记录钉死成 `[0ms, 200ms]`，因此产物是可复现的（原则 #35：同一件事只有一份定义）。

### 19.6 一个真实缺陷：被继承的管道写入端让"5ms 停止"报成"30s 停止"

**现象。** 本轮改完 `spawn` 签名后跑全量测试，`a_cooperative_process_stops_after_the_polite_signal`
失败一次，断言值是 `after = 30.001030294s`——恰好是那个 `sleep 30` 的一生，而整轮测试也只用了 30.01s。

**定位。** 推理把范围压到一点：`Stopped` 只在宽限期内观察到子进程结束时返回，`finally` 的宽限期是 5s、
`signal_group` 是一次 `kill(2)`，所以 30s 只能花在 `reap_readers()` 上——它 `join` 两个读线程，而读线程只在
**管道写入端全部关闭**（EOF）时才结束。正常情况我在 60 次循环里量过：观察到退出约 5ms，排水约 10µs。
异常情况是：**另一个线程正在建管道时 fork 出的子进程继承了写入端**（就是 T01.02 里 `ETXTBSY` 那次
同一类竞态，见 §12.2），于是"子进程已死"与"EOF 到来"之间隔着那个无关进程的一生。而 `after` 是在
`reap_readers()` **之后**才求值的，所以报出来的"停止耗时"其实是"宿主排水耗时"。

**两处都修（都属于本轮的改动面，因此不推给后续任务）：**

1. **测什么就报什么**：`Stopped`/`Killed` 的耗时在排水**之前**取，并抽出 `reap()` 把"等子进程"与
   "等读线程"分开，注释写明理由。
2. **排水有界**：新增 `DRAIN_DEADLINE = 1s` 与 `wait_for_readers()`；到期未等到 EOF 就记一条 warn
   （"N of M stream readers … did not reach end-of-file within 1s …"）并把线程**脱离**，
   而不是把调用方挂住。子进程自己写的东西在它结束时就已在内核缓冲里，1s 足够读完；等不到的那个写入端
   属于别的进程，本来也不是我们的输出。

**回归用例**（不依赖那条竞态，因此可重复）：`waiting_for_readers_stops_at_its_deadline`（一个读线程故意
2s 后才报告，等待必须在 50ms 到期）、`a_reader_that_never_reports_is_not_counted_as_finished`（发送端全断开
时不得视为已完成，也不得等满整个期限）、`waiting_for_readers_counts_them_all_when_they_finish`。

**我没有做到的**：那条竞态本身没有再复现（8 次全量测试都是 `234 passed`），因此上面 1 的"报数不再被排水
污染"只有推理与代码结构支撑，没有一次现场复现作证据。这一点按原则 #25 如实写在这里，不写成已验证。

### 19.7 未覆盖项（T01.05）

1. **信任不持久化。** `PermissionService` 是进程内状态：重启后一切回到"未信任"。持久化属于 T02.01
   （工程公开配置与机器本地存储）与 T02.03（打开工程时的信任提示），本轮不抢先定义存储格式。
2. **没有信任提示的界面。** `TrustPrompt` 是提示所需**事实**（`build.rs`、`.cargo/config.toml`、
   `rust-toolchain*` 各自能做什么），把它画成对话框并按 §3.4"最后一步展示最终变更和失败影响"来做，
   是 T02.03 的工作；本轮没有 UI，也没有把"人看过提示"当成可核验事实。
3. **`open_url` 的启动路径没有接许可。** 它是宿主第二处启动程序的位置，但（a）今天没有任何生产调用方，
   （b）它交出去的是**用户自己的处理程序**而不是工程代码，把它套上 `Command` 类许可在今天等于
   做一个永真判断。留给 T01.07（服务注册表统一启动接缝并给服务工程作用域）与 T01.09（网络授权）一起定，
   而不是现在造一个空的检查点。**这是本轮"未信任工程不执行代码"唯一没有结构性保证的启动位置。**
4. **执行器提交时的能力声明仍未强制。** T01.03 的 `SubmitRequest` 记录 `principal`/`capability`，
   本轮**没有**在 `Executor::submit` 里加门禁：真正的执行点在 `spawn`，而任务里能做的工作是宿主自己的闭包，
   不是工程代码。给提交加一层"声明式"门禁会造出第二条与实际执行不同的权限路径（原则 #59），
   因此留到 T01.07：那时 `OwnerId` 才有工程作用域，`SubmitRequest` 才有工程可问。
5. **没有"关闭工程即结束其工作"的路径。** 与上一条同源：`OwnerId` 目前不携带工程数据，T01.07 接上。
6. **网络与部署只有"未决定"。** 见 §19.5 第 2 条：本轮交付的是"准确拒绝"，不是网络/部署能力本身。
7. **记录只在内存里，且只在单进程内。** 没有落盘、没有轮转、没有跨会话合并；工程诊断包（T22.x）
   与通知中心（T01.06）要引用它时需要再决定保留策略与脱敏（原则 #33：日志不得泄露机密——
   本轮的记录只写能力名、作用域路径与主客体，不写命令内容与参数，这一点是有意的）。
8. **未在非 Linux 平台上运行。** 权限判定、信任提示与记录是纯逻辑+文件读取，平台无关；但
   `project-trust` 检查为了证明"命令真的会跑"要一个 shell，非 unix 上会像 `process-trees` 那样记
   `not-verified`（缺的是证据，不是能力），这一点**没有在真实 Windows/macOS 上验证过**。

### 21.2 验收词是怎么被结构保证的

"错误有原因与下一步，不只输出日志"有两个半：**每个错误必须有原因与下一步**，以及**普通日志不得变成通知**。

1. **原因只能来自真实生产者的值。** `Cause` 的四个变体各自持有一个真实值——`TaskRecord`、
   `ProcessOutcome`、`SpawnError`、`PermissionRefusal`——并且**没有任何接受自由文本的构造函数**。
   因此"把一行日志变成通知"这件事在类型上不成立；`report()` 只接受 `Cause`。
2. **下一步不可能缺失。** `Cause::steps()` 是对四个变体的全量 `match`，每个分支都返回至少一个
   `NextStep`，所以新增一种原因时编译器会强制回答"那接下来怎么办"。
3. **动作与建议分开。** `NextStep::Do` 是宿主或界面**可以执行**的动作（重试 / 停止任务 / 打开任务 /
   打开日志）；`NextStep::Advice` 是给**人**的一句话，用在没有自动恢复手段的地方（安装程序、修正路径）。
   权限拒绝的建议直接复用契约自己的 `DenialReason::explanation()`（原则 #35：同一句话不写两份）。
4. **严重度由原因推导，不由调用方选择。** `Cause::severity()` 把执行器的答案翻译成级别：失败 → `error`；
   被放弃 / 被期限取消 / 拒绝 → `warning`；成功 → `info`；**被人取消 → `info`**（这不是问题，
   而"任务自己宣布被取消、却没人请求过"按 T01.03 记成失败，因此这里也必须是 `error`，不能软化）。
5. **重复只计数。** `report()` 返回 `first_time`，第二次起只增加 `occurrences` 并更新 `last_seen`，
   并且**不**再写日志（否则日志就成了它要避免的那种骚扰）。只有当同一问题的**消息不同**时才另开一条，
   因为"又失败了，但报的是另一件事"是新消息。被清掉的问题再次出现会重新出现在列表里——
   把复发藏起来正是原则 #22 禁止的静默失败。

### 21.3 验收证据（`--probe-host` 第 11 项检查）

```
notifications       ready        a real failed task -> error with a step that asks first because re-running
                                 can repeat its effects, and a task link; a real task that worked -> info;
                                 a real failing process reported twice -> 1 entry with 2 occurrences; a
                                 program that never started -> error; a refusal on an untrusted project ->
                                 warning; the catalogue: 5 notification(s) = 3 error, 1 warning,
                                 1 information, links ["task", "task", "process", "program", "permission"];
                                 #1 [error] task #3 "readiness: a task that fails" failed after 3.268µs:
                                 readiness: this failure is deliberate
summary: 9 ready, 1 gap, 1 not verified      exit=4
```

这条检查不用任何手写字符串：它让**真的执行器**跑一个真的会失败的任务和一个会成功的任务，让**真的子进程**
退出码 9 并在 stderr 写一行（同一结果上报两次），让**真的缺失程序**启动失败，再让**真的权限门禁**在未信任
工程上拒绝一次；然后要求每一条都有原因、至少一个下一步、一个链接，且严重度分别是 error / info / error /
warning，重复只记 2 次而不新增条目。产物里连第一条通知的完整渲染都打了出来。

### 21.4 设计决定

1. **三种严重度，不是五种。** 日志有 debug/trace，通知没有：通知是对"要人处理"的承诺，
   多出来的级别等于承诺会为噪声打断人。
2. **链接是数据，不是可点击的字符串。** `Link` 的每个变体都带真实 id（任务 id/归属、pid、程序路径、
   能力+作用域），界面因此能打开具体对象，而不是解析一段描述文字。
3. **`Cause::for_task` 在没有 outcome 时返回 `None`**，而不是造一条"暂无结果"的通知：
   排队中/运行中的任务没有可报告的事实，为它造条目就是原则 #22 禁止的占位成功。
4. **清空不删记录。** `dismiss` 只把条目移出"待处理"列表，`counts()` 与 `notifications()` 仍看得见；
   roadmap §3.2 要求"严重问题可追踪"，删掉就不可追踪了。
5. **第一次出现写一行日志。** §4.1 要求日志、通知、权限相互链接；一行**同级别**的日志就是那个链接，
   而且只写一次，这样日志不会变成横幅。
6. **时间仍然来自唯一的时钟**（`host::log::Clock`，与权限服务同一处），测试用 `FixedClock`
   把 `first_seen`/`last_seen` 钉成 `0ms`/`250ms`。

### 21.5 未覆盖项（T01.06）

1. **没有界面：没有横幅、没有面板、没有焦点策略。** blue2 T01.06 只到"中心"这一层；§3.4 与 T04.07 决定
   通知怎么到达人（不抢键盘、可发现），T05.07 决定权限解释长什么样。本轮交付的是它们要用的数据。
2. **恢复动作只被"描述"，没有被"执行"。** `RecoveryAction` 是数据；真正执行需要 T01.07 的服务注册表
   （那时宿主才能按工程拿到执行器与子进程），因此本轮没有 `apply(action)` 这样的方法——
   写了也没有诚实的实现。
3. **出厂路径还没有真实生产者。** 目前只有 `--probe-host` 的检查把真实失败送进中心；发出任务、
   跑构建、写文件的功能（T01.07/T16.x/T03.x）都还没接进来。这是本轮最实质的局限，写明于此。
4. **冲突与他人修改产生的通知没有来源。** roadmap §3.2 里的"恢复/冲突"依赖 T03.05（外部修改监测）
   与 T03.06（恢复副本），它们还不存在。
5. **通知不落盘、不跨会话。** 与权限记录同一局限（§19.7 第 7 条）：保留策略与脱敏要等诊断包（T22.x）
   与通知中心真正要引用它的时候再定。
6. **中心不抑制"同一批工作"的重复横幅。** 目前去重按"同一问题"合并；按任务/按工程的静音、

### 23.3 关闭顺序（为什么是这个顺序）

`CloseReport::order` 报告的固定五步：

| 步 | 做什么 | 为什么在这个位置 |
|---|---|---|
| 1 | 标记作用域已关闭 | 先于一切：调用方手里的 `ProjectServices` 从这一刻起被拒（`ScopeRefusal::Closed`），不会与正在拆的服务抢跑 |
| 2 | 停作用域的任务 | 执行器先拒绝新工作，再请求每个任务停止，并在自己的宽限期内等 worker；配合的 job 会顺手带走它拥有的进程（T01.04 的 `cancelling_a_task_that_owns_a_process_takes_the_process_down` 就是这条路） |
| 3 | 按组清理作用域的进程 | 第 2 步之后仍留在表里的，说明它的任务没有配合；先礼貌信号，超期才强制（T01.04 的策略原样复用） |
| 4 | 撤销该工程的信任与授权 | 授权是给**这一次打开**的，不是给这个目录永远的；重开必须重新问 |
| 5 | 记录没有停下来的东西 | 只有到这一步才知道哪些没落地；它们进 `CloseReport`，被放弃的任务另外进通知中心 |

### 23.4 设计决定

1. **一个工程一个作用域，键是已解析的路径。** 同目录的另一种写法（`nested/..`）不是第二个工程；
   第二次 `open` 被拒绝并说明为什么（`scope-table`），而不是悄悄给出第二个执行器——那正是"跨工程污染"的定义。
2. **失败的开只有两种结果，没有第三种。** 要么装好一个可用的作用域，要么什么都不变并说明失败在哪一步。
   路径先解析（不存在的目录不会被建出半个作用域），执行器最后起（它是唯一起线程的一步）。
3. **关闭先于拆除使句柄失效。** 关闭前拿到的 `ProjectServices` 是克隆，但共享同一个 `AtomicBool`；
   一旦关闭，`submit`/`spawn` 一律 `ScopeRefusal::Closed`。否则"关闭后调用方还能提交"是一个真实的悬挂来源。
4. **`close_scope` 与 `distrust` 是两件事。** 前者是"这次会话结束了"，后者是"我把信任收回了"；
   记录里分成 `closed` 与 `distrusted` 两种事件，因为读记录的人必须能分辨。这也是 T02.03 那句
   "打开时重新问一次信任"能成立的前提。
5. **拒绝被自动上报，关闭的发现不自动上报。** `spawn` 的拒绝恰好对应通知中心已有的两种原因
   （权限拒绝 → 契约自己的解释；程序起不来 → 检查说明），因此自动上报并成为**第一个出厂路径上的通知生产者**。
   反过来，"某个任务被放弃了"虽有对应原因（会进通知中心），而"某些进程没能被清理干净"没有诚实的下一步
   （见 §23.5 第 3 条），因此它只进 `CloseReport`。通知中心只接受下一步是诚实的原因——这条线本轮之后保持不变。
6. **进程句柄与作用域共享同一个进程。** 谁先 wait 谁收尸，另一方看到同一个状态；
   句柄在调用期间借用进程（`Mutex`），因此"谁收割了它"只有一个答案。
7. **不是空成功的关闭。** 关闭一个没打开的工程返回 `CloseFailure::NotOpen`，不是"关闭成功，0 个服务"。

### 23.5 未覆盖项（T01.07）

1. **没有决定"什么时候打开/关闭工程"。** 本模块只提供机制，时机属于 T02.03（打开/最近工程）与
   T03.07（关闭脏工程、任务停止与批处理弹窗）。因此出厂路径上目前仍没有 `open` 的调用方，
   只有 `--probe-host` 的检查在驱动它。
2. **`ProjectServices` 不持有文件服务与路径服务。** T01.07 的标题是"服务注册"，本轮注册进来的是
   执行器、进程、权限与通知；`paths::HostDirectories`/`ProjectRoot` 是纯函数式的解析与检查，
   没有需要停止的状态，因此没有进表——把不需要生命周期的东西也放进注册表只会制造"看起来要关"的错觉。
3. **"进程没能被清理"这条分支没有测试覆盖。** 在 unix 上要走到它需要 `kill(2)` 本身失败（`SignalFailed`），
   或平台没有进程组（非 unix 的 `DirectOnly`）。两者都不可在本机复现，因此 `ProcessCleanup::not_clean`
   在每次运行里都是空的。这是本轮最明确的"有代码、无现场证据"的一处，按原则 #25 写明。
4. **没有"按需启动服务"。** 作用域在打开时一次性起好服务，"现在还有什么在跑"因此只有一个答案；
   代价是打开一个只用一部分能力的工程也会起执行器线程（两个 worker）。懒加载要在真正需要时再决定。
5. **通知中心仍是进程级的，不按工程分区。** 一条通知靠它的 `Link`（任务/进程/权限）归属到工程，
   没有"只看这个工程的通知"的过滤；面板与过滤属于 T04.02。
6. **没有跨进程/跨会话的悬挂清理。** 宿主崩溃后上一会话留下的进程没人管（§17.5 第 4 条同样如此）；
   `RUSTAGE_SESSION` 标记是为此预备的证据，策略未实现。
7. **未在多进程或多线程并发打开/关闭同一工程下验证。** `open` 的重复检查与插入在同一把锁内完成，
   但"两个线程同时开同一个工程""一边关闭一边打开"只有代码结构与一次竞态检查（第二次检查）支撑，
   没有并发压力测试。

### 25.3 输入探针为什么是"两侧"的

只测"点一下会触发回调"是不够的：一个把事件广播给所有控件的实现也能通过。因此检查同时要求
**按下后落在控件外的抬起不激活**，并观察库自己发布的 `canceled` 信号。本机结果是
`clicked` 在第一次点击后为 1，第二次（外部抬起）后**仍为 1**，`canceled` 为 1——命中测试真的
发生了，而不是回调被无条件触发。键盘路径再单独验证一次（`Return -> clicked(2)`），
因为那是没有指针的人走的路径。

### 25.4 记录的三条规则（也是门禁在查的东西）

1. **`probed` 只允许出现在本记录产生的那台机器上。** 检查脚本要求恰好一台宿主 `probedOn`，
   且 `probed` 的格必须带 `outcome` 与证据。把别处结论抄进本记录会在门禁处失败。
2. **能力名来自探针源码。** 检查脚本从 `src/host/readiness.rs` 的 `Capability::name` 读出全部
   检查名，要求它们在组里恰好各出现一次；Rust 侧另有一条测试反向要求每个检查名出现在
   `host-probe.json` 里。两个方向都闭环：探针新增/改名一个检查而不更新记录，门禁和测试都会失败。
3. **文档表格由数据推导。** 六张表（状态、结果、组、宿主、矩阵、证据）逐行对照 `host-probe.json`，
   改一处漏另一处即失败——与支持矩阵同一套办法。

### 27.2 一处决策表变更，以及为什么它必须发生

路线图在四处要求"网络授权"（F16 不暗自联网、F20 网络授权可诊断、F23 逐项授权、§3.4 密钥/网络是宿主职责），
但白皮书 §12.5 的决策清单里**没有网络这一行**。因此本轮之前 `EffectClass::Network` 只能返回
"没有决定"（§19.5 第 2 条如实写明）。本轮把这一行补进 §12.5：

> | 对工程网络策略里的服务发起请求 | **工程已信任且服务范围获授权后 agent 可触发** | 会外发数据并可能携带凭据；只允许到达工程策略里声明并授权的服务，不暗自联网 |

它不是"实现方自己发明了一条授权"，也不是平行体系：**同一张表、同一套授权、同一条记录**，
只是多了一行。正因为如此，这次变更走完了全部已建立的门禁：

* `docs/plan/whitepaper.md` §12.5 增加该行（检查脚本逐行比对白皮书 ↔ 数据文件）；
* `docs/plan/contracts.json`/`contracts.md` 增加对应权限行与新的拒绝原因 `service-not-configured`；
* `src/contracts/permission.rs` 增加 `Capability::RequestNetworkService`、`DenialReason::ServiceNotConfigured`，
  以及"工程是否声明了网络策略"这一个**配置事实**（不是授权）；
* 三条断言旧事实的用例（网络"没有决定"）**按新事实改正**：现在只有 `Deploy` 仍无决定，
  而网络请求的拒绝来自契约本身（`a_network_effect_is_refused_by_the_contract_not_by_absence`）。

拒绝顺序也定在契约里：**先信任，再策略**。未信任工程得到 `untrusted-project`（"先信任工程"是更基本的
下一步），已信任但没声明策略得到 `service-not-configured`（"声明这个服务并授权网络请求"）。

### 27.3 三个"结构保证"而不是三条约定

1. **密钥打印不出来。** `Secret` 没有 `Display` 实现，`{:?}` 只写长度
   （`Secret([redacted; 24 bytes])`），取值必须写 `expose()`——审阅时可以 grep 这个名字。
2. **不可达的服务在配置层面就不存在。** `NetworkPolicy` 是目的地清单；没被声明的服务连"判断"都进不去。
3. **请求必须拿许可。** 唯一能打开连接的是 `connect(&NetworkPermit, ..)`，唯一能铸造许可的是
   `NetworkGateway::permit(..)`，它按顺序问四件事：策略里有没有这个服务、门禁是否允许
   （`EffectClass::Network` → `request-network-service`）、TLS 配置能否解析、凭据是否可用。
   与 `OwnedProcess::spawn` 要求执行许可同一形状。

### 29.4 设计决定

1. **根路径不进文件。** 文件所在目录就是根，所有引用相对它解析。把绝对根写进文件等于给"这个工程在哪"
   第二个答案，而工程一被搬动或换台机器检出，那个答案就是错的。
2. **数字保留字面写法。** `1e2` 与 `100` 是同一个值的两种写法；重新格式化把"人写的文件"变成"库写的文件"。
   写法留在 `Number` 里，解释才是转换（`as_u64`/`as_i64`）。同理，重复成员直接拒绝：一个名字两个值
   不是"有偏好的文档"，是一个意思有两种的文档。
3. **未知成员一律保留并报告，只有一个例外。** 例外是凭据引用与它的 `source`：那里成员集合是封闭的，
   出现未知成员按"机密被写进工程"拒绝（并说明材料该放系统钥匙串或环境变量），因为那个成员很可能
   就是密钥本身。JSON 与 TLS 配置的未知成员仍是保留，不是拒绝。
4. **机器本地状态不进工程文件。** 窗口几何、上次打开的页面、本机代理与 TLS 覆盖都属于宿主配置目录：
   工程文件是要被共享和提交的，把一台机器的状态塞进去，在下一台机器上就是错的。这些成员若出现，
   按未知成员报告，而不是被当作有意义的东西读进来。
5. **保存 = 临时文件 + `rename`**（roadmap §4.2 的准备/写临时产物/提交/确认），且写回原文件前比对
   读入时的字节：别人在你读之后改了文件，本构建**拒绝写**（`ChangedOnDisk`），而不是用旧副本覆盖。
6. **时间以 unix 毫秒存放。** 格式的精度就是 1 毫秒：更细的瞬间按截断写出（凭据早/晚一个微秒到期不是
   任何人能据以行动的信息）；超出 i64 的瞬间**不写**该成员，而不是饱和成某个"不是它的时间"。
7. **格式版本三种去向**：等于本构建写的版本 → 逐成员解释；**高于**本构建 → 只读打开、只尽力读身份、
   没有任何写回路径；**低于**本构建 → 带原因拒绝（迁移是 T02.07 的职责，本轮不猜）。
8. **生成物必须指到已声明的页面文档**（`generated[].from`）：同一目标的两种写法（`./pages/main.json`
   与 `pages/main.json`）解析到同一处就算同一个，这样"改了路径造成假报警"不会发生。
9. **一个转义器。** `probe::report::json_string` 现在委托给 `project::json::escape_string`（原则 #35）：
   两个写出器对"什么需要反斜杠"只能有一种看法，否则总有一个产物是错的。
10. **`VERSION_1_MEMBERS` 是值不是注释**，并由用例对照写出器实际产出的成员名与顺序：新增成员必须
    在这里、在格式文档里、在迁移里同时出现，否则用例先失败。

### 31.3 验收词怎么变成"可查的东西"：三条不变量

* **INV-NO-HALF-PROJECT**（结构 + 测试）：暂存目录在目标同级、提交是一次 `rename`；失败或取消
  移除暂存目录。结构上"原目录被填"只可能发生在那一次改名里，因此不存在"写了一半的工程"。
* **INV-NO-OVERWRITE**（测试）：非空目录、文件、缺失父目录都在写入之前被拒绝；空目录可以被填
  （`rename` 允许替换空目录），"向导打开期间别人写进目标目录"这一冲突由提交失败覆盖，别人的文件
  原样留在那里。
* **INV-CREATED-IS-READABLE**（测试）：`verify_staged` 用设计器自己的读者读回暂存目录里的
  `project.json` 与每个页面文档；写出器与读码器不一致会让创建失败，而不是交付一个打不开的工程。

### 31.4 设计决定

1. **创建 = 计划 / 暂存 / 一次改名**，不是"在目标目录里逐个写文件"。这让"取消不能留下半个工程"
   成为结构性质：目标目录在最后一次改名之前从未被写过一笔。
2. **页面文档不写 parent，只写 children。** 同一棵树只存一份；父子链接由 store 的 apply 建立
   （`INV-SINGLE-WRITER`：`Node` 的写入方法是 `pub(crate)`，只允许 store 调用）。文件里出现的
   `parent` 成员按未知成员保留并报告，而**不是**被信任成树——这条也有用例钉住。
3. **文件 → 模型这座桥本轮没有写。** `DocumentStore` 只 adopt 根节点一个身份，其它节点的身份必须
   由 id 分配器发放（"凭空发明的 id"会被拒绝），因此从文件建模型需要一个 store 侧的"
   adopt 文件身份"的接缝。那个接缝属于**打开工程（T02.03）**——那里同时有信任与作用域的决定；
   提前写一个没人能跑的 `to_change_set` 就是"没有证据的声明"（原则 #25）。本轮把这条写成模块文档
   与本记录，而不是留下半成品。
4. **模板只描述工程文档，不发明代码。** 应用模板相对基础页面模板只多一件事：把页面生成到
   `src/generated/main.rs` 的映射（F2）。组件、主题、多窗口、清单属于各自的任务；模板若自己发明，
   交付的就是一个没人能构建的工程。
5. **身份可注入。** `ProjectIds` 是参数而不是在内部读时钟：这样"同一个请求两次"可重复、可断言；
   随构建发布的 `SystemProjectIds` 用时间+进程+计数器，且刻意不透明（除工程文档外没人读它）。
6. **暂存目录是目标同级的隐藏目录**（`.<name>.rustage-staging-<pid>-<n>`）：同一文件系统才能用
   rename 提交，隐藏则不会被误认为工程的一部分；已存在同名暂存目录时**拒绝**而不是复用。
7. **`ProjectDraft` 是"还不存在的工程"的唯一描述方式**（不是第二套写出器）：它产出的就是
   `ProjectDocument`，由格式自己的写出器渲染，完整性检查也用读码器同一条（`check_unique`/
   `check_generated_sources`），因此创建的工程与读回来的工程是同一种东西。
8. **样式表只有一条规则**（`.page { display: flex; flex-direction: column; }`）：模板不该决定别人
   应用长什么样，主题属于 F13/F14。

### 31.5 本轮发现并修掉的缺陷（都是本轮用例抓到的）

1. **页面文档的 `page` 对象里，未识别成员在写回时被丢掉**。`to_json` 只写了 `id`/`name`/`root`，
   没有把 `page_preserved` 放回去——这正是 `INV-NO-FIELD-LOSS` 禁止的事，被
   `a_member_this_build_does_not_know_is_kept_and_reported` 抓住并修好。
2. **错误路径里出现双点**：`nodes[0]..children[0]`。原因是构造路径时用 `member_path("")`（空名字
   仍然会加一个 `.`）；改用 `Reader::path()`。用例
   `a_member_of_the_wrong_shape_is_refused_with_the_path_that_holds_it` 钉住正确写法。

### 33.3 验收词怎么变成"可查的东西"：三条不变量

### 33.4 设计决定

1. **"打开"与"信任"是两个动作。** 打开只读入；信任是人的一次回答，记录在授权记录里，按会话有效
   （T01.05 的语义：信任按次而非按目录），因此重新打开一个工程会重新提问。这样"可只读打开"不需要
   任何特殊路径——它就是默认。
2. **提问在回答前被重新读取**（TOCTOU 防护）。目录可以在提问与回答之间获得 `build.rs`；把答案用
   在一个已经消失的状态上，等于替人就另一个状态做了决定。
3. **工具链诊断走门禁。** `cargo --version`/`rustc --version` 是本构建启动的程序，所以它需要
   `EffectClass::Command` 的许可；未信任工程的正确结果是"未检查（会运行程序）"，而不是"跳过检查
   直接给版本"。报告里记录**执行过的每条命令**，所以它是证据而不是声明。
4. **最近项记目录而不是文件。** 目录是人认识、会搬动的东西，也是"不见了"这一状态的单位；文档在
   目录里的名字由格式固定（`project.json`）。
5. **修整按身份，不按路径。** 把一个条目指到"另一个也有工程的地方"是最容易发生的静默错误；因此
   新位置必须带同一个身份，否则报出两个身份并拒绝。路径仍在的条目**不修**（那会变成"悄悄改变条目
   指向"的入口）。
6. **最近列表是机器本地状态**，因此不进工程文档：它在宿主配置目录里，写入方式与工程文档相同
   （临时文件 + 改名）。读不出来时报错而不是清空——静默忘记一堆工程是用户看不见的损失。
7. **只读打开是成功而不是失败**：`--open-project` 对只读状态退出 0（验收词要的是"可以只读打开"），
   只有打不开时才退出 4。
8. **两处去重**：版本读取（`format_version`）与"临时文件 + 改名"（`json::write_atomically`）现在各自
   只有一份实现，工程文档、页面文档与最近列表共用（原则 #35）。

### 33.5 本轮发现并修掉的缺陷（都是本轮用例抓到的）

1. **修整时把目录当成工程文件读**（`ProjectSession::open(to)` 传的是目录），OS 报 "Is a directory"。
   改成读 `to/project.json`。用例 `a_missing_entry_is_repaired_only_onto_the_same_project` 抓住。
2. **工具链版本取错了词**：`cargo 1.98.1 (hash 2026-08-05)` 取最后一个词会报出提交日期
   `2026-08-05)`。改成取程序名之后的那个词，并把用例收紧成"必须像版本号"（第一版用例只检查非空，
   因此放过了它——这正是"用例太松等于没有用例"的一次实例）。

迁移的完整往返由用例给出（读 v1 → 判定 `Migrated` → `save()` 拒绝并保持原文件不变 →
`save_migrating()` 写出 `.v1.bak` 与 v2 文件 → 再读为 `Current`）。

### 35.3 本轮发现并修掉的设计错误（用例抓到）

**页面文档曾与工程文档共用 `FormatVersion::CURRENT`。** 把工程格式升到 v2 之后，所有页面文档（仍是 v1）
会被页面读码器判为"更旧"而拒绝——一次工程格式变更静默作废了每一个页面。修法是让每种文档拥有自己的
版本序列（`PAGE_FORMAT`、`RECENT_FORMAT`），共享的只有 `FormatVersion` 这个类型。这个错误只有在真的
做一次版本变更时才会暴露，也正是决策 Q6 要求"每次格式变更都附带迁移步骤与可重复测试"的价值。

### 35.4 设计决定

1. **`startup` 是可选成员，但写明为 `null`。** "尚未选择入口"是真实状态（有页面、还没决定从哪开始），
   而一个文档只能有一种写法：v2 总是写出该成员，因此 `render()` 的字节比较仍然是可用的检查。
2. **迁移步骤是值，不是注释。** `MIGRATION_STEPS` 有 from/to/说明，`migration_path` 回答"这个版本能不能到达
   当前版本"；到不了就明确拒绝（T02.07 会在此基础上做迁移候选、diff 与校验）。
3. **v1→v2 这一步不需要改写字节**（成员是新增且可选），但它仍是一步：有版本号、有说明、有测试——
   这样"本构建能读哪些版本"是可回答的，而不是靠读代码猜。
4. **写回旧文档必须先留底。** `save()` 对旧版本直接拒绝并说明原因，`save_migrating()` 才写，且先写
   `.v1.bak`（原字节）。决策 Q6 要的是"迁移前不原地覆盖原文件"，因此这个约束放在**保存路径**上，
   调用方无法绕过。
5. **声明与成员必须一致。** v1 文档带 `startup` 会被拒绝：迁移表的意义是"旧文档没有这个成员"，
   而不是"我们宽容地把它当成有"。

2. 没有**导入已有设计工程**的路径（T02.07）。

## 36. T02.05 文件添加/排除/移动/重命名/删除预览与引用修正

**最低验收：路径、设计引用和文件操作失败可恢复。** 本轮把这句话拆成三件可复跑的事：
(1) 路径——目的地可以是一个**还不存在**的目录，但越界仍是拒绝；(2) 设计引用——移动时改写、删除时阻断，

### 36.3 本轮发现并修掉的设计错误（用例与真实输出抓到）

1. **删除和排除被写成了同一件事。** 第一版 `Delete` 只去掉声明，计划行甚至写着"文件本身被留在原处"，
   与 `Exclude` 完全重合。路线图两处明说这不是一件事（§238"排除不等于删除"、§294"删除文件与排除工程
   分开，引用受影响先提示"），因此改为：删除真的把文件移走（先移入 `.rustage-deleted/<它自己的路径>`，
   文档写成功后再移除），并补一条"写失败要放回"的用例。
2. **移动谎报了资源表。** `Move` 把被改写的旧路径列进 `undeclared`，于是报告里出现
   "resources/logo.svg stops being a project resource" —— 而文档里那条声明是被**改写**成了新路径，资源
   表没有变小。改为不再列它，并加一条用例把"列出谁在引用"与"移动时改写了谁"钉成同一张清单
   （`what_names_a_file_is_the_same_list_that_a_move_rewrites`）。
3. **删除会静默留下悬空成员。** `pages[].stylesheet`、`generated[].output`、`generated[].from` 若指向被删
   的文件，第一版什么都不说就删了。现在与"入口被引用"同一条规矩：阻断并逐条列出，要求先改指向。
4. **回滚留下空目录。** 删除失败把文件放回后，`.rustage-deleted/…` 的空目录留在工程里（用例抓到）。
   `undo` 只在回收位下的移动后做空目录修剪：普通移动的回滚不清目录，那可能删掉与本次操作无关的目录。
5. **`ProjectRoot::resolve` 的规则放错了地方。** 它与"目的地可能还不存在"直接冲突，前一轮的用例先撞上
   （移动到一个新目录被报成"父目录不存在"）。新增 `resolve_for_creation` 而不是放宽 `resolve`：读文档时
   一个缺失的父目录是"还没有"，写文件时它是"可以被创建"，两条规则各有各的读者。
6. **一处编译期笔误**：`Some(path.as_str()) == destination`（`path` 已是 `&str`）触发
   `error[E0658]: use of unstable library feature str_as_str`，改为 `Some(path) == destination`。

### 36.4 设计决定

1. **预览是纯读，不是"没执行的执行"。** `--apply` 与不加 `--apply` 走的不是同一条路：预览只 `plan` + `render`，
   连信任问题都不回答（它不产生副作用，不需要授权）；应用才问问题、取 `write-file` 许可。这样"预览"
   不会因为将来某处多加一行而变成一次未经授权的写入。
2. **文件先动、文档后写，失败只可能落在写文档上。** 于是恢复路径只有一条（把已做的移动逆序放回），
   不必为"文件移动失败"和"文档写入失败"各写一套恢复。回收位在工程内，两个方向都是一次 `rename`。
3. **"没做"和"做了又回滚"在退出码上相同，在文字上不同。** 两者都退 4（操作没有发生），但后者会说
   "已放回，工程和之前一样"，前者会说"什么都没改"。失败绝不退 0——即使一切都被放回。
4. **阻断项与计划同一次读出。** `blockers` 由同一次读取算出，因此"能不能做"先于"做了什么"；一个带阻断项
   的计划 `is_executable()` 为假，`execute` 直接拒绝，不存在"先做一半再看"的路径。
5. **`Exclude` 与 `Delete` 共用一份"谁在引用"的清单，但用不同的词。** 同一份 `undeclared` 在两个操作里
   输出不同的人话（"停在原处" / "不再属于本工程"）：词跟着操作走，而不是跟着字段走。

### 36.5 未覆盖项

1. **没有界面**：右键菜单、拖动移动、就地改名（`TreeView` 的相关缺口见 §36.6 与上游反馈第九节）属于
   T04/T09；本轮是模型 + 命令行。
2. **不改写设计文件**：页面文档里指向某资源的属性（`asset`）在移动/删除时是**阻断**，不是改写。改写设计
   需要页面编辑器（T03.05），本轮不发明第二套页面写入口。
3. **成功之后不能撤销**：删除成功后回收副本就被移除，"撤销删除"属于 T09/T26（本轮只保证失败可恢复）。
4. **回收位不做随时间清理**：只有"写失败回滚"与"写成功后移除"两条路径会动到它；进程被杀后留下的回收
   目录不会被自动扫描或清理（`--project-check` 只读文档，不扫目录）。
5. **删除空目录本身**：删掉文件的父目录（例如 `resources/icons/`）会留在工程里是空目录；"删目录"是另一个
   操作，未实现。
6. **一次只做一个操作**，没有批量与"应用到多项"；多选与批处理属于 T08/T09。
7. **没有"复制/另存"**：路线图 §294 的文件操作里还有"复制路径 / 显示 / 比较"，不在 T02.05。
8. **回收位名 `.rustage-deleted` 未进入格式文档**：它是实现细节（不影响读回），但也没有被任何门禁保护；
   将来若要做"清理未引用资源"（T02.08/T21）需要把它纳入忽略规则。

### 37.4 设计决定

1. **没有工程级 profile 成员。** 格式 v2 没有它，加一个就是格式变更（`F1`/`Q6`：改格式要带版本与迁移），
   而本任务不需要。因此"继承"的确切含义是：**沉默的层不表态**，由下层决定，报告写明值来自哪一层——
   而不是发明一个文档里没有的层次。
2. **列表是替换而不是累加。** Cargo 自己的 feature 选择是累加的，但这里是设计器拥有的"目标配置"；
   选择替换 + 逐条报告被替换项，好处是"被去掉的特性"不可能看起来像"从来没要过"。
3. **身份是读取的参数，不是条目里的字段。** `active_for(id)`/`overrides_for(id, target)` 都要求身份，
   因此"拿别处的配置"没有可用签名；`for_project` 是给已经持有配置的调用方补上的同一道门。
4. **过期选择拒绝而不是回退。** 上次选的目标没了就报错并列出可选目标：静默换一个目标正是"过期结果
   冒充当前结果"。
5. **本机状态不需要权限，但需要身份。** 它是宿主自己的状态（与 recent 同一类），不是工程的内容，
   因此不取 `write-file` 许可；但它记的每一条都绑定工程身份，这才是"不串用"的落点。
6. **机密视图由存储接口回答健康，而不是由本模块读材料。** `CredentialRef::health(store, now)` 只返回
   五种状态；`lookup` 留给真正要发请求的网络层。于是"渲染出机密"在类型上不可表达。

### 38.3 本轮发现并修掉的问题

1. **`ProjectFile::version()` 回答的不是文档声明的版本。** 对一个 v1 文档它返回 **v2**（本构建能用的

2. **较新版本根本走不到 `ProjectError::NewerFormat`。** 读取新版本是**成功**的（`ProjectContent::Foreign`，

3. **留底文件名不是"原扩展名 + .bak"。** `with_extension("v1.bak")` 是**替换**扩展名，写成

### 38.4 设计决定

1. **候选与提交分开，且候选只读。** `--import` 不加 `--apply` 连信任问题都不问——它不产生副作用，
   不需要授权；`--apply` 才问问题、取 `write-file` 许可。用例直接断言"计划之后文件原文未变、留底不存在"。
2. **留底绝不覆盖。** 第二次迁移撞上已有留底就拒绝：留底是"文件当时是什么"的记录，覆盖它等于销毁证据。
3. **留底写完先读回逐字节比对，再迁移。** 一个不持有原字节的"留底"不是留底；把这件事在迁移之前查出来，
   才是"可恢复"与"文件丢了"的区别。
4. **失败按写之前/写之后分两类。** 写之前失败：什么都没写，工程原样（`project_left_as_it_was` 为真）。
   写之后失败：用留底把原字节放回；只有放回也失败才报 `left_behind`（并指出文件在哪）。
5. **diff 是成员级的，且不列未变化项。** 行级 diff 会把 JSON 的排版噪声当成变化；成员级 + 容器只报形状，
   报告才是在说"这次导入会改什么"。这条与原则 #22 一致：报告要么有用，要么是在掩盖。
6. **"能否读回"与"是否就是读到的那份"是两个问题**，`Backup` 分别回答（`is_readable` / `matches`），
   谁都不替谁回答。
7. **`--check-backup` 只看文档所在的那一层目录**（不扫树），与本项目"不扫出工程根"的既有边界一致。
