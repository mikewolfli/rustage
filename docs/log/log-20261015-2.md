## 1. 问题拆解：要证明的是哪一句话

"Windows 格"在本项目里其实有两种不同的主张，混在一起讨论就会得到错误答案：

| 主张 | 需要什么证据 | Wine 能提供吗 |
|---|---|---|
| 设计器**能在 Windows 上编译** | 对应 triple 的真实构建（原则 #47：目标专属依赖要在 Cargo target 配置里声明并实跑目标构建） | **不需要 Wine**：交叉编译即可，且这是真证据 |
| 设计器**在 Windows 上运行** | 在**那个 OS** 上运行（[support-matrix](../plan/support-matrix.md) 的 `certified` 定义） | **不能**：Wine 不是 Windows，它的回答是关于 Wine 的实现 |
| 探针**在那台机器上的结论** | `--probe-host` 在真机上的输出（[host-probe](../plan/host-probe.md) 规则 2：`probed` 只允许出现在本记录产生的那台机器上） | **不能**：Wine 下的输出记录的是 Wine 的环境 |

因此本轮不去争"Wine 等于 Windows"，而是分别取两半的证据，并把 Wine 的边界写清楚。

## 2. 实测一：Windows 交叉构建（真正的目标构建，不需要 Windows 机器）

```text
$ rustup target add x86_64-pc-windows-gnu
$ sudo apt-get install -y --no-install-recommends gcc-mingw-w64-x86-64   # GCC 13-win32
$ cargo build --target x86_64-pc-windows-gnu
warning: unused variable: `grace`
   --> src/host/subprocess.rs:584:33
    |     pub fn terminate(&mut self, grace: Duration) -> Termination {
    |                                 ^^^^^ help: if this is intentional, prefix it with an underscore: `_grace`
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 1m 01s
$ ls -l target/x86_64-pc-windows-gnu/debug/rustage.exe
-rwxrwxr-x 2 mikeli mikeli 549108063 … rustage.exe
$ cargo clippy --target x86_64-pc-windows-gnu --all-targets
warning: unused import: `DEFAULT_GRACE`  (以及 8 个 executor 导入、2 个我本轮新增的导入)
     --> src/host/subprocess.rs:971, src/project/session.rs:789
```

**这次构建本身就是证据**：`rustage` 第一次为 Windows 编译就通过（1 分 01 秒），依赖树里含 `wgpu`
与 `boa`，说明"没有 Windows 机器所以 Windows 格只能 `unverified`"这句话在**构建**这一半上不成立
（**运行**那一半仍然成立，见第三节）。

**它同时抓到三处缺陷**（都属于"只在 Windows 上才看得见"，因此从来没有被看见）：

1. `OwnedProcess::terminate(grace)` 的 `grace` 在非 unix 分支里**没有被使用**（分支立刻 `kill_directly`），
   于是 Windows 构建报 `unused variable`。修法是让那个分支**如实说出宽限期没有生效**，而不是把参数
   悄悄丢掉：

   ```rust
   reason: format!(
       "this host knows no way to signal a process group on {}; the direct process was killed at \
        once and its descendants were not — the {grace:?} grace period applies only where a group \
        can be signalled",
       std::env::consts::OS,
   ),
   ```

   这不只是消警告：调用方在 Windows 上读到的报告现在会说"宽限期在这里没有用处"，而不是让人以为
   它生效了（原则 #22/#45）。
2. `host::subprocess` 的测试模块里，`DEFAULT_GRACE` 与 8 个 executor 导入只在 unix 的用例里被使用
   → 在 Windows 上未使用。修法是把这些导入**跟着用例一起 gate 到 `#[cfg(unix)]`**。
3. `project::session` 的测试模块里，我上一轮新增的 `ToolUnavailable`/`read_tool_version` 只在
   `#[cfg(unix)]` 的用例里使用 → 同样 gate。

**修后（两个目标都零警告）**：

```text
$ cargo build --target x86_64-pc-windows-gnu   # 0 warning
$ cargo clippy --target x86_64-pc-windows-gnu --all-targets   # 0 warning（测试代码也为 Windows 编译过）
$ cargo build && cargo clippy --all-targets    # 本机 0 warning
$ cargo test                                   # 509 passed; 0 failed
```

顺带一个正面结论：**测试代码本身可以为 Windows 类型检查通过**（`clippy --all-targets --target
x86_64-pc-windows-gnu` 无错），这是"测试里写死了 unix 假设"这一类问题的第一道闸门。

## 4. Wine 暴露出的第四处缺陷：探针找 `cmd` 却存在 `cmd.exe`（已修）

**现象**：第一次 Wine 运行报 `url-handler -> gap`，理由是 `cmd is absent on PATH`。

**排查**：`std::env::split_paths` 是正确的（按平台分隔符切分），`is_on_path` 也遍历了 PATH。实测
Wine 的 PATH 与文件系统：

```text
$ wine64 cmd /c "echo PATH=%PATH%"
PATH=C:\windows\system32;C:\windows;C:\windows\system32\wbem;…
$ ls ~/.wine-rustage/drive_c/windows/system32/cmd.exe   → 存在
$ ls ~/.wine-rustage/drive_c/windows/system32/cmd       → 不存在
```

**根因**：Windows 上程序是带扩展名存放的，shell 通过 `PATHEXT` 找到 `cmd.exe`；而 `is_on_path` 只找
了裸名字 `cmd`。于是在**这条检查唯一关心的平台**上，它把"装了"报成"没装"——一个假缺口。

**修法**：把"一个程序在 PATH 目录里可能叫什么"抽成一个可测的纯函数 `candidate_names(program,
windows, pathext)`：非 Windows 只返回裸名字；Windows 依次追加 `PATHEXT` 的每个扩展（未设置时用平台
默认 `.COM;.EXE;.BAT;.CMD`，顺序保持平台自己的顺序）。`cfg!(windows)` 与 `env::var` 只出现在调用点，
因此**这个规则在 Linux 上就能被测试**——否则它只会在没有测试机的平台上生效。

**证据（同一条命令，修前修后）**：

```text
修前： url-handler         gap          cmd is absent on PATH; …
修后： url-handler         ready        cmd is present on PATH; refused before launch: -open-soon, javascript:, no scheme
       summary: 8 ready, 5 gap, 2 not verified   →   9 ready, 4 gap, 2 not verified
```

新增用例 `the_windows_lookup_uses_pathext_and_the_unix_one_does_not` 覆盖四种情况：给定 `PATHEXT`、
未给（用默认）、`PATHEXT` 里的空项被跳过、非 Windows 不追加任何扩展。

## 5. 仍然为缺口的部分：探针自己的检查依赖 unix shell（本轮记录，不修）

Wine 下剩下的 4 个 `gap` 与 1 个 `not-verified` 里，有 **4 项同因**：`project-trust`、`notifications`、
`project-scope`（gap）与 `process-trees`（not-verified）都要**启动一个受控程序**来证明"信任/授权/清理
真的生效"，而那些检查用的受控程序是 `sh`（`ProcessSpec::new("…", "sh").args(["-c", script])`），脚本
本身也是 POSIX 语法（`sleep 30 & echo $!; wait`）。Windows 与 Wine 上都没有 `sh`，于是：

* `process-trees` 报 `program not found` 并记 `not-verified`（第五次记录已经预告过这一条：非 unix 上会
  像 `process-trees` 那样记 `not-verified`，缺的是证据不是能力）；
* 另外三项记 `gap`，理由是"命令没能跑起来"——**这也是假缺口**：`gap` 在报告的词汇里意思是"本机缺此
  能力"，而真正缺的是检查自己的夹具。

**为什么本轮不修**：这不是把 `sh` 换成 `cmd` 就完事——受控脚本要按平台重写（`cmd` 没有 `sleep &`、
`wait`、`$!` 的对应物），而这背后是一个更大的选择：受控程序可以改用**宿主自己的可执行文件**
（本轮的实测证明 `rustage.exe` 在 Windows 上能作为子进程启动），于是检查不再依赖任何 shell。那是一次
设计变更，需要单独一轮并同步 `docs/plan/host-probe.*` 的措辞（`gap` 与 `not-verified` 的判据）。

**本轮的处理**：把这一条写进 [host-probe.md](../plan/host-probe.md) 的 Windows 行（"缺的不只是机器，
本探针的 4 项检查还需要一个 shell"）与本文，并作为下一步的一项。

## 8. 未覆盖项与阻塞项

1. **没有 Windows 机器**：`certified` 与 host-probe 的 windows 列仍然没有证据；Wine 不改变这一点。
2. **`x86_64-pc-windows-msvc` 没有构建过**：本轮只有 `-gnu`（mingw）。msvc 需要 MSVC 的 CRT/SDK，
   本机没有（`cargo-xwin` 是一条可选路径，未尝试）。
3. **Wine 的版本与配置固定在一处**：Wine 9.0、`WINEARCH=win64`、前缀 `~/.wine-rustage`；换版本可能
   改变本轮的每一项观察，因此这些结果只能挂在"Wine 9.0"上。
4. **没有 GUI 观察**：窗口"被创建"是从子进程日志与退出码读到的，没有人在屏幕前确认 Wine 的窗口真的
   出现（本机 X11 会话是 linux 的桌面，不是 Windows 的）。
5. **4 项检查依赖 shell**（第 5 节）：Windows 上的 `gap`/`not-verified` 有一部分是夹具的限制。
6. **APT 与 Rust 目标的安装是本轮的副作用**：`gcc-mingw-w64-x86-64`、`wine64`、
   `rustup target add x86_64-pc-windows-gnu`，以及约 1.1 GB 的 Wine 前缀 `~/.wine-rustage` 留在本机；
   撤销方式是 `apt-get remove`、`rustup target remove` 与删除该前缀。

## 9. 决策记录

1. **Wine 不作为 Windows 实机的替代，也不写进任何"认证"格。** 依据：principle #24（模拟不能替代目标
   构建与运行）、[support-matrix](../plan/support-matrix.md) 的 `certified` 定义（在所指 OS/triple/
   设备上），以及本轮实测——Wine 的回答是关于 Wine 的（`clipboard -> ready` 走的是 X11）。
2. **交叉构建算目标构建证据，因此 windows 宿主行升到 `build-verified`。** 依据：原则 #47（目标专属
   依赖要实跑目标构建）与矩阵对 `build-verified` 的定义（有记录的构建通过；尚未运行）。
3. **Wine 的实测结果写进本记录，不写进 host-probe 的表。** 依据：host-probe 规则 2（`probed` 只允许
   出现在本记录产生的那台机器上，且恰好一台）。把 Wine 的 8/9 格抄进 Windows 列会让那一列看起来像
   真机结论。
4. **缺陷要修在"能覆盖到该平台的规则"上，而不是热点补丁。** PATHEXT 那条把平台规则抽成纯函数并配
   Linux 上可跑的用例，因为 `cfg!(windows)` 分支永远不可能在本项目的机器上被观察到。
5. **本轮不重写探针的受控程序（第 5 节）。** 依据：那是一次设计变更（受控程序从 `sh` 改为宿主自己的
   可执行文件），会影响 `gap`/`not-verified` 的判据与 host-probe 的措辞，需要单独一轮。

2. 若坚持 msvc triple：尝试 `cargo-xwin`（无需系统包）或准备一台 Windows 机器；前者能给
