## 4. 关闭的缺口一：`--probe-apis` 编辑族的 `line_state`

**旧行为**：`multiline_highlight_state` 探针断言旧限制——第 1 行（在 `/* … */` 内）读回
`LineState::Clean` 且没有块注释 token，据此记 `gap`。这是 `--probe-apis` 唯一的缺口。

**新修订的接缝**（`src/widget/special_widgets/code_editor/editor.rs`）：
`line_state_is_known(line) -> bool`（谓词：走查是否证明了这一行）与
`resolve_line_state(&mut self, line) -> LineState`（解析器：推进链并返回真实状态）。**没有新增
`LineState` 变体**——反馈旧文写的 `LineState::Unknown` 与实际实现不符，本轮在
[`feedback-20261015.md`](../rw-feedback/feedback-20261015.md) 里改正了。

**改法**：探针改为断言那条契约本身——

```rust
let unproven = editor.line_state(1);          // 未走查的行仍是 Default（Clean）
let known_before = editor.line_state_is_known(1);   // 但谓词说它"未知"
// 断言 unproven == Clean && !known_before；
let resolved = editor.resolve_line_state(1);  // 解析器给出真实答案
// 断言 resolved == LineState::BlockComment && line_state_is_known(1)
```

测试模块的 `KNOWN_GAP` 常量随之删除，`probes_are_verified_except_the_recorded_gap` 改为
`every_editing_probe_is_verified`（缺口的**消失**也要被钉住，否则它可能悄悄回来）。

**证据**：

```text
$ ./target/debug/rustage --probe-apis target/audit-20261015-3/verify/apis ; echo $?
editing    verified code_editor::CodeEditor::line_state/line_state_is_known/resolve_line_state
per family: layout 3/3, generation 5/5, event 3/3, unbind 3/3, editing 8/8
summary: 22 verified, 0 gap
0
```

## 5. 关闭的缺口二：主机探针的 `native-file-dialog` 改问能力位

**旧行为**：`check_native_dialog` 调 `rust_widgets::create_file_dialog(0,0,0,640,420)`，返回 0 即记
`gap`，理由写成"固定修订在这三个桌面后端上不创建文件对话框控件，因此拿不到系统自己的选择器"。

**为什么必须改**：新修订提供了系统选择器的接缝——`choose_path`/`open_path`/`save_path`/
`select_directory`（`src/lib.rs`）与 `PlatformCapabilities::file_dialog`（在**调用前**就能问
"这个后端有没有原生选择器"，`PathPickerError::Unsupported` 与它成对）。于是旧理由**不再成立**：
留着它就是原则 #22/#27 禁止的"过期陈述冒充当前事实"。

**改法**：检查改为读能力位，且**从不真的弹出选择器**（弹出是模态的、需要人在屏幕前，与
`url-handover` 是同一条边界）：

```rust
let advertised = rust_widgets::platform::capabilities().file_dialog;
// false → Gap：这个后端没有原生选择器（自绘框是回退，由 chooser-frame 单独检查）
// true  → NotVerified：有选择器，但呈现它是模态的，探针不替用户打开它
```

**证据（两种构建，同一条检查的两种诚实答案）**：

```text
$ ./target/debug/rustage --probe-host …                                    # 默认（状态后端）
native-file-dialog  gap          rust_widgets::platform::capabilities().file_dialog -> false
summary: 12 ready, 1 gap, 2 not verified

$ ./target/debug/rustage --features linux-native -- --probe-host …          # 原生 GTK
native-file-dialog  not-verified rust_widgets::platform::capabilities().file_dialog -> true
summary: 13 ready, 0 gap, 2 not verified
```

主机侧记录（[`host-probe.md`/`.json`](../plan/host-probe.md)）与 `host::dialog`/`readiness` 模块文档
一并对齐：`create_file_dialog` 仍然返回 0（库现在自绘每一种），但**宿主可以拿到系统选择器**这句话
现在成立，因此不再写"拿不到"。

## 6. 迁移：有界会话改用自己的 `quit()`

**旧行为**：`--launch --exit-after-ms` 由一个 watcher 线程到点 `std::process::exit`，日志写着
"ending the process because the pinned revision's quit() is main-thread-only"。那个理由现在**为假**。

**新修订的接缝**（`src/platform/stop.rs`）：`rust_widgets::quit() -> bool` 记录一个跨线程的停止请求，
**循环自己的帧回调**在循环线程上执行真正的 toolkit 停止——因此请求可以从任何线程发出，macOS 也适用
（记录是一次原子写；`-[NSApplication stop:]` 仍在主线程上被调用）。

**改法**（`src/host/platform.rs`，`run_loop` 的有界分支）：

```rust
let _watcher = thread::spawn(move || {
    thread::sleep(exit_after);
    let reader = rust_widgets::quit();      // 记录停止请求；返回"有没有循环在读它"
    emit(Level::Info, "host::platform", &format!(
        "session deadline {exit_after:?} reached; asked the loop to stop ({})",
        if reader { "a loop is running and stops at its next frame" }
        else { "no loop had ticked yet; the request is recorded for the next loop" }));
    flush();
});
rust_widgets::run();
Ok(LoopEnd::HostEnded)
```

同步修正：`LoopEnd::HostEnded` 的文档（"因为无法请求循环停止"→"通过请求循环停止"）、
`app/run.rs` 的打印注释、`CONTRIBUTING.md` 的 `--launch` 说明、`platform.rs` 的模块文档。
`ExitCode` 导入随之不再需要，已删。

**证据（原生会话实测）**：

```text
$ ./target/debug/rustage --launch --exit-after-ms 250 ; echo $?
launching the baseline session; it will end itself after 250 ms
INFO host::startup: backend gtk initialised, gui mode NativeInteractive (+15 ms)
INFO host::startup: window 6000285942072475648 created 1280x800 (+15 ms)
INFO host::platform: entering the event loop for a bounded session (+15 ms)
INFO host::platform: session deadline 250ms reached; asked the loop to stop (a loop is running and stops at its next frame) (+265 ms)
INFO host::startup: window 6000285942072475648 closed, event loop returned (HostEnded) (+275 ms)
desktop session started: backend gtk, gui mode NativeInteractive, window 6000285942072475648, ended HostEnded, 275 ms
0
```

默认构建上 `--launch` 仍然**拒绝**（后端 `PreviewOrStub`）：退出码 3，理由不变——这是"没开窗口"的
诚实答案，不是回归。

## 10. 决策记录

1. **把固定修订升到 `58012c05`（本地 HEAD = `origin/main`）。** 依据：决策 U1 的升级流程；第七次
   记录 §14 把 re-pin 列为下一步第一件事；那 8 个提交正是实现全部反馈条目的提交。选择 HEAD 而非
   中间提交，是因为反馈核对（第七次记录第二节）针对的就是 HEAD。
2. **先量后改。** 依据：第七次记录 §14.1 明写"先编译一次量迁移量，再决定新修订号"；实测零编译差异，
   所以 re-pin 是"补接缝"而不是"改接口"。
3. **缺口用新修订的接缝关闭，而不是改口径。** `line_state` 用 `line_state_is_known`/`resolve_line_state`；
   `native-file-dialog` 用 `capabilities().file_dialog`。依据：原则 #22/#27（不许用成功形状掩盖），
   #24（契约以实际为准）。
4. **有界会话迁到 `quit()`，不再 `process::exit`。** 依据：原则 #41/#59（平台策略属于库；不保留过期的
