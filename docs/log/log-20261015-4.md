## 2. 迁移一：`host::watch` → `ChangeKind`

**上游接缝**（`58012c05`，`src/asset/watcher.rs`）：`AssetEvent::FileChanged { path, kind, timestamp }`
的 `kind` 是库自己的 `ChangeKind { Created, Modified, Removed, Renamed }`，并由 `asset` 模块 re-export。

**改了什么**（`src/host/watch.rs`）：

1. `WatchEvent::Changed` 的载荷从 `os_kind: String`（把 `notify::EventKind` 打印成文本）换成
   `kind: ChangeKind`。整型合并逻辑不变（`BTreeMap<PathBuf, ChangeKind>`，同一路径同一轮合并为最新一次）。
2. 模块文档里"**What this adapter cannot see**：删除在上游被丢弃，所以 `WatchEvent` 没有 `Removed`
   变体可许诺"这一段**已删除**——它现在为假。换成一段诚实的剩余边界说明：适配器仍看不到"改动是谁做的"
   （依赖只报路径与种类，不报作者），归属是宿主策略（T03.05），故意不烘进适配器。

**为什么这么做**（原则）：#35"同一语义只保留一份定义"——种类枚举来自依赖，不在宿主再复制一份；
#41"平台/库机制由库封装"；#27"文档与实现一致"——记载"看不到删除"的段落必须随实现一起改。

**新增用例**（`src/host/watch.rs` 的测试模块）：

- `a_creation_carries_a_kind_from_the_dependency_vocabulary`：新建文件必须报告 `Created` 或 `Modified`
  （文件系统把紧随的写入也算作一次改动时是 `Modified`），**而不是**空白种类。
- `a_deletion_is_observable_and_classified_as_removed`：删除一个已存在的文件后，轮询必须看到该路径被
  归为 `Removed`。**这条用例在旧修订上不可能通过**——依赖当时丢弃删除事件；它是这次迁移关闭的缺口的
  可复核证据。

**主机探针证据**（`--probe-host`，`directory-watch`）从

```text
a write in the watched directory produced 1 event(s); watching a missing directory was refused
```

变为

```text
a write in the watched directory produced 1 event(s), the file classified as Modified; watching a missing directory was refused
```

`src/host/readiness.rs::check_watch` 相应改成捕获种类并写入证据。

## 3. 迁移二：`host::clipboard` → `clipboard_text() -> Option<String>`

**上游接缝**（`58012c05`，`src/lib.rs`）：`rust_widgets::clipboard_text() -> Option<String>` 回答
"有没有可粘贴的文本"；`None` 表示"没有文本或不是文本"，不会与"读到空串"混同。

**改了什么**：

1. `src/host/clipboard.rs::NativeClipboard::read`：无 rich 后端（`platform_clipboard()` 为 `None`）时，
   不再用 `get_clipboard_text()` 的空串判断，改问 `clipboard_text()`：

   ```rust
   None => match rust_widgets::clipboard_text() {
       Some(text) => ClipboardRead::Text(text),
       None => ClipboardRead::Empty,
   },
   ```

   模块文档里描述旧访问器"把空与无文本合并成空串"的段落随之改写，改为说明 `Option` 已经承载了这一区分。
2. `src/host/readiness.rs::check_clipboard`：探针存下用户剪贴板原有文本的方式，从
   `get_clipboard_text()`（空串）改为 `clipboard_text()`（`Option`）。`None` 现在诚实地表示"没有可保存
   的文本"，探针据此清掉自己的标记并如实报告"原本无文本"，而不是假装还原了一个从未看到的字符串。

**为什么这么做**：#22"失败必须显式可诊断"、#27"文档与实现一致"；rich 后端仍在时优先问 rich 后端以保留
`NotText` 的区分（`a_non_text_clipboard_is_not_reported_as_no_text` 仍通过）。

## 4. 复核 `host::open_url`：分层保留（附一条新请求）

第三次记录 §9.1 把 `host::open_url` 的"自实现处理器分派"列为待迁移，上游接缝是
`Platform::open_external`。本轮**逐个事实核对后判定：保留宿主实现**，理由如下（原则 #38：若不能消除
真实重复，应保留简单实现并记录分层原因）。

**接缝能给的**：`open_external(target) -> Result<(), OpenError>`，`OpenError` 分三种
（`Unsupported`/`InvalidTarget`/`NoHandler`），后端负责 `xdg-open`/`open`/`cmd /C start` 的映射与启动。

**接缝给不了的（两条现验证证据会丢失）**：

1. **处理器存在性**。接缝是**即发即忘**：其文档明写"返回即已交出、**不等于**已打开"，且只在真的交出目标
   时才可能报 `NoHandler`。宿主现在的 `url-handler` 探针能验证"`xdg-open` 在 `PATH` 上"（`is_on_path`）。
   若改问 `capabilities().open_external`，Linux 后端对该位是硬编码 `true`（"后端有这个方法"），
   探针就会把"有接缝"当成"处理器已安装"——正是原则 #45"不硬编码未实现的系统能力、默认值须诚实"、
   #22"不以成功形状的默认值掩盖"所禁止的形状。
2. **完成状态**。宿主现在区分"已开始 / 已失败（带退出码与 stderr）/ 仍在运行"。接缝不回传子进程句柄，
   这三者无法再区分（库有意为之：等待会阻塞在用户会话上）。虽然目前没有 GUI 消费者读这三者（T01.02
   的服务尚未接线），但把它作为"设计上更强的东西"降级不是一次等价的迁移。

**为什么不"半迁"**：把启动分派交给库、同时保留宿主自己的 `is_on_path`，需要宿主再过一遍"本平台处理器
叫什么"——那正是接缝存在的理由（其源码注释写着"没有这个方法，每个宿主都要重新推导同一条
`cfg(target_os)` 阶梯"），半迁会把它变成两个真相源（#35）。

**结论与后续**：**本轮不迁移**。已把"缺一个处理器存在性查询"作为新请求写入
[`feedback-20261015.md` 第九节](../rw-feedback/feedback-20261015.md)：建议新增无副作用的
`Platform::has_external_handler()`，或让 `PlatformCapabilities::open_external` 如实反映"处理器程序在
`PATH` 上"。该查询到位后，本模块即可无损迁移，`url-handler` 探针证据不降级。核对中还确认：宿主自己的
`subprocess.rs` 已给子进程 `process_group(0)`，故接缝的"处理器独占进程组"这一额外好处对本宿主并不构成
迁移理由。

## 5. 复核 `host::platform` 依赖面计数与 `host::dialog` 原生选择器：保留

- **`host::platform` 的依赖面计数**（第三次记录 §9.1-4）：模块文档里"让依赖修订的表面可计数"只是说明
  "换修订时该重看哪些文件"，不是一个能力声明。换成能力查询收益小、触面大，现有注释已把它系于决策 U1
  的升级流程。**保留**。
- **`host::dialog` 的原生选择器采用**：这条不在第三次记录 §9.1 内，但同属 `feedback-20261015.md` §7
  第 2 步的五条之一，故一并复核。`choose_path` 是**阻塞模态**调用，而宿主现有 `FileChooser` 是
  `PendingChoice` 异步接口；采用它要改该接口，且原生/自绘的分工取决于 F26（设计器自己的文件列表）。
  模块文档已把这点记为后续工作。**保留待 F26**。

## 8. §9.2 阻塞项与 §9.3 未声称项：本轮未变（需真机/真人）

第三次记录 §9.2/§9.3 的边界本轮**没有变化**，因为它们的解不是代码：

- macOS 与 Windows 上的 `--probe-host` 两列仍 `blocked`（本机没有测试机）；
- "窗口被合成到屏幕并接受输入"仍需人在屏幕前；

  `platform::stop`，但仍属"待真机"）；
- Wine 下的运行结果不作为实机证据。

**一条复核时发现、但本轮未动的候选**：`58012c05` 的 `rust_widgets::schedule_on_main(after, work)`
的文档把"在期限后结束一个会话"列为它自己的用例（"a smoke test that must terminate itself, without a
watcher thread and without a process kill"）。它比第三次记录 §6 采用的方式更贴近 #41：宿主可以不再
自建一个 watcher 线程，而是把停止排进循环自己的队列（`schedule_on_main(exit_after, || { quit(); })`，
它甚至在循环尚未起动时也能在之后的帧上执行）。**本轮未改**：它属于第三次记录 §6 的已验收路径，不在
§9 范围内；且它**不改变** §9.3 记下的"靠帧回调兑现停止"这一性质（两种写法都需要一次帧回调），因此
它是一次实现清理而不是一次能力补强，留待需要再动那条路径时一并做。
