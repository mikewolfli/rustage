## 3. T13.01：数据 schema、状态字段、样例/空/错误数据与版本

**交付物**（`src/app/data_model.rs`，新增）。验收词是“**样例不替代运行数据，不存机密**”。两者都是“别让占位替身
冒充真东西”，于是模块把两者做成难以混淆：

- **数据集自报身份。** `Dataset` 是 `Kind::Runtime`、`Kind::Sample`、空集或带原因的 `Kind::Error`；
  `Kind::label()` 把差别写出来（“sample (not runtime data)”），于样例永不能被读成实时值。
- **错误被抬出来，不被样例盖住。** `active` 有运行数据时答运行数据、取数失败时答错误、才轮到场样例——
  且样例总是带标注。于是“取数失败”不会长得像“这是你的值”。
- **样例拒存机密。** `sample` 答出可疑字段名而不是把它存下，于是凭据不会被一次预览运行捕获进工程。
- **值就是工程的值词汇。** 一个字段持 `contracts::model::PropertyValue`，于是预览绑定的数据与设计器其余部分同形。

**命令符**：`--data <op>...`（`schema:<name>:<version>`、`field:<name>:<kind>[:required]`、
`sample:<field>=<value>`、`runtime:<field>=<value>`、`error:<reason>`、`check`、`active`、`state`、`show`；
kind 写作 `text`/`integer`/`number`/`bool`/`enum(a,b,c)`）。

**用例**（`app::data_model` 17 项 + CLI 解析 1 项）：样例被标注为非运行数据；运行数据优先于样例；错误被抬出
而不回退到样例；无运行数据时才用样例；两者都没有则为空；样例拒存凭据；凭据名不论分隔符都能识别（含 `author`
**不**误报）；凭据形状的值也被抓到；合法数据集无诊断；未知字段被报；缺必填被报；类型不符被报；枚举越界被报；
版本不符先于逐字段检查被报；schema 渲染字段与必填；字段种类可解析/渲染；错误种类携带原因。

### 3.1 由测试当场发现的缺陷

1. **子串匹配造成误报（测试发现）：** 首版 `is_secret_name` 用“去分隔符后 `contains`”，于是 `author` 命中
   `auth`，会误拒一个正当字段。改为**按分隔符与驼峰边界切词**后比较整段，或比较各段**拼接**后的整体
   （于是 `api_key`/`apiKey`/`authToken` 命中，`author` 不命中）。
2. **迭代器签名（编译期）：** `filter(char::is_alphanumeric)` 对 `Chars` 不成立（需要 `FnMut(&char)`），改为闭包。

## 4. T13.02：类型化单/双向绑定、转换契约、循环/缺字段诊断

**交付物**（`src/app/binding.rs`，新增）。验收词是“**不兼容/循环拒绝，双向更新不振荡**”。三者都是“一个停不下来的
绑定”，于是模块在它被加前就拒掉：

- **转换声明它能携带什么。** `Conversion` 是声明的，`Conversion::accepts` 答这个转换能不能把源送到目标——
  两个文本形载体之间的 identity、恰好一侧是文本形时的 text 桥、两个数值载体之间的 scale；其余被拒，
  于是一对类型不会被一个“其实转不了”的转换接上。
- **有损转换不得双向。** 经有损转换的 `Direction::TwoWay` 被当作**振荡**拒绝，因为写回无法复现读到的东西，
  两侧会不断互相纠正。
- **环由“闭合它的那条绑定”拒绝。** `Graph::admit` 在副本上试这条绑定，答出它会闭合的环并点名路径，
  于是环不会被构造到一半。
- **缺字段/缺槽位被点名。** 字段种类与槽位类型来自 `Environment`，`Graph::admit` 答出缺的是哪一个。

**命令符**：`--binding <op>...`（`schema:<name>:<version>`、`field:<name>:<kind>`、`slot:<node>.<property>:<type>`、
`bind:<source>=<target>:<direction>:<conversion>`、`check`、`state`、`show`；源/目标写作 `f:<field>` 或 `<node>.<property>`，
方向 `one-way`/`two-way`，转换 `identity`/`text`/`scale:<factor>`）。

**用例**（`app::binding` 19 项 + CLI 解析 1 项）：兼容单向被接受；缺数据字段被拒且点名；目标槽位未知被拒；
类型不兼容被拒且点名；声明的 text 转换桥接文本与颜色；scale 转换桥接两个数值载体；两个文本之间的 scale 被拒；
有损转换的双向被当作振荡拒绝；双向 identity 被接受；槽位间的环被拒且点名路径；双向自环被当作环拒绝；
三绑定链被接受；`check` 逐条报告不能加入的绑定；空图无环；图渲染绑定；载体从环境解析；转换解析且拒绝零因子；
`find_cycle` 对无环图答 None；**单条双向绑定不构成环**。

### 4.1 由测试当场发现的缺陷

1. **单条双向绑定被误判为环（测试发现）：** 首版把双向绑定拆成两条反向弧但不区分来源，于是 `A↔B` 自己
   就形成 `A→B→A` 的“环”。改为弧携带**绑定序号**、且一次行走不得重复用同一条绑定：一条双向绑定的两条弧
   是**同一个**逻辑关系，因此 `A↔B` 不是环，而“双向 + 另一条回边”才是。
2. **测试用例写错转换（测试发现）：** 枚举→枚举的链在首版用了 `text` 转换（`accepts` 要求恰好一侧文本形，
   两个枚举都不是），应为 `identity`。
3. **检查期告警：** 三个 `is_*` 改为 `matches!`（`clippy::match_like_matches_macro`），测试里 `== false` 改为 `!`；
   未用的 `Verdict` 导入删去。

## 5. T13.03：事件 schema/触发载荷、处理函数清单与绑定 UI

**交付物**（`src/app/events.rs`，新增）。验收词是“**名称存在与实际接线/触发分开验证**”。三个容易混为一谈的事实，
因此有三个分开的回答：

- **声明是类型化契约，不是名字。** `EventDecl` 带载荷字段，于是声明的同时也就说了触发必须携带什么（原则 17）。
- **声明不等于接线。** `Registry::has` 只答名字是否已知；`Wiring::is_wired` 答某节点是否真有处理函数；
  `status` 答两者中哪一个成立。于是“事件存在”永不被读成“已接上”。
- **接线不等于触发。** `fire` 校验载荷并报告是否接线，于是“载荷合法但无处理函数”的报告是**未接线**，而非成功。
- **载荷用同一个数据校验器。** 触发载荷经 `data_model::validate` 校验，于是事件的契约与数据集的契约用同一条规则，
  而不是两条。

**命令符**：`--events <op>...`（`event:<name>`、`field:<event>:<field>:<kind>[:required]`、
`attach:<node>:<event>:<handler>`、`status:<node>:<event>`、`fire:<node>:<event>:<field>=<value>[,...]`、
`check`、`state`、`show`）。

**用例**（`app::events` 15 项 + CLI 解析 1 项）：声明的名称即使无接线也存在；未声明的事件不可 attach；
attach 已声明事件即接线；同一节点同一事件重复 attach 是**替换**而非重复；两个节点可各接同一事件；
处理函数清单去重；`any_wired`；触发未声明事件被拒；合法载荷但无处理函数报未接线而非成功；非法载荷由同一校验器报出；
缺必填载荷字段被报；触发已接线事件报已接线（且**另一节点仍未接线**）；三种状态渲染不同；注册表渲染载荷契约；接线渲染其附件。

## 6. T13.04：事件到属性/命令/业务函数、权限与订阅释放

## 9. T13.07：文件/网络适配器接口、样例替身、取消和外部副作用权限

**交付物**（`src/app/adapters.rs`，新增）。验收词是“**未知结果不自动重试，离线设计不依赖服务**”。两者都是“不发明答案”：

- **未知结果是它自己的结果。** `Outcome::Unknown` 不是失败：请求发出去了、结果不知道，于是 `attempt` 在它上面**停住**——
  重试可能重复副作用。只有**已知失败**才是策略可以重试的。
- **样例替身是本地的。** `Adapter::Sample` 从队列作答，于是 `Availability::Offline` 仍能对着它设计；
  只有需要网络的请求在离线时被拒，而耗尽的替身如实说明“没有答案了”，不作答“没问题”。
- **副作用需要它的能力。** 请求种类点名所需的 `Capability`，裁决来自工程的 `PermissionGate`，
  于是写入或网络调用不会在没有宿主所需授权时执行（原则 12/21）。

## 13. T14.03：状态保留：输入/焦点/滚动/选中与不兼容重建提示

## 15. T14.04：多视口矩阵、尺寸/方向/主题/语言/样例配置

**交付物**（`src/app/viewport_matrix.rs`，新增）。验收词是“**各视口共享文档，运行会话状态隔离**”。两半都是结构性的，
于是类型让两半都无法做错：

- **只有一份文档，而且由矩阵持有。** `Matrix::revision` 是唯一的一处事实，于是每个视口**按构造**都是同一份文档的一个
  视图，而不是靠纪律维持。
- **会话属于它自己的视口。** `Viewport::session` 是每视口的，于是启动/停止/重启一个够不到另一个——用例启动一个，并
  断言另一个仍是停止的。
- **配置是每视口的。** 尺寸、方向、主题、语言、样例都是视口自己的，于是同一份设计可以同时在多种设置下复核。
- **名字唯一。** `Matrix::with` 拒绝同名第二个视口，于是视口总是可寻址的。

**命令符**：`--matrix <op>...`（`document:<name>`、`viewport:<name>:<w>x<h>:<orientation>`、`theme:<name>:<t>`、
`language:<name>:<lang>`、`sample:<name>:<s>`、`commit`、`start:<name>`、`stop:<name>`、`restart:<name>`、
`remove:<name>`、`check`、`state`、`show`；方向写作 `portrait`/`landscape`）。

**用例**（`app::viewport_matrix` 11 项 + CLI 解析 1 项）：每个视口共享那一份文档；提交一次改动让所有视口的修订号一起走；
启动一个不动另一个；重启只数在自己身上；停止一个另一个仍在运行；视口可以各自携带不同配置；重名被拒；未知视口名被拒；
移除一个不动其余的会话；方向可解析且可渲染；矩阵渲染文档与全部视口。

## 16. T14.05：设计选择/交互模式、运行实例/布局树、事件与数据检查器、节点/源码定位

## 18. T14.07：预览应用失败、崩溃、重载/重建/状态重置恢复

**交付物**（`src/app/preview_recovery.rs`，新增）。验收词是“**显示编辑与运行版本不一致，不伪装成功**”。两件事支撑它：

- **编辑版本与运行版本是两个事实。** `Preview` 两个都留，于是“文档是什么”与“实例是什么”可以真的比，而不是默认相等——
  在运行中改了文档，它们就可见地分开了。`edit` **故意不动**运行实例，因为那正是一次“边跑边改”的事实。
- **恢复要回答自己是否同步。** `Recovery::succeeded` 只在实例**运行且处在编辑版本**时为真；起不来的那次答 `life: down`、
  `running version: none` 与一个原因，于是失败的恢复不能被读成好结果。
- **状态的去向被点名。** `StateOutcome` 分开 kept / 刻意 reset / lost，于是一次丢掉 live 状态的重建会说出来，
  而不是报一个平淡的成功。

**命令符**：`--preview-recovery <op>...`（`edit:<version>`、`launch`、`reload`、`rebuild`、`reset`、`exit:<code>`、
`crash:<signal>`、`fault:<reason>`、`clear`、`check`、`state`、`show`）。

**用例**（`app::preview_recovery` 14 项 + CLI 解析 1 项）：启动把实例带到文档版本；运行中编辑使两个版本分开；重载把运行实例带到文档版本；
重建同样；重置丢掉状态且仍同步；带 fault 的启动保持 down 且不成功；带 fault 的重载不伪装已恢复；清除 fault 后重载能起；

## 19. T14.08：100 次绑定/重建、多视口负载与 UI 延迟验收

**交付物**（`src/app/load.rs`，新增）。验收词是“**订阅/内存不持续增长，无效输入保留**”。两者都是**检查**而不是承诺：

- **跑完回到起点才算稳。** `Load::steady` 把每个视口的最后一轮与第一轮比，于是回到起始订阅/节点数的驱动通过，
  而一路爬升的不通过；且 `growth` 点名第几轮、从几到几。
- **无效输入被留着，不是被丢掉。** 每个被拒的操作连索引与原文一起记下，报告给出计数，于是负载运行不能悄悄丢掉读不懂的东西。
- **延迟要么量到了，要么说没量。** 一轮的延迟是驱动观察到的；驱动没观察到时报告写 *not measured*，
  而不是印一个看起来很快的 0。

**命令符**：`--load <op>...`（`budget:<ms>`、`cycle:<viewport>:<subscriptions>:<nodes>[:<latency>]`、
`repeat:<viewport>:<cycles>:<subscriptions>:<nodes>[:<latency>]`、`leak:<viewport>:<cycles>:<subscriptions>:<nodes>`、
`invalid:<text>`、`check`、`verdict`、`show`）。

**用例**（`app::load` 12 项 + CLI 解析 1 项）：稳的 100 轮回到起点；泄漏使其不稳；成长连带轮次与计数被报；一个视口泄漏就足以判定不通过；
峰值是见过的最高计数；没有轮次也算稳且什么都没量；无效输入连索引与原文保留；超预算的延迟被报；没量延迟说 not measured 而非 0；
2×100 轮带延迟全部量到；报告点名每个视口；单轮在两个计数上都算稳而节点数变化不算稳。
