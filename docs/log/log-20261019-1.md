## 3. blue10 缺口 1：稳定 UI 进程 + 可替换业务进程的真实对跑

### 3.1 新增的宿主能力：`DuplexProcess`

`host::subprocess` 原有的 `OwnedProcess` 捕获 stdout/stderr、stdin 固定为 `null`，适合构建与
测试，但不能承载请求/应答。新增 `DuplexProcess`：

- 仍然由本会话创建进程组（`process_group(0)`）、写入 `RUSTAGE_SESSION` 标记、必须持有
  `ExecutionPermit`；启动校验与 `OwnedProcess` 合并为同一个 `prepare`，两条路径不会漂移。
- stdin/stdout 作为双向通道；stdout 由读取线程逐行送入有界等待的通道，`receive(limit)` 超时
  返回可诊断错误，不会无限挂起。
- stderr 单独收集并有界截断；进程崩溃时的原因可随错误一起报告。
- `finish(grace)` 先关闭输入（EOF 是礼貌请求），等待；超时才升级到组信号 `SIGTERM`，再超时
  `SIGKILL`。`Termination` 的措辞已从“礼貌信号结束了它”改为“在礼貌请求后自行结束”，因为
  EOF 与信号都是请求，不能把 EOF 说成信号。

### 3.2 新增的业务进程：`app::logic::worker`

`Worker` 与 `serve` 把既有 `core`/`ipc` 接成一个可运行的对端：

- 第一条必须是 `handshake`；请求先于握手是协议故障，不隐式开会话。
- 握手回复 `manifest`，带名字、版本、代际与能力；宿主用同一个 `Session::open` 检查代际。
- 请求形态：`event <name>`、`event <name> <type>:<value>`、`state`、`snapshot`、`restore`
  （后跟 `state=`/`field=` 行）、`quit`。
- 业务拒绝（无迁移、守卫不成立）回复 `error=...` 并继续服务；协议错误才终止进程。
- `restore` 在整段解析成功后才替换状态；malformed restore 不改动当前状态。
- **worker 自己检查代际**：旧代际帧回复 `fault=...`，宿主侧也检查。只由一侧执行的代际检查
  不是边界。
- 负载是十六进制帧内的按行文本；值里的换行/反斜杠有转义，避免记录被拆开。

### 3.3 命令面

```text
--logic-worker  name:<n> version:<v> initial:<state> transition:<s>:<e>:<n>...
--logic-process session:<id> name:<n> version:<v> generation:<n> new-generation:<n>
                first:<state> first-transition:<s>:<e>:<n>...
                second:<state> second-transition:<s>:<e>:<n>...
                first-event:<e>[:<type>:<v>] second-event:<e>[:<type>:<v>]
                second-binary:<path>
                first-schema:<field>:<type>:<since> second-schema:<field>:<type>:<since>
                from-version:<n> to-version:<n>
                expect:<state>... check show
```

`--logic-process` 的行为是确定且可观察的：启动旧代 → 握手 → 跑旧代事件 → （`preserve` 时）
取旧代快照 → 启动新代 → （`preserve` 时）把快照 `restore` 进新代并逐行比对 → 跑新代事件 →
把旧代帧发给新代并验证 `fault` → 两个进程都 `quit` 并等待真实退出 → 比对 `expect`。任一步失败
返回非零，不把部分成功写成成功。`first-set`/`second-set` 让命令行程序也能声明状态字段，
`start_logic_process` 在把程序序列化给子进程时会拒绝它无法携带的 guard/need/非 `Set` 动作，
不静默丢掉逻辑。

### 3.4 状态跨进程保留

`preserve` 让走查不只验证“新逻辑能跑”，还验证“旧状态能带过去”：

1. 旧代执行 `idle --go--> running`，`set` 写入 `count=number:3`；
2. 旧代 `snapshot` 返回 `state=running` + `field=count=number:3`；
3. 新代启动后 `restore` 同一段文本；宿主逐行比对返回值与快照完全一致；
4. 新代执行只有新程序才有的 `running --approve--> done`，结果仍是
   `done [count=number:3]`。

这证明了传输层的无损保留。schema 变化不再留在这个缺口里：`first-schema`/`second-schema`
把同一次 `snapshot` 接进 `migration::plan`/`apply`，见 §3.5。

### 3.5 schema 级迁移：丢值就阻止切换

`--logic-process` 新增 `first-schema:<field>:<type>:<since>`、`second-schema:...` 与
`from-version`/`to-version`。声明了 schema 时：

1. 旧代的 `snapshot` 文本先被解析成 `migration::Snapshot`；出现 `first-schema` 未声明的字段立即
   拒绝，并把旧代仍可回答 `state` 作为观测输出——不能把“没分类”的字段当成“没丢”。
2. `plan` 逐字段分类（kept/added/retyped/dropped），`retyped` 只允许已声明的 text 承载；
   `dropped` 区分“快照里真的有值”和“只是声明消失”。
3. 只有 `blocks_auto_switch()` 为假时 `apply` 才产出目标快照并 `restore` 进新代；为真时
   **不启动新代**，旧代继续服务，命令以 `ExitCode::Reported`（4）结束。
4. `downgrade` 由 `plan` 拒绝，同样保留旧代；不是“先切过去再回滚”。

真实走查（`tests/logic_process.rs`，全部通过）：

| 场景 | 输出要点 | 退出码 |
|---|---|---|
| v1 `count:number` → v2 `count:text` + `note:text` | `count: retyped number -> text`、`note: added`、`2 field(s) carried`、新代 `done [count=text:3, note=text:]` | 0 |
| v1 `count` 在 v2 被删除且持有 `3` | `count: dropped (...; value lost)`、`generation 1 still serving: running`、`the automatic switch is blocked`，且没有 `new generation 2:` | 4 |
| 快照含 `count`，但 `first-schema` 只声明 `mode` | `refusing to drop it silently`、`generation 1 still serving: running` | 4 |
| 字段名为空，或同一侧重复声明同一字段 | `non-empty name` / `declares field "count" more than once` | 4 |

接收侧也不是只信发送方的预览：`--logic-worker` 与候选程序可以用 `schema:` 声明自己接受的
状态契约，`restore` 会拒绝未声明字段或类型不符的值，并且拒绝时不改当前状态。真实候选走查
（`tests/logic_process.rs::a_generation_that_refuses_the_import_does_not_replace_the_old_one`）
让宿主把 `count` 迁移成 `text`，而候选仍声明 `number`：宿主报告
`the new generation refused the import: ... is text, but schema v2 declares number`，观测到旧代
仍在服务，新代未被采用，exit 4。这样“导入失败保留旧版”不再只是模型里的分支。

## 4. blue10 缺口 2：候选构建真实编译

### 4.1 候选不是“描述”，而是 `cargo build` 的产物

`--logic-candidate` 新增：

```text
build:<manifest-path>  bin:<name>  target-dir:<path>
```

有 `build:` 时处理器真实运行：

```text
cargo build --manifest-path <manifest> --target-dir <target> --bin <name>
```

- 判定只看真实退出码与产物是否存在；失败时打印 stderr 的最后 8 行，`Build.outcome` 为
  `Failure`，不会因为没有 `admit` 就变成成功。
- `target-dir` 默认在系统临时目录，不在运行中二进制旁边；`Candidate::may_replace` 仍拒绝
  与 `running:` 相同的路径。
- 候选只由 `build` 产生；`check` 依旧不构成候选（T17.04 的验收词）。
- `build:` 与手写的 `action:`/`outcome:`/`stamp:`/`artifact:` 互斥：同时出现直接拒绝，
  避免“真实构建忽略了一个手写结论”的静默歧义。

### 4.2 候选程序与设计器共用一份协议定义

`fixtures/logic-candidate` 是一个不依赖第三方 crate 的小二进制，通过 `#[path]` 直接包含：

- `src/app/logic/core.rs`
- `src/app/logic/ipc.rs`
- `src/app/logic/worker.rs`

因此候选进程说同一版本的帧协议，不存在“fixture 里复制一份协议、日后漂移”的问题（原则 #35）。
fixture 自己的业务程序故意与旧代不同：`idle --go--> review --approve--> done`，而旧代是
`idle --go--> running`。`--logic-process` 的新代事件 `go`/`approve` 能走到 `review`/`done`，
这就是“新逻辑确实在新产物里生效”的观察点，而不是只换了启动参数。

### 4.3 实现中当场发现并修掉的问题

1. 用 `include!` 包含带 `//!` 模块文档的源文件时，`rustc` 报 E0753；改为真实模块文件 +
   `#[path]`，并使 fixture 的模块目录存在（否则 `#[path]` 的相对路径无法解析）。
2. 首版 `#[path]` 层级按“源文件所在目录”手算，实际按“模块目录 × 包根”解析；构建直接报
   “couldn't read ...”。已按构建错误修正并实跑通过，而不是猜一个能过的路径。
3. `DuplexProcess::finish` 首版消耗 `self`，而驱动结构持有它，无法在成功后继续打印进程标签；
   改为 `&mut self` 并用 `finished` 标记防止 `Drop` 二次终止。
4. `Termination::Stopped` 的说明把“关闭 stdin”说成“礼貌信号”；已改为“礼貌请求”。
5. `--logic-candidate` 没有 `admit` 时原本只打印“debounced”；现在真实构建会先构建并报告结果，
   构建失败仍返回非零。

### 5.7 Linux 原生图形会话：从“日志说创建”到“窗口真的存在”

第一次有界会话的日志已输出 `window ... created 1280x800`，但 `xwininfo -root -tree` 当时只看到
一个 **10x10 的未映射 helper**，没有 1280x800 的窗口。原因是 `src/host/platform.rs` 只调用了
`rust_widgets::create_window`：该函数在 `WidgetKind::Window` 上路由到 custom control backend，
只挂载一个模型，**不构造 OS 窗口**；`show_widget` 也只把模型置为可见。日志里的 1280x800 是请求
值，不是可观察事实。

修正后，宿主按三步建窗：

1. `rust_widgets::platform::get_platform().create_window(...)` 构造真实 GTK toplevel；
2. `runtime::register(Window)` 挂载宿主绘制/分发所用的 widget；
3. `runtime::set_host_window(widget, host)` 建立双向翻译，再 `show_widget(widget)`。

`close_window` 也改为先 `hide_widget` 再解除关联，避免 native 窗口在进程退出前一直可见。

```text
$ cargo build --features linux-native --bin rustage
$ ./target/debug/rustage --launch --exit-after-ms 8000 &
$ sleep 2; xwininfo -root -tree | grep rustage
0x5000001 "rustage": ("rustage" "Rustage")  10x10+10+10  +10+10
    0x5000003 "rustage": ("rustage" "Rustage")  1280x800+10+46  +0+36

$ xwd -root -silent -out /tmp/rustage-session6.xwd
$ python3 /tmp/xwd_to_png.py /tmp/rustage-session6.xwd /tmp/rustage-session6.png
v7 2560x1440 bpp=24 stride=4 ...
# 窗口客户区采样点 (100,100)、(600,300) 均为 (240,240,240)，
# 即 paint_area 的 clear colour；说明 connect_draw 真实执行，窗口不是桌面残留。

desktop session started: backend gtk, gui mode NativeInteractive, window 6000285942072475649,
ended HostEnded, 8043 ms
# exit 0
```

这是**窗口真实存在、窗口标题/几何可见、绘制回调按 clear colour 执行、事件循环有界关闭**的证据。
它仍然**不**证明控件树的绘制内容、IME 时序、鼠标/键盘事件转发或视觉回归：基线窗口没有控件，
客户区本来就是空白。因此：

- `hosts.linux.designerHost` 的理由补上了这条运行证据（状态原本就是 `certified`，不因文案改变）；
- `linux × desktop` 输出 profile **仍是 `build-verified`**：那一格说的是生成物，不是设计器窗口；
- 控件交互与 IME 仍按 §8 保留为未覆盖。

`tools/gui-smoke/run.py` 是可复跑的门禁：它等待真实 1280×800 窗口，先用 `xwd -id` 截取窗口，
断言按钮矩形内至少有 4 个不同像素值（空白 clear colour 只有 1 个，这是“控件树真的画了”的
轻量视觉检查，不是主题相关的基线 diff），再点击按钮一次，然后“按下 → 拖出按钮 → 抬起”
（这一步不得产生 click），再点击一次；它断言 click 序列正好是 `[1, 2]`、两次 worker 状态分别
为 `running`/`idle`、进程 exit 0。链路是：

```text
GTK paint_area → dispatch_pointer_event → Button::handle_event → base.clicked
  → host on_click → mpsc channel → worker thread → typed frame → --logic-worker
  → state reply → host::gui-smoke log
```

这已经不是“UI 进程内部自演”：业务状态在第二个真实进程里，管道和代际检查都是 §3 的同一套实现。

没有点击时 `--smoke` 仍以 **exit 4** 结束（实测 `smoke 0 click(s)`），不把“窗口存在”当成功。

同一次会话的 `xwd` 截图里，客户区左上角能看到一个带 `Click` 文本的真实按钮，说明
`render_frame_tree` 把挂载的控件画出来了。

**键盘输入仍被上游阻塞，但修复已被临时验证。** 宿主尝试了 `runtime::focus_widget(field_id)`
（设置路由器焦点）以及 `XSetInputFocus` + `Tab`，然后用 XTest 注入 `abc`，文本框没有收到任何改变。
原因在固定修订 `8178d048`：`dispatch_pointer_event` 从不调用已有的 `focus_on_pointer_press`
（生产代码里没有调用者），且 GTK 的 `paint_area` 只调用 `set_can_focus(true)`、从未
`grab_focus()`，所以键盘事件到不了这个区域。（**§11.1 复核更新：** 在固定修订上给 `paint_area`
显式 `grab_focus()` + X `XSetInputFocus` 后，键盘与真实 IME 已可工作；上游两处缺口仍未修复。）

为了确认这两点就是全部缺口，本轮在一个**临时 git worktree**（`/tmp/rust-widgets-keyboard`，
HEAD 仍为 `6c6af71e`）上只加了 18 行：

1. `dispatch_pointer_event` 在 press 命中可聚焦控件时调用 `focus_on_pointer_press(target)`；
2. GTK 按钮按下处理里 `paint_area.grab_focus()`。

用补丁构建后 `tools/gui-smoke/run.py --keys` 通过：

```text
gui-smoke: keyboard input verified with the upstream focus fix
INFO host::platform: smoke field final: "abc"
```

随后已删除 worktree，并把 `Cargo.toml`/`Cargo.lock` 恢复为固定 git 修订；仓库代码与默认门禁
**没有**携带这个补丁。默认 `run.py` 不启用 `--keys`，所以它不会把未修复的上游当成通过。
具体请求与验证细节见 [feedback-20261015.md §17](../rw-feedback/feedback-20261015.md)。

**附带观察：** 补丁后文本确实变成 `"abc"`，但 `LineEdit` 的 `on_value_changed` 回调没有触发
（没有 `smoke field changed: abc` 日志）。宿主因此用循环结束后的 `get_widget_text` 直接读结果；
回调路径是否缺一个 `ValueChanged` trigger 仍待上游确认，已记在同一节。

**一个未定性的观察：** 用“立即 press/release”的脚本时，有一轮记录到同一会话多次回调；把
press 与 release 分开的复跑稳定为每次物理点击 **1 次**。本轮没有定位它是 XTest/GDK 的多次点击
合成还是回调重复，因此不以多次回调作为通过证据，也不把它写成已确认的产品缺陷；
`tools/gui-smoke/run.py` 用分开的按下/抬起，稳定得到 `[1, 2]`。

### 11.1 IME：之前“无法合成可靠 preedit”的判断是错的

根因不在宿主代码，而在输入法状态：

```text
$ fcitx5-remote            # 0 = closed / 1 = inactive / 2 = active
1
$ fcitx5-remote -n        # current input method
keyboard-us
```

当时 fcitx 处于未激活状态，当前输入法还是 `keyboard-us`，所以 GTK 每一键都收到一个普通
`commit`——这是输入法的正确行为，不是“preedit 合成失败”。把状态切到激活的 `pinyin` 后，同一
二进制立即出现真实合成：

```text
$ fcitx5-remote -o && fcitx5-remote -s pinyin
$ fcitx5-remote
2
$ fcitx5-remote -n
pinyin
```

```text
INFO host::platform: smoke IME client window: realized=true, gdk=true, context=Some("fcitx5"), gtk-im-module=Some("")
INFO host::platform: smoke IME preedit: n
INFO host::platform: smoke IME preedit: ni
INFO host::platform: smoke IME preedit: ni h
INFO host::platform: smoke IME preedit: ni ha
INFO host::platform: smoke IME preedit: ni hao
INFO host::platform: smoke IME commit: 你好
INFO host::platform: smoke field changed: 你好
INFO host::gui-smoke: event accepted: Field/change (text="你好") -> node 2: call edit (call)
INFO host::gui-smoke: worker after change: state=editing
INFO host::platform: smoke field final: "你好"
```

`context=Some("fcitx5")` 是比“有 commit”更强的证据：它说明选中的是 fcitx5 的 IM context，而不是
会逐键提交的 fallback。`gtk-im-module=Some("")` 表示 GtkSettings 没有显式指定模块，GTK 按
`GTK_IM_MODULE=fcitx5` 选择了 fcitx5；这两点一起排除了“宿主根本没装 IM context”的可能。

宿主侧本轮补的三件事：

1. `focus_in` 时先 `reset()` 再 `focus_in()`，并在日志里记录 focus-in，避免把 WM 的焦点
   交接时序误判成输入法问题；
2. 字段文本由一个 100 ms 的去重 watcher 观察，IME commit、`ValueChanged` 和宿主键路径谁先
   报告都只产生一次 `Field/change`；
3. `tools/gui-smoke/run.py --ime` 显式记录并设置环境前提（`fcitx5-remote -o`、`-s pinyin`），
   退出时恢复原状态；如果环境不满足，脚本失败而不是把逐键提交当成通过。

连续 5 次 `python3 tools/gui-smoke/run.py --ime`（修复 harness 前）以及修复后 3 次，共 8 次均得到：

```text
gui-smoke: real fcitx preedit and commit verified
INFO host::platform: smoke IME commit: 你好
INFO host::platform: smoke field final: "你好"
```

**边界：** 这不是“任何环境都会合成”。fcitx 未激活或停在 `keyboard-us` 时，逐键 commit 是正确
行为；上游仍缺少“指针按下移动键盘焦点”和“`ValueChanged` 在键路径上触发”的修复（feedback §17）。
本轮只证明：固定修订 + 宿主焦点 workaround + 一个已激活的 pinyin 输入法，真实 preedit/commit
可稳定复现。

### 11.2 F13/F14：声明事件、绑定与多控件路由已接到真实控件

上一轮的冒烟桥只把单个按钮的字符串送进 worker，确实不是设计器事件模型。本轮把它改成三层：

| 层 | 实现 | 真实输入 |
|---|---|---|
| 声明 | `app::data::events::{Registry, Wiring, fire}` | `click`（无载荷）、`change`/`submit`（`text` 必填） |
| 绑定 | `app::data::dispatch::Dispatcher` | 主按钮 `Command(count)`、字段 `Call(edit)`、提交按钮 `Call(submit)`；权限经 `PermissionGate` 允许 |
| 投递 | `app::run::gui_smoke::{Document, Bridge}` | 只有同时通过声明、载荷、接线和绑定的事件才进入 `--logic-worker` |

`host::smoke` 现在传的是带角色的 `SmokeEvent`（`Primary`/`Field`/`Submit`），不再让平台层
知道文档节点或动作。真实回调来源：

- 主按钮 `on_click` → `Primary/click`；
- 字段文本 watcher（以及 IME commit / `ValueChanged`）→ `Field/change`，载荷是完整文本；
- 第二个按钮 `on_click` → `Submit/submit`，载荷是提交时字段的文本。

一次真实会话的日志（`run.py --keys`）：

```text
INFO host::gui-smoke: event accepted: Primary/click -> node 1: command count (command)
INFO host::gui-smoke: worker after click: state=running
INFO host::gui-smoke: event accepted: Submit/submit (text="") -> node 3: call submit (call)
INFO host::gui-smoke: worker after submit: state=submitted
INFO host::platform: smoke field changed: abc
INFO host::gui-smoke: event accepted: Field/change (text="abc") -> node 2: call edit (call)
INFO host::gui-smoke: worker after change: state=editing
```

拒绝路径不是异常退出，也不是静默成功：未声明事件 `Undeclared`、载荷不满足 `Payload`、
声明了但该节点没接线 `Unwired`、接线了但没绑定动作 `Unbound` 都会以 `event refused: ...` 记录，
并且**不会**发给 worker。`gui_smoke::tests` 的 7 个测试逐条覆盖这些分支；`host::smoke::tests`
覆盖角色/载荷/无桥丢弃。

worker 程序对 `click`/`change`/`submit` 在 `idle`/`running`/`editing`/`submitted` 四个状态下
都是全定义的，因此“事件模型接受”不会因为业务核心缺少对应转移而变成 `error=`；如果 worker 仍
返回 `error=`，Bridge 以 ERROR 级别记录，而不是把错误文本当作 state 打印。

**仍未覆盖（如实保留）：** 这是“真实控件的运行时事件路由”，不是设计期的事件编辑面板。
`panel.events`/`panel.data` 的增删改绑定 UI、任意控件树的节点身份分配、以及文档加载后把真实
声明接进这条桥，仍是后续工作；本轮没有把冒烟文档说成完整设计器。

### 11.3 中文“只有第一个字正常”：用系统字体覆盖编译子集

用户报告的现象与编译子集完全吻合：`desktop` 内置的 CJK 矢量子集只覆盖 `U+4E00..=U+511F`，
`你`（`U+4F60`）在范围内，`好`（`U+597D`）、`界`（`U+754C`）不在，于是第一个字有轮廓、后面
是 tofu。宿主现在在 `init` 时注册系统 CJK 字体（优先
`/usr/share/fonts/truetype/droid/DroidSansFallbackFull.ttf`，否则
`/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc`）：

```text
INFO host::platform: registered system CJK face: /usr/share/fonts/truetype/droid/DroidSansFallbackFull.ttf
INFO host::platform: smoke field final: "你好世界"
```

视觉证据 `target/cjk-20261019-field.png` 由真实 GTK 窗口的 `xwd` 截图裁剪得到，四个字
`你好世界` 全部有可辨认轮廓。

**取舍：** `runtime-fonts` 注册的字体对它所覆盖的每个字符都会被咨询，包括 Latin；本机因此用
系统字体作为默认字面，而不是加一层脚本过滤（库里没有这个接口）。如果系统没有候选 CJK 字体，
宿主以 WARN 明确说“子集外会是 tofu”，不把缺失伪装成支持。
