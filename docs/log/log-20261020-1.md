## 1. 结论摘要

1. **T18.06 的设备发现不再是声明式输入。** `--target-local discover[:ios|android]` 真实启动
   `xcrun simctl list devices available --json` / `adb devices -l`，解析真实答案并保留
   `Booted`/`Shutdown`/`device`/`unauthorized`/`offline`。安装计划对有记录但未就绪的设备给出
   `DeviceNotReady`，而不是把“已发现”当成“可安装”。
2. **T18.04 的 SDK 不再手填。** `sdk:android:auto` 从 `ANDROID_HOME`/`ANDROID_SDK_ROOT`/宿主默认
   安装位读取 `platforms/android-36`；`sdk:ios:auto` 询问 `xcrun` 得到 `26.2`。工具不在 `PATH`
   但位于 Android SDK 的 `platform-tools`/`build-tools` 时仍能被找到并按其真实路径启动。
3. **T18.07 的签名从引用走到真实工具。** `sign:<id>:<identity>:<artifact>:<credential>:<source>`
   先按引用检查凭证存在（环境变量/文件/钥匙串元数据，不读取值），再执行
   `codesign --force --sign <identity> <artifact>` 并 `codesign --verify`；只有两步都成功才把 job
   标为 done 并记录产物的字节数与摘要。非 macOS 宿主明确回答“没有对应适配器”，不假装调用 gpg/signtool。
4. **T18.05 的受限生成物已真实链接并运行。** `tools/generated-project/run.py --profile mini` 与
   `--profile embedded` 用 `--generate target:stripped` 的源码建立独立消费者 crate，分别以
   `mini`/`embedded` 单一 profile feature 构建并运行，得到 `generated-mini-ok` / `generated-embedded-ok`。
5. **T18.04 另取得 Android 交叉构建证据。** 同一份 default 生成源码以 `mobile,android` 在
   `aarch64-linux-android` + NDK 29 上构建为 ELF 64-bit ARM aarch64 共享库。**没有**运行、没有安装、
   没有据此宣称真机或模拟器支持。
6. **blue12 的 F19 已实现到真实调用链。** 新增
   `src/app/debug/{adapter,protocol,session,breakpoints,inspect,mapping,hotswap,recovery}` 与
   `--debug` 命令；真实 DAP 传输、请求顺序（含 lldb-dap 的
   `launch` → `initialized` → `setBreakpoints` → `configurationDone` → `launch response` 顺序）以及
   macOS 上的真实 `lldb-dap` 最小调试例与 attach 均已验证。Linux/Windows 适配器与真机目标仍未实测。
7. **本机真实 `lldb-dap` 会话语义已验证，且一个误判已修正。** 首次会话在 `launch` 上超时，原因
   最终确认是**客户端的协议顺序**（先等 launch 响应才发 configurationDone），不是系统权限；修正后
   真实会话完成停止/线程/作用域/变量/求值/单步/继续/退出。适配器探针一度用
   `DevToolsSecurity -status` 作为硬门禁，但本机该值为 `disabled` 时真实会话仍然可用，这是**假阴性**；
   门禁已删除，探针只按适配器能否启动判定，最小调试例由真实会话证明。
   真实 attach 也已验证：附加到外部 `sleep` 进程后断开，进程仍存活；disconnect 发送
   `terminateDebuggee = false`。

### 2.1 真实设备发现（T18.06）

- `app::targets::local::Probe` 除程序名外保存搜索目录；`from_path` 追加 Android SDK 的

### 3.2 真实的协议顺序问题与修复

第一次对 `lldb-dap` 发起会话时，`launch` 在 10 秒后超时。原因不是客户端不写帧，而是顺序：

- `lldb-dap` 在处理 `launch` 期间发送 `initialized`，并要等 `configurationDone` 才回答 `launch`；
- 客户端若先等 `launch` 响应，就永远等不到发送 `configurationDone` 的机会，形成死锁。

修复：`Client` 拆出 `send_request(seq)`/`await_response(seq)`；launch/attach 先发送请求，等
`initialized`，设置断点，发送 `configurationDone`，最后等待 launch 响应。这条顺序由
`tests/fixtures/dap_stub.py` 固化为可重复的集成测试。
