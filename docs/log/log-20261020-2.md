## 4. 响应式工作台 layout

### 4.1 结构

新增 `src/app/run/workbench_layout.rs`：

- `Area` 描述每个控件在窗口中的角色：菜单、工具栏按钮、左/右/底部面板、编辑组 tab、编辑区、
  状态栏；
- `WorkbenchLayout` 实现 `rust_widgets::layout::Layout`，按客户端尺寸计算矩形；
- `WindowHandle::set_layout` 把布局存到窗口上，库在 `Resized` 时重新应用，所以缩放窗口是真实
  路径，而不是启动时算一次；
- 每个面板再用 `PanelHandle::set_layout(BoxLayout)` 排自己的标题与列表，面板缩放时内部也跟着
  缩放；
- 编辑组数量由 `Groups` 模型决定；`sync_editors` 重建布局并重新 `set_layout`，模型与布局不会
  对“当前有几组”产生两套答案。

宽度不足 840 px 时左右侧栏宽度为 0（不重叠），编辑区仍占满中间；这与“移动端布局”不是同一件
事，只是工作台窗口的降级。

### 4.2 真实缩放证据

`WorkbenchLayout` 自己的 5 项测试固定了：尺寸变化时侧栏/编辑区随之变化、窄窗口不重叠、

### 4.3 缩放后的重绘缺口（上游）

实测时发现一个不属于布局计算的缺陷：用 `wmctrl -r ... -e` 把窗口从 1280x800 调到 1000x700，
日志确认 `workbench layout for 1000x700` 已执行，但 `xwd` 抓到的窗口内容仍是 1280 布局，直到
再点一次工具栏才更新。源码定位：`native.window_painters` 在 Linux 后端只写不读，
`invalidate_surface(window_id)` 只查 `native.canvases`（子表面），所以对窗口返回 `false`；
`Resized` 分支也没有对窗口 paint area 执行 `queue_draw`。完整请求与判据见
[`feedback-20261020.md` §3.3](../rw-feedback/feedback-20261020.md)。本轮没有用闪烁式可见性
切换或改文本来制造重绘；布局模型、测试与点击后的真实截图都是真实证据。

## 5. Linux gdb DAP 调试会话

### 5.1 探针

```text
$ target/debug/rustage --debug probe
lldb-dap: not found — missing (remedy: install `lldb-dap` from the LLVM package for this distribution); capabilities: launch attach conditional logpoints hit evaluate
gdb: /usr/bin/gdb — ready (GNU gdb (Ubuntu 15.1-1ubuntu1~24.04.1) 15.1); capabilities: launch attach conditional evaluate
adapters: 1 ready on linux
```

### 5.2 协议差异与修正

真实会话先暴露了 GDB DAP 与 lldb-dap 的两处不同；它们不是本仓库测试桩能发现的：

1. **launch 在请求内启动程序。** `gdb/dap/launch.py` 的 `launch` 请求执行 `run`，
   `configurationDone` 是空操作，且 `stopOnEntry` 不被识别；它识别的是
   `stopAtBeginningOfMainSubprogram`。若按 lldb 的顺序在 launch 之后再设断点，程序可能已经
   跑过断点。修复：`Adapter` 增加 `stages_breakpoints_at_entry`，GDB 为真；会话对 GDB 发送
   `stopAtBeginningOfMainSubprogram: true`，在 main 停下后应用断点，并如实报告
   `staged at main to apply breakpoints`。
2. **`repl` 上下文是 GDB 自己的命令行。** 求值 `n` 在 `repl` 下会执行 `next` 而不是读取变量；
   首轮输出出现了 `evaluate` 之后程序单步。修复：`Adapter` 增加 `evaluate_context`，GDB 用
   `variables`，lldb-dap 保持 `repl`。
3. **GDB 的 `variables` 不夹取 count。** `gdb/dap/varref.py` 用请求的 `count` 索引按子项数
   分配的列表；请求 100 个而作用域只有 1 个时抛 `list index out of range`。修复：会话从
   `scopes`/父 `variables` 记住每个引用的已知数量，请求页不超过该数量。

### 5.3 真实会话

```text
$ rustc -g /tmp/rustage-dbg-linux/main.rs -o /tmp/rustage-dbg-linux/program
$ target/debug/rustage --debug adapter:gdb authorize \
    launch:/tmp/rustage-dbg-linux/program break:/tmp/rustage-dbg-linux/main.rs:3 \
    start wait:8000 continue wait:8000 stack scopes:0 variables:1 evaluate:n \
    continue wait:8000 disconnect check
launched /tmp/rustage-dbg-linux/program (staged at main to apply breakpoints; continue to run)
stopped: breakpoint at line 2 (thread 1, source version 0)
running
stopped: breakpoint at line 3 (thread 1, source version 0)
frame 0 main::main at /tmp/rustage-dbg-linux/main.rs:3:0 (source version 0)
scope Locals reference 1 (1 variables)
scope Registers reference 2 (60 variables)
variables 1-1 of 1
variable n: i32 = 41
evaluate i32 41
running
output value 42
exited 0
disconnect: ending the launched process
disconnected
debug: clean
```

观察点：

- `breakpoint 1` 请求在 `main.rs:3`，GDB 的实际绑定也是第 3 行；停在 main（第 2 行）是
  **GDB 的断点布置停点**，不是把请求行当成已命中行。
- `scopes:0` 使用真实 `stackTrace` 返回的 frame id `0`；`variables:1` 使用真实作用域引用
  `1`，读到 `n: i32 = 41`；`evaluate:n` 在 `variables` 上下文返回 `i32 41`。
- 继续后程序真实打印 `value 42` 并以 0 退出。

### 5.4 attach 安全

```text
$ python3 ...  # 启动外部 sleep 300，取真实 pid
$ target/debug/rustage --debug adapter:gdb authorize timeout:8000 \
    attach:<pid> wait:4000 status disconnect
attached to <pid> (the process is not terminated on disconnect)
no debug event within 4000 ms
adapter gdb; session gdb: running; attached; source version 0
disconnect: detached from a process this session did not start
disconnected
alive after disconnect: True
```

`attach` 路径从不把 `owns_process` 置真，因此 `disconnect` 的 `terminateDebuggee` 为 `false`。

### 5.5 能力表的边界

GDB 的 `initialize` 响应声明 `supportsLogPoints` 与 `supportsHitConditionalBreakpoints`，但本轮
没有用真实会话验证 logpoint 与命中计数，所以能力表仍把它们标为 `false`（禁用而不是假装可用）。
条件断点与求值已由真实会话覆盖。

### 6.3 Linux gpg 签名

T18.07 的签名接口此前只驱动 macOS `codesign`。本轮在 Linux 上补上真实 `gpg`：

```text
$ target/debug/rustage --target-queue host:linux job:s1:linux:sign \
    sign:s1:<fingerprint>:/tmp/rustage-gpg-evidence/artifact.bin:RUSTAGE_SIGN_TOKEN:environment
signature signed with <fingerprint> by gpg
s1 sign linux: done built signing <fingerprint> with RUSTAGE_SIGN_TOKEN from environment (reference only)
1 job(s): 0 queued, 0 running, 1 done, 0 failed, 0 cancelled

$ gpg --verify artifact.bin.asc artifact.bin
... Good signature from "Rustage Evidence <evidence@example.invalid>" [ultimate]
```

- `sign_with_gpg` 执行 `gpg --batch --yes --detach-sign --local-user <identity> --output <artifact>.asc <artifact>`，
  再以 `gpg --batch --verify` 复核；只有两步都成功才是 `Signed`。
- 凭据只检查存在（环境变量/文件/钥匙串元数据），不把密码传给命令行；需要口令的密钥会得到
  gpg 自己的失败信息，而不是假成功。
- 单元测试 `gpg_signs_and_verifies_a_real_file_with_a_throwaway_key` 在临时 `--homedir` 里生成
  一次性密钥，不触碰用户 keyring；本机实跑通过。
- Windows 仍为 `Unavailable`（`signtool` 未驱动），没有假装已签。

1. **Windows 调试适配器未实测。** `vsdbg` 仍只在能力表里；本机没有 Windows。
2. **macOS 的 `lldb-dap` 未在本轮复跑。** `Adapter` 新增了两个字段，但 lldb 的
   `stages_breakpoints_at_entry = false` 与 `evaluate_context = "repl"` 保持原有行为；
   真实 macOS 会话需要在下一轮重新确认。
3. **GDB 的 logpoint / 命中计数未验证。** 能力表保持禁用；GDB 的 `initialize` 声明支持，
   但声明不等于真实行为。
4. **Linux 的 profile 产物未运行。** 五格都是 rlib 构建证据；没有 mini/embedded 设备，
   也没有 tablet/mobile 真机。
5. **工作台布局不是拖拽停靠。** 面板位置由响应式 layout 计算；拖拽停靠、浮动、每个 tab 的
   滚动位置仍属后续切片。窄窗口把侧栏收成 0 宽，而不是提供一套移动端工作台。
6. **GTK resize 后不主动重绘。** 新布局在下一次输入事件前可能仍显示旧帧；这是上游
   `window_painters` 未被读取的缺陷（[`feedback-20261020.md` §3.3](../rw-feedback/feedback-20261020.md)），
   不是宿主布局计算错误。
7. **断点重映射的窗口循环仍未接上。** `Book::remap` 与 `SourceMap` 有模型级证据；自动重设
   DAP 断点的 UI 循环仍属窗口层。
8. **源映射没有独立持久化文件。** `mapping::from_debug/to_debug` 与生成管线共用
   `SourceMap`；`--generate` 仍未写 `.map` 文件。
9. **Android/iOS 安装与运行仍未做。** 本轮没有新增设备证据。
10. **Wine/Windows 实机仍未运行。** `build-verified` 不等于 `certified`。
