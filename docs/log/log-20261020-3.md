## 3. 上游反馈：embedded profile 回归

`cargo build --manifest-path ~/workspace/rust-widgets/Cargo.toml --no-default-features \
  --features embedded --lib` 失败：

```text
error[E0599]: no variant, associated function, or constant named `TabWidget` found for enum `WidgetKind`
  --> src/lib.rs:891:42
(same for `Splitter`, `Grid`, `Dialog`)
```

`lib.rs` 的四个新构造器用 `#[cfg(not(alloc_frugal))]`，而 `widget/kind.rs` 的变体用
`#[cfg(widgets_unstripped)]`。`embedded` 的 `alloc_frugal` 为假、`widgets_unstripped` 也为假，
所以构造器被编译、变体不存在；`mini` 因 `alloc_frugal` 为真而绕过。详细请求与判据见
[`feedback-20261020.md` §0.1](../rw-feedback/feedback-20261020.md)。

Linux 五 profile 的本轮结果：

|---|---|---|

| tablet | 同上换 `tablet` | 通过 |
| mobile | 同上换 `mobile` | 通过 |
| mini | 同上换 `mini` | 通过 |
| embedded | 同上换 `embedded` | **E0599，失败** |

`tools/generated-project/run.py --profile mini` 仍得到 `generated-mini-ok`；

### 4.2 修复 1：页面文档到生成器没有消费者

`src/app/generate/document.rs` 早有 `to_library_document`（页面扁平节点 → 库的单键 widget
文档），但标着 `#![allow(dead_code)]`，没有任何调用点。`--generate document:<file>` 只把文件
原文交给库，因此 `/pages/main.json` 会被拒绝为：

```text
rustage: (document): JSON root must have exactly one widget key, found 3: format, nodes, page
```

修复：`src/app/run/generate.rs` 新增 `read_document`。它先解析 JSON；若对象同时有 `page` 与
`nodes`，就通过 `root_of` 找到工程根、用 `PageDocument::parse` 读取，再调用唯一的翻译函数。
原始 widget JSON（`tools/generated-project` 使用）路径不变。新增单测
`a_project_page_is_translated_into_the_generator_document`。

### 4.3 修复 2：新工程根节点不是生成器可消费的控件

模板把页面根建成 `NodeKind::new("page")`，而库生成器只认识 `window`。即使修好 4.2，出厂模板
仍会在生成期得到 `page: no control by that name`。依据决策 Q5（页面/窗口作为同一入口单位），
把新页面的根改为 `window`：

```text
# /tmp/.../pages/main.json
"nodes": [{ "id": 1, "type": "window", "children": [], "properties": [] }]
```

旧工程若根仍是 `page`，`--generate` 会明确拒绝，不静默改写文档。`create.rs` 的模板测试同步
断言 `"type": "window"`。

### 4.4 修复 3：支持矩阵负向测试失效

`tools/support-matrix/check-support-matrix.test.mjs` 的“文档与数据不同步会被拒绝”用例仍在替换
一行早已变成 `build-verified` 的 macos 行，替换不到任何文本，断言因此读到空错误串。现在替换
linux 的首个 `build-verified` 格，负向用例重新能失败。

## 9. 第 1 步：命令面板与焦点路由（本轮后续）

> 依据：[issue-20261020](../issues/issue-20261020.md) 第 1 步、[blue13](../plan/blue13.md) P0-2、
> [项目原则](../plan/principle.md) #17/#22/#26/#59。实现未提交。

### 9.1 结构与单一事实来源

- 新增 `src/app/run/workbench_palette.rs`：`Palette` 持有 open/query/entries/selected/previous
  focus，搜索、最近使用、帮助全部调用 `app::commands::palette`（`search`/`Recents`/`help_for`），
  没有第二份命令清单或第二套过滤算法。
- `src/app/run/workbench_gui.rs` 用真实控件镜像它：`PanelHandle` + `new_line_edit` +
  `new_list_box` + `new_label`，面板由 `BoxLayout` 排布；打开/关闭与查询变化只更新这一份状态。
- 命令面板是窗口级 overlay，由 `WorkbenchLayout` 的 `Area::Palette` 定位；它创建在编辑组之后，
  GTK overlay 的叠放顺序因此把它放在停靠面板与编辑器之上。
- 工具栏新增 `Commands`，View 菜单新增 `Command Palette`；两者都走 `palette:open`，不复制逻辑。

### 9.2 焦点与重入

- 打开：记录 `focused_widget()`，显示面板并 `focus_widget(query)`；失败时明确报告并关闭，
  不留下一个没有键盘入口的面板。
- 关闭：隐藏面板，`focus_widget(previous)`；原控件已销毁时 `clear_focus()`。
- 列表重建（clear/add/set_current_index）排到下一轮主循环。原因是列表的 `item_selected`
  回调会锁同一个 `Gui` 互斥量；在持有锁的动作里同步重建会让 `std::sync::Mutex` 自锁。
  这不是绕行，而是把“控件信号可能同步重入”的所有权边界写清楚。
- 列表信号的订阅通过 `widget::runtime::with_widget_mut` 与 `event_signal_dyn`，没有新增库 API，
  也没有绕过真实控件。

### 11.2 画布用什么控件，为什么不是子按钮

一开始按“每个节点一个真实 Button 覆盖在画布上”实现过，但两个问题在真实窗口里立刻出现：

1. 根容器 `window` 覆盖整张画布，所有指针事件都被它截获，画布本身收不到 press/move/release；
2. 即使只为叶子建按钮，框选跨过按钮时事件会转到按钮，release 不再回到画布，框选无法完成。

改成由库的 `Canvas` 控件自身绘制节点（`fill_rect`/`draw_rect`/`draw_text`），命中测试由
`Scene` 对同一组矩形完成。这样画布始终拥有整块指针区域，点击与框选走同一条路径。

创建控件时发现 `create_widget_of_kind(WidgetKind::Canvas, …)` 在原生桌面后端返回 0：它要求
platform 提供 per-widget surface，而原生桌面没有。库自己的 `create_*` 走的是
`get_control_backend_for_widget(kind).create_canvas(...)`；工作台改用这条路径后成功。缺陷记入
[`feedback-20261020.md` §0.4](../rw-feedback/feedback-20261020.md)。

### 11.3 交互规则

- Outline 行点击映射到 `row_nodes()` 的同一索引；选择调用 `select_only`。隐藏节点拒绝为
  `node 4 is hidden; hidden nodes are not selectable`，锁定节点拒绝为
  `node 5 is locked; locked nodes are not selectable`。拒绝后列表回到场景真正的选择，不留下
  “看起来选中”的行。
- 画布释放时，位移小于 8 设计像素算点击：`Scene::hit` 取最上层可选节点；大于等于阈值算框选：
  `Scene::within` 取所有可选交集，再 `select_many`。隐藏与锁定节点在两种路径里都被跳过。
- 列表重建会同步发出 `item_selected`。回调在“该行已经是当前主选择”时直接返回，否则会形成
  “选择→重建→再选择”的无限循环；这是本轮在真实窗口里观察到并修掉的缺陷。
- 画布重画被排到下一轮主循环：回调里不能重入正在派发事件的控件。

## 12. 第 4 步：调试面板（T19.03–T19.06）

> 依据：[issue-20261020](../issues/issue-20261020.md) 第 4 步、[blue13](../plan/blue13.md) P0-2、

### 12.1 结构

- 新增 `src/app/run/workbench_debug.rs`。面板的 **Start/Run/Step/Stop** 驱动一个后台线程；线程用

  演示 debuggee，`initialize` → `launch`（staged at main）→ `setBreakpoints` →

### 12.3 性能与“黑屏/顿挫”修复

真实窗口测试暴露了三处会让人误以为界面卡住的问题：

1. **画布每收到一个指针移动就排队一次全量重画。** 现在 `sync_canvas` 把最新画面写进一个快照，
   并用 `AtomicBool` 保证同一时刻只有一个重画在队列里；重画只读最新快照，间隔 8ms。拖拽时
   不会堆叠帧，选中/点击仍即时。
2. **每次 Start 都重新编译 debuggee。** 现在源文本不变就不改写文件，并写一个 `build.txt`
   命令戳；源文件和命令都没变就复用 `target/rustage-debug/app`。第二次 Start 不再付编译成本。
3. **无窗口的残留与“黑屏”。** 探针之前遇到断言超时会提前退出，Xlib 的 I/O 错误又会绕过
   Python 的 `finally`；现在探针在 C 级 `atexit` 注册清理，并用 `start_new_session` 启动工作台，
   Xephyr 只使用没有锁文件的显示号。运行结束/异常退出都不会留下窗口或 `Xephyr`。

调试面板原本用 `ListBox` 显示行；从主循环定时器里 `clear_items`/`add_item` 后，模型已有 7 行
但画面仍是首行，`invalidate_surface(list/window)` 也没有触发重绘。面板改为固定 7 个 `Label`
（每行一个，`set_widget_text` 的重绘路径与状态栏一致），并在日志里记录 `debug rows shown: 7/7`。
该上游行为记入 [`feedback-20261020.md` §0.5](../rw-feedback/feedback-20261020.md)。
