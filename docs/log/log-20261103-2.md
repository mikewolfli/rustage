## 4. RW-109：页面格式 v7 的节点 `constraints`

### 4.1 文档模型（`src/project/record/page.rs`）

- `PAGE_FORMAT` 6 → **7**；节点成员从 5 个变为 6 个（新增 `constraints`）。
- 新类型 `PageConstraints`：保留成员顺序、逐项校验形状，`to_json()`/`render()`/`get()`。
  - 六个尺寸界：非负 u32；
  - `margin`：整数或 1/2/4 个整数的数组（与库的 `insets_from_value` 同规则）；
  - `overflow`：`clip`/`visible`/`scroll`；
  - 未知成员保留并交给库的 `validate_child_attrs` 具名（不在宿主再建一份属性表）。
- 节点新增 `constraints()`/`with_constraints()`；写文件时即使缺省也写 `"constraints": null`
  （与其他成员“一个页面一种拼写”一致）。
- v6 文档里的 `constraints` 不按 v7 解释（保持 preserved）；v7 文档正常读写。
- 校验：`constraints` 只允许出现在非根节点；根节点由生成请求的尺寸放置，写在根上会被
  本构建读取而被 solve 忽略，因此按“静默丢弃”拒绝并给出 `nodes[id].constraints` 路径。
- 测试：`node_constraints_round_trip_verbatim`、`invalid_constraints_are_refused_with_the_reason`、
  `constraints_on_the_root_are_refused_by_name`。

### 4.2 生成翻译（`src/app/generate/document.rs`）

- `node_body` 把 `constraints` 的每个成员写成节点属性（flat），这正是库
  `ChildLayoutAttrs::from_value` 读取的位置；嵌套的 `constraints` 不会出现在库文档里。
- 测试：
  - `constraints_travel_as_the_flat_attributes_the_library_reads`；
  - `a_declared_minimum_height_reaches_the_generated_solve`：vbox + `min_height: 80`，
    读取 `GenerationReport::node_rects` 断言子节点高度 ≥ 80，证明约束真的到达库的 solve。

### 4.3 面板

`Declaration.constraints: Vec<(u64, &PageConstraints)>`，面板逐节点显示
`node {id}: min_width=…, margin=…`，并注明“本布局不支持的成员由库在 diagnostics 中具名
（例如 `overflow` 尚无运行期载体）”。

## 6. H-29：三档断点预览（`--preview tiers:<page>[:<dir>]`）

`src/app/run/preview.rs`

- 三个档位与宽度来自库自身：`rust_widgets::style::breakpoint_tokens()` 的
  `compact_max`、`medium_max`、`medium_max + 1`；分类用 `Breakpoint::of`，若宽度与档位不符
  直接报错，不写误导性结果。
- 每档用 `designer::generate` 求解（宽 × 800），打印 `node_rects` 与 `layout_issues`。
  实测同一页面：

```text
compact: 599x800 -> 3 node rect(s), 0 layout issue(s)
  node 1 (path []): x=0 y=0 599x800
  node 2 (path [0]): x=8 y=8 583x388
  node 3 (path [1]): x=8 y=404 583x388
expanded: 840x800 -> 3 node rect(s), 0 layout issue(s)
  node 1 (path []): x=0 y=0 840x800
  node 2 (path [0]): x=8 y=8 824x388
  node 3 (path [1]): x=8 y=404 824x388
```

- **可选帧输出**：`tiers:<page>:<dir>` 在每档把生成器的 `node_rects` 逐个应用到已装载控件
  （`widget::runtime::set_geometry`），再用库的 `SvgPaintBackend`/`paint_tree_into` 写
  `<dir>/<tier>.svg`。几何来自生成 solve，绘制来自库本身，不另写布局或渲染。两个实现细节：
  ① 只有完整装载器 `JsonLoader::load` 会建立父子链并让 paint 走子树，增量视图会话只画根；
  ② C ABI/状态后端的 `set_widget_geometry` 只记录一个 paint 不读的矩形，必须用
  `runtime::set_geometry` 才能真正移动控件。实测三帧中标签/按钮按各自绘制规则显示
  （按钮高度用 `size_hint` 居中于分配矩形），三份 SVG 宽度与内容均不同；装载的控件与
  `forget_layout` 在结束时逐项清理。
- **边界**：分档“不同子树”需要库的声明式文档支持 breakpoint（`Node::breakpoint` 目前只在
  Rust View API），JSON 文档没有该字段；因此本命令求解同一棵树的三档宽度，并在输出末行写明
  `RW-117`。没有给宿主页面格式加一个生成不消费的 breakpoint 字段（原则 #13/#26）。
- 单位测试：`tiers_tests` 三个（分类、三档求解、三份帧与求解一致）。

## 8. H-28：鸿蒙 NAPI 桥接入（宿主脚手架）

### 8.1 决策

blue22 H-28 只写“Harmony NAPI 桥接入（宿主脚手架 0 引用）”，验收引用上游
`examples/harmony_napi_bridge_flow.md` 与 `rw.h`，没有定义宿主入口。本轮按推荐方案执行，
但把范围收窄到**可直接核验的宿主脚手架**：在 `packaging/harmonyos/` 补齐 `module.json5`
本来就引用、而目录里一直缺失的应用层（`EntryAbility.ets`、`pages/Index.ets`、NAPI 模块与
CMake），而不是新造一个 `--scaffold` 命令。理由：

- `module.json5` 的 `srcEntry` 已指向 `./ets/entryability/EntryAbility.ets`，补上它是修一个
  悬空引用，不是新功能；
- 宿主当前没有“生成应用工程”的产品边界（设计器输出是三宿主的 Rust UI），新增 CLI 会是
  Plan 未定义的接口；把桥写进既有打包脚手架则正好是“0 引用 → 有引用”；
- 真正的构建阻断不是代码，而是 T00.04 未定的应用身份/最低系统版本/签名。

`pages/Index.ets` 必须 import `libentry.so`（桥的消费者，不是第二套 UI）；`tools/resources/lib/manifest.mjs`
的检查从“资源树不得提供 ArkTS 壳”改为“声明的壳必须存在、且必须引用桥”，并新增两个负向测试。

`substituted:false` 原样写出；静态文件在身份未定时也会输出，静态项里出现 token 则拒绝。
新增 `tools/resources/generate-resources.test.mjs` 四个用例（定身份写全部、未定身份写静态、

`packaging/harmonyos` 内，`../`/绝对路径被 `check-resources` 与生成器双双拒绝
（防止把包外文件复制进产物）。

### 13.3 RW-58（行滚动）：预览状态保留的滚动半

`src/app/preview/state_keep.rs`、`src/app/preview/preview_service.rs`、`src/app/run/preview.rs`

T14.03 的验收包含滚动，而本模块此前把“滚动无通用读写”写成 `SCROLL_GAP` 常量，并由预览
报告给用户。4.0.0 的 `ScrollableRows` + `scroll_row` 属性（31 个行容器）让这句话不再成立，
因此本轮把滚动接上：

- `capture_state(index, focused)` 逐节点读库的 `scroll_row` 属性（`read_widget_property_by_id`）；
  不是行容器的控件（标签等）返回 `None`，记为 0。
- `set_scroll_row(id, row)` 通过同一属性回写（`write_widget_property_by_id`），由控件自己
  clamp；宿主不维护第二份“第一个可见行”。
- `restore_scroll(capture, index)` 只规划 `scroll > 0` 且 node+kind 都匹配的项；`Gone`/
  `Incompatible` 按原有规则报告、不应用。`restore_focus` 现在只规划 `focus` 为真的项——
  `capture_state` 会记录所有节点的滚动，不能因此把每个节点轮流聚焦一遍。
- `Preview::restore_state` 先恢复焦点，再恢复滚动；`SCROLL_GAP` 改为**像素**滚动
  （`ScrollArea`/`MdiArea`）的具名边界，不再是“没有任何通用读写”。
- GUI 的预览重建（`workbench_gui::preview_rebuild`）现在在 `update_json`/`mount_json`
  前后调用 `capture_state`/`restore_state`：之前这套状态保留只在 CLI 与测试里用，
  工作台的预览重建根本不保留焦点或滚动。恢复结果写入
  `app::run::workbench-preview-state` 日志（逐条 `render()`），不新增界面文案。
  **证据边界**：有界 GUI 会话不加载工程，不会走到 `preview_rebuild`；该接线只做了
  `cargo check` 验证，`capture_state`/`restore_state` 本身由下面预览测试真实覆盖。
- CLI 的 `preview capture` 只打印“会被恢复的状态”（有焦点或滚动了至少一行），
  没有时输出 `nothing focused and nothing scrolled`，不再为一个页面打印全部节点。

### 13.8 GUI 窗口按键路由（T04.08/T05.05）

在此之前，工作台没有任何键盘路由：菜单、工具栏、命令面板都能执行命令，但按 Ctrl/Cmd
快捷键什么也不会发生（快捷键只在 `--keys` 与审计路径真实生效）。库其实提供了窗口级入口
`WindowHandle::set_key_handler`：事件循环在把按键交给焦点控件之前，先把**命令键**交给窗口，
裸字符、IME 组合中的键和处理器拒绝的键都继续到控件。

实现：

- `src/app/commands/shortcuts.rs` 新增 `key_of_shortcut(shortcut, platform)`：把库的规范
  `shortcut::Shortcut` 转成本 keymap 自己的 `Key`。两者词汇不同（库写 `Esc`/`Del`，
  `Primary` 在 macOS 是 `Cmd`、在 Windows/Linux 是 `Ctrl`），因此转换必须**按平台**
  写 primary：`Platform::keymap()` 把绑定拼成 `Cmd+Z`，传入键也必须是 `Cmd+Z`，两者才能匹配。
  没有本 keymap 拼写的键（F 键、媒体键）返回 `None`，窗口不认领。
  **这一条是自查发现的 bug**：最初的实现把 `Primary` 一律写成 `Ctrl`，在 Linux/Windows 上
  解析正常，但在 macOS 上绑定已改成 `Cmd`，所以**每个 primary chord 都匹配不上**；新增的
  `Platform::MacOs` 断言（`uses_meta()` 且解析为 `edit.undo`）就是防止它再回归。
- `src/app/run/workbench_gui.rs` 在进入事件循环前安装处理器：
  - 用**平台 keymap**（macOS/Windows/Linux）解析，和窗口、审计读的是同一张表；
  - `Scene` 带上当前模式、焦点面板、`text_field`（`FocusInfo::accepts_text_input`）与
    `composing`，因此文本框里裸 Escape 不会关面板，输入法组合期间一律放行；
  - `Triggered` → 走与菜单叶相同的 `run_command`，并认领该键；`Pending`/`Suppressed`/
    `Nothing` → 不认领，键继续到控件。
- **两键序列**（默认表里只有 `Ctrl+K Ctrl+S`）故意不在窗口处理器里路由：处理器一次只看到
  一个规范键，若缓存第一个 chord，下一键若是文本就永远到不了处理器，缓存会变脏；序列仍由
  `--keys` 与审计路径覆盖。

  带参数的面板项按 `Menu::command_id` 查表。
- **真机可验证的接缝**：每次路由命中写一行 `app::run::workbench-keys` 日志

## 15. 第五轮：编辑器文本进入模型、脏状态与关窗拦截（2026-11-04）

依据：blue22 §5「把闭合项按真实消费者收编进宿主」与 §4.1 的 **RW-53**（宿主阻塞点“未保存修改拦截”）；
原则 #6（文档模型是唯一事实来源）、#10（用户操作形成完整事务）、#22（失败显式可诊断）、
#59（同一概念不得有漂移的平行路径）。上游基线仍是 rust-widgets 4.0.1（`ee4260d8`），**本轮未修改上游代码**。

### 15.1 发现的缺陷：编辑器的文本从未进入文档模型

工作台的编辑器是库的 `CodeEditor`，但宿主**没有订阅它的文本变化**：

- `CodeEditor::text_change`（每次提交的编辑，描述行区间，不克隆文档）与 `text_changed`（整篇替换）
  都没有消费者；
- `Gui::active_document` / `file_save` / `file_save_all` / 自动补全与导航读的都是
  `Groups` 里的**模型文本**。

后果（按严重度）：

1. **保存写入的是旧文本**：在窗口里打字后执行 `file.save`，写到磁盘的是打开时的内容，
   输入的字符被静默丢弃（原则 #10/#22）。
2. **任何触发 `sync_editors` 的命令都会把输入回滚**：`sync_editors` 用模型文本覆盖控件，
   而模型没有新输入，所以切换标签页 / 拆分分组 / 扩展选择等操作会把刚打的字抹掉。
3. **脏状态永远为假**：`Tabs::is_dirty` 在 GUI 里从未被置真，标题的 `•` 标记与
   `close_project` 的未保存拒绝（`ui.error.project-close-dirty`）都是死代码。
4. **状态栏永远指向 `src/main.rs`**：`Workbench` 的文档只在启动时写过一次，
   切换标签页不更新，`status_line()` 因此长期显示一个窗口并未展示的文档。

附带发现（同一路径）：`CodeEditor::set_text` 会**压入一个撤销检查点**（文档写明“pushes one undo
checkpoint”），宿主加载文档时没有清空历史。于是启动后按 Ctrl/Cmd+Z 会“撤销加载”，把控件清空，
再经 `edit_history` 把空文本写回模型——这也是第 1 条数据丢失的一条入口。

### 15.2 实现（全部使用库自己的入口，不自造）

- `src/app/shell/groups.rs`
  - `Groups::set_text(document, text)`：按**文档名**写缓冲区。`type_into` 只能写焦点视图的文档，
    而文本变化报告携带的是“报告时该控件展示的文档”，两者不是一回事；按名字写才不会串档。
  - `Groups::dirty_documents()`：从标签页现算的脏文档集合（同一缓冲区多视图只算一次）。
    这是“哪些缓冲区有未保存修改”的**唯一**推导，删掉 `close_saved` 里原来的自建集合。
  - 两个新测试：多视图共读一个缓冲区；多视图下脏文档只记一次。
- `src/app/run/workbench_gui.rs`
  - 挂载每个编辑器时订阅 `text_change`（逐次编辑，`connect_ref`，不分配 `Arc`）与
    `text_changed`（整篇替换）。回调只写两个**位于 `Gui` 锁之外**的小映射：
    `editor_documents`（控件当前展示的文档）与 `editor_changed`（待读取的控件集合）。
    这样信号在“调用方已持有 `Gui` 锁”的路径里也不会死锁；`sync_editors` 的加载用既有
    `syncing_editors` 守卫跳过（加载不是人的编辑）。
  - `Gui::apply_pending_editor_text()`：把待读取的控件文本读进模型（`with_widget_mut` +
    `CodeEditor::text()`）。读不到的控件（正被借出）留在待读取集合里下次再试；已卸载的控件
    直接丢弃，绝不写进“当前恰好活跃”的缓冲区。
  - `Gui::set_document_text()`：写模型 + 用 `saved_texts` 基线算脏 + 同步标签页脏标记与标题；
    从脏转净时打一条 `app::run::workbench-editor` 日志。**边界**：没有磁盘基线的缓冲区
    （`src/main.rs` 等演示文档）永不算脏——它们没有可写回的文件，`file.save` 本来就以
    `ui.error.save-no-baseline` 拒绝，提示“请先保存”会是一句做不到的话。
  - `sync_workbench_document()`：把焦点分组当前标签页的文档与脏状态写进 `Workbench`，
    `status_line()` 因此跟着标签页走。`save_document` 成功后同时清除标题的脏标记。
  - `sync_editors`：进入时先 `apply_pending_editor_text()`（否则回写会用旧模型覆盖未读的输入）；
    加载文档后 `editor.clear_history()`——**加载不是可撤销的编辑**，否则 Ctrl+Z 会清空缓冲区。
  - `run_call` / `apply_action`：派发前先应用待读取的编辑，所以“打完字立刻按快捷键保存”
    不依赖轮询时机；`schedule_editor_model` 每 250ms 兜底一次（无待读取项时零成本，
    代价上限是每次一个缓冲区副本，而不是每次按键一个）。
  - **RW-53 收编**：`WindowHandle::set_close_handler`（库的关窗否决入口，macOS `windowShouldClose:` /
    Win32 `WM_CLOSE` / GTK `delete-event` 都走它）在进入事件循环前安装。`window_close_allowed`
    先应用未读编辑，再问 `Groups::dirty_documents()`：有脏缓冲区就**拒绝关闭**，状态栏写明数量，
    日志逐条列出文档名，随即用库的 `ConfirmDialog` 问一句“退出并放弃 / 继续编辑”。
  - **确认对话框用库控件，不自造**：`ConfirmDialog::new` + `set_accept_text`/`set_reject_text`，
    挂到模态栈（与重命名对话框同一套 `runtime::register`/`enter_modal`）；两个信号只写
    `close_slot`（信号在运行时派发中执行，此时去拿 `Gui` 锁会与关窗处理器自己死锁），
    `schedule_close` 每 50ms 在主循环上应用答案（与 rename/prompt 的轮询同形）。
    “继续编辑”只关掉对话框并说“没有丢弃任何修改”；“退出并放弃”调用 `rust_widgets::quit()`
    （只记录请求，帧末由循环停止，不跨线程调工具包）。键盘遵循控件自己的契约：
    Enter 走焦点环，初始为 dismiss；Tab 两下到确认动作后 Enter 才放弃。
  - **菜单退出走同一道闸**：`apply_action("quit")` 与 `file.exit` 都先问 `window_close_allowed`，
    干净窗口立即退出，有脏缓冲区时问同一句问题。这样“关窗”和“退出”不会有两套丢弃语义；
    有界会话（`--exit-after-ms`）是直接 `rust_widgets::quit()`，不经这道闸，所以自动化不会被弹窗挂住。
- `language/en.json`、`language/zh-Hans.json`、`src/app/locale/vocabulary.rs`：
  新增 `ui.error.window-close-dirty`、`ui.dialog.close-dirty-{title,message,accept,reject}`、
  `ui.status.close-cancelled`（`WINDOW_KEYS` 450 → 456）。

### 15.6 下一轮候选（本轮审计结论，未实施）

按“优先用库已有能力、不自造”的要求复核了画布，结论是**本轮不动**，原因如下：

1. 宿主的 `CanvasTransform`（`src/app/run/workbench_scene.rs`：`scale`/`offset_x`/`offset_y` +
   `place`/`to_design`）与库的 `canvas::CanvasTransform`（`scale`/`offset` + `point`/`rect`/
   `inverse_point`）是同一概念的两次实现（原则 #59）。迁移本身可行，但宿主当前把节点矩形按
   屏幕坐标画进 `Canvas`，控件自身的 `transform` 恒为单位阵；要让库的变换生效，必须同时把
   绘制改成模型坐标，并接受文字位置随缩放、字号不随缩放的外观变化。
2. 库的网格与标尺**不能表达宿主当前语义**：`Canvas::set_show_grid` 的网格按**表面像素**
   等距绘制（从控件矩形原点起算），`set_grid_space(Model)` 只影响吸附、不影响画法；
   `draw_rulers` 用的是表面像素刻度、没有模型单位标签。宿主的网格是“16 设计单位 × 缩放、
   对齐设计原点”，标尺带 100 单位文字。直接换成库的绘制会是可见的信息退化，属于产品决策，
   不能由实现方替项目方定。
3. 因此本轮记录的是**具名边界**，而不是“改用库 API”的待办：若要收敛，先补上游能力
   （网格按 `GridSpace::Model` 绘制、标尺可指定单位与标签），再一次性迁移宿主变换。

**后续（见 §17）：** 第 1 条里“同一个变换算两遍”的部分**已在第七轮收敛**——宿主的
`CanvasTransform` 类型已删除，改用库的 `canvas::CanvasTransform`；只剩“谁来施加这个变换”
（宿主按表面坐标绘制，控件自身 `transform` 仍为单位阵）与第 2 条的网格/标尺语义待处理。

## 16. 第六轮：预览重建的“输入”状态保留（T14.03 输入半）

依据：roadmap T14.03「状态保留：输入/焦点/滚动/选中」，blue22 §5 的统一验收（回写 roadmap/issue），

### 16.1 缺口

`state_keep` 的 `Kept` 早就有 `input`/`selection` 字段，但 `capture_state` 一律写空、
`restore_state` 只应用焦点与行滚动——输入的保留只能靠 CLI 手工注入 `input:<node>:<text>`。
GUI 的 `preview_rebuild` 因此在每次结构/属性编辑后丢掉用户在预览控件里输入的文字。

**难点是语义，不是通道**：库的 `get_widget_text`/`set_widget_text`（以及 `text` 属性）已经能读写，
但没有任何能力声明“这段文字是用户输入的”。若把所有非空文字都当作输入，重建会把文档刚刚
改过的标签文字也“恢复”回去——把声明值冻结成用户状态，正好违反原则 #6。

### 16.2 实现：用“与声明不同”作唯一判据

- `src/app/preview/preview_service.rs`
  - `Preview` 新增 `declared_text: BTreeMap<NodeId, String>`：JSON 路径在
    `json_to_view_tree` 得到的 `Node` 树上按 `props["text"]` 提取（键的十进制拼写就是 `NodeId`，
    与既有约定一致）；宿主 `Document` 路径取 `DocumentNode.text`；每次 mount/update 重建，
    `release_engine` 清空。它是**声明的事实**，不随打字变化。
  - `capture_state` 改用 `state_keep::capture_with_declarations`。
  - 新增 `restore_input(&Capture) -> Vec<InputRestore>`：只对“同 node 同 kind”的条目写回，
    写通道就是 `text` 属性本身；应用结果与不可恢复原因一并返回。
- `src/app/preview/state_keep.rs`
  - `capture_with_declarations(index, focused, declared)`：只有当控件当前文字与声明不同才记为
    `input`。声明没有提到 `text` 的节点不参与——没有文本通道的控件不是输入，而库不提供
    “此文本来自用户”的标志（已作为 RW-122 提给上游）。

  - `text_of`/`set_text` 直接走 `read_widget_property_by_id`/`write_widget_property_by_id`

- `src/app/run/workbench_gui.rs`：`preview_rebuild` 的 restore 闭包在焦点/滚动之后调用

- `src/app/run/preview.rs`（CLI）：`capture` 的“实况”过滤加入 `input` 非空项，空集文案改为

- **边界（如实登记）**：选中（selection）没有通用读写对，因此不捕获、不恢复（RW-122）；
  像素滚动仍是 `SCROLL_GAP`；宣言未写 `text` 的控件的输入不在覆盖范围内。

## 17. 第七轮：画布变换改用库类型（T09.05 的第一半）

依据：T09.05「平移/缩放/适合/实际尺寸、网格/标尺/参考线」，§15.6 的候选审计，原则 #35/#59
（同一语义只保留一份定义；不得有漂移的平行路径）。上游基线 4.0.1（`ee4260d8`），**未修改上游代码**。

### 17.1 改了什么

宿主的 `CanvasTransform`（`scale: f32` + `offset_x/offset_y: i32` + `place`/`to_design`）与库的
`widget::special_widgets::canvas::CanvasTransform`（`scale` + `offset: Point` + `point`/`rect`/
`inverse_point`/`inverse`）是同一映射的两次实现。本轮删掉宿主那份：

- `src/app/run/workbench_scene.rs`
  - 删除宿主 `CanvasTransform` 类型与 `place`/`to_design`。
  - 新增 `fit_transform(rect)` / `scaled_transform(rect, scale)`：**只保留策略**（按设计尺寸适配、
    或使用人指定缩放并居中），返回库的 `CanvasTransform`。
  - 新增 `canvas_rect(Rect) -> WidgetRect`：宿主设计矩形 → 库矩形类型，供 `transform.rect(...)` 使用。
  - `CanvasView::transform` 返回库类型；`CanvasLayout::update` 改用 `fit_transform` + `rect`。
- `src/app/run/workbench_gui.rs`
  - 绘制与命中改用库方法：节点/框选矩形 `transform.rect(canvas_rect(..))`、
    指针反算 `transform.inverse_point(Point::new(x, y))`、拖拽 ghost 的起点同一路线。
  - 网格/标尺取 `transform.offset.x/.y`（库字段名）。
- 测试随类型同步（`actual.rect(canvas_rect(..))`、`actual.offset.x/.y`）。

**一处可感知的差异**：库的 `rect` 对宽高做 `round().max(1)`，宿主原来做截断后 `max(1)`。
缩放后长宽可能差 1 像素；这是库的舍入规则（原则 #52 要求适配器采用明确舍入，而不是截断），
不是回归。

### 17.2 仍然存在的边界（不假装完成）

宿主仍**按表面坐标**向 `Canvas` 推命令，所以控件自身的 `transform` 恒为单位阵。要把映射交给控件
（模型坐标命令 + `Canvas::set_transform`），还要先处理 §15.6 第 2 条：库的网格按表面像素等距绘制、
标尺无模型单位标签，直接切换会造成可见的信息退化。这两件事一起做才有意义，已写入
`CanvasView::transform` 的注释与 §15.6。

## 19. 第九轮：窗口编辑器改为“一个文档一个库缓冲区”，并按文档设置语言

依据：T06.01「共享缓冲/就地编辑/区间 undo」、T06.02「高亮接库」、T04.04「同缓冲多视图」；
原则 #6（模型是唯一事实来源）、#12（能力以契约为准）、#23（成本随改动量）、#26（完整闭环）。
上游基线 4.0.1（`ee4260d8`），**未修改上游代码**。

### 19.1 改了什么

窗口编辑器此前是“每个分组一个 `CodeEditor` + 一个缓冲区，切标签时把整篇文本 `set_text` 进去”。
库的编辑器本来是多缓冲的：`open_buffer`/`activate_buffer_id`/`close_buffer_id`，而
`buffer_summaries` 的文档注释写的就是“宿主标签条需要的东西”。因此改成：

- 新增 `sync_editor_buffers(editor, documents, active, texts)`：
  - 条带里有、编辑器没有的文档 → `open_buffer(文档名, 模型文本)`；
  - 编辑器里有、条带里没有的缓冲区 → `close_buffer_id(id)`（库的规则：关最后一个会清空而不是删除）；
  - 按**id**激活当前文档的缓冲区（前面的关闭只挪位置，不换 id）；
  - 只有模型与活动缓冲区文本不一致时（是命令写了模型，不是人打字）才 `set_text` + `clear_history`。
- `sync_editors` 不再持有“活动文档文本”字段：缓冲区协调需要整条带每个文档的模型文本，因此把
  `(文档 → 文本)` 传进去；`StripState.text` 随之删除（不再有未读字段）。
- **代价与收益**：每份打开的文档在编辑器里各有一份文本（库的每缓冲设计），换来的是每份文档的
  undo 历史与光标/滚动随文档保留；打字路径仍然只读活动缓冲区，成本不随文档数量增长。
- **顺手补上 T06.02 的窗口一侧**：激活缓冲区后按文档扩展名设置库的语言
  （`Language::of_path(...).id()` → `CodeEditor::set_language`），所以窗口里的 `.rs` 现在是库的
  高亮器在画，而不是默认纯文本。宿主 `highlight.rs` 的增量缓存仍只服务 CLI `--highlight`。

### 19.2 验证（真实会话）

`--smoke` 在原有步骤里加了一段“记住 → 切走 → 切回 → undo”，并读回控件状态：

```
INFO …: an editor edit reached the model of src/main.rs (56 -> 64 chars, the model now carries
        the text: true), dirty true, tab Some("• main.rs"), … dialog … dismissed true
INFO …: switched away Some(Ok(())) and back Some(Ok(())), undo said "已撤销最新更改",
        the buffer is 64 -> 56 chars and still carries the text: false;
        surface (buffers, language, text) Some(Some((3, Rust, 56)))
```

## 21. 第十一轮：撤销/重做的可用态与原因（菜单 + 命令面板）

依据：原则 #22「失败必须显式可诊断」、#55（接线/可用是两种状态）、#59（同一概念不得有两条漂移的
路径）、#12（能力以契约为准）；T05.02「菜单禁用原因呈现」、T05.04「禁用原因可查」。上游基线
4.0.1（`ee4260d8`），**未修改上游代码**。

### 21.1 缺口

`edit.undo` / `edit.redo` 一直显示为可用：菜单项从不置灰，命令面板也没有禁用原因；只有在真的执行
之后才由处理器回一句“没有可撤销的更改”。库其实已经给出事实（`CodeEditor::can_undo`/`can_redo`），
宿主没有消费它。

### 21.2 实现

- `src/app/commands/command.rs`
  - `Context` 新增 `can_undo: Option<bool>` / `can_redo: Option<bool>` 与
    `with_history(can_undo, can_redo)`：`None` 表示**调用方没说**，命令保持可用（不凭猜测置灰）；
    `Some(false)` 才是“控件说没有”。
  - `Command` 新增 `needs_undo`/`needs_redo` 标记与 `.needing_undo()`/`.needing_redo()` 构造；
    `Registry::resolve` 在“信任/运行中”之后、效果授权之前检查，拒绝理由分别是
    `the focused editor has nothing to undo` / `…redo`。
  - `built_in()` 的 `edit.undo` / `edit.redo` 打上标记。
  - 新测试 `a_history_command_refuses_only_when_the_editor_says_there_is_nothing_to_do`：
    未知（`None`）→ 可用；两侧 `Some(false)` → 各自拒绝且理由具名；`Some(true)`/`Some(false)`
    混合 → 只拒一半。
- `src/app/run/workbench_gui.rs`
  - `command_context(gui)`：在既有 `palette_context()` 上加 `with_history(...)`，两个值来自
    焦点编辑器的 `can_undo`/`can_redo`；没有编辑器面时仍为 `None`（不猜）。
  - `history_items: Vec<(menu, row, command)>`：`add_menu_leaf` 记账时只记 `edit.undo`/`edit.redo`
    两行（菜单按**行号**启用，行只建一次）。
  - `refresh_history_commands(gui)`：从同一个 `can_undo`/`can_redo` 写菜单行的启用态；在
    `run_call`、`apply_action` 尾部与 `set_document_text`（打字落地）各调一次。
    `MenuHandle` 没有逐行启用入口（`ToolBarHandle` 有），因此按既有模式 downcast 到库的 `Menu`
    调 `set_item_enabled`/`item_enabled`——**同一条事实、同一个来源**，只是调用面不同。
  - `history_state(gui)`：把菜单行状态与命令面板的 `why_not` 一起读出来，只用于 smoke 证据。
