## 这份登记回答什么

白皮书 §8 留下 Q1–Q6 六个悬置问题，§17.7 给出的是**默认建议而非结论**，并明确写着
"特别是 Q2 和 Q3 会影响代码生成与工程工作流，首轮开发前应确认"。本登记做三件事：

1. 把 Q1–Q6 连同工程格式、生成入库、升级策略、组件表达四项策略固定成**可核对的结论**，
   每条都带备选方案、拒绝理由、兼容影响、复核触发、责任归属和受影响任务。
2. 把"不写版本字段""打开即静默升级"这类会让数据静默损坏的做法**显式记入被拒绝的备选**，
   以后有人想改回默认建议时，看到的是理由而不是一条空白。
3. 把不能由实现方代填的身份与发行取值**单独列出并保持未定**，避免用推测值把检查"填绿"。

本登记不回答"哪个决策更好"，也不证明实现已经存在。它只保证：读过它的人能说出每一处
为什么这样定、换方案要付出什么、什么情况下必须回来重看。

### 决策登记

| 编号 | 主题 | 状态 | 决策 |
| --- | --- | --- | --- |
| Q1 | 输出粒度 | ratified | 生成粒度固定为：一个工程一个 Cargo package；每个页面/窗口生成独立模块（一个页面一个文件）；工程入口、共享注册与启动代码集中在固定的一组文件里，不随页面增加而改写。 |
| Q2 | 生成物是否入库 | ratified | 设计 JSON、CSS 与资源入库；生成 Rust 采用确定性输出并纳入版本控制，文件内标出生成器版本、格式版本与受管理区域（生成区由生成器写入，用户手写区不在其中）；打开工程、预览与构建都不依赖设计器本身是否在场。 |
| Q3 | 事件连线范围 | ratified | 首版的事件连线只支持两条目标：类型兼容的控件事件到属性更新，以及类型兼容的控件事件到已声明命令；不支持把任意 Rust 表达式或闭包体写进设计文档。 |
| Q4 | 自定义控件 | ratified | 首版只接受显式注册、并提供属性、事件与目标能力描述的控件；不做动态插件加载（不加载 dylib、脚本或运行时代码）。设计器与生成器都不按控件名称猜构造器或属性。 |
| Q5 | 多窗口/多页面 | ratified | 工程持有多个页面/窗口，工程元数据指定启动入口；页面之间导航使用显式动作或命令，不使用隐式全局切换或隐式「最后打开的页面」。 |
| Q6 | 格式迁移 | ratified | 工程文件必须带格式版本；打开旧版本时先执行有版本号的迁移，再校验并展示迁移结果；遇到高于当前或未知的格式版本时拒绝写入（只读打开并说明原因）；迁移前不原地覆盖原文件。 |
| F1 | 工程格式（结构策略） | ratified | 工程格式采用单一工程根目录：设计源为 JSON（工程元数据加每页一份页面文档）加 CSS 样式表，资源保持为工程内原始文件；所有路径以工程根解析，越出工程根的引用被拒绝；文档模型必须能表达工程标识与格式版本、页面/窗口入口、资源引用、目标 profile 配置，以及生成文件与设计源的对应关系；未知字段保留并报告，不静默丢弃。 |
| F2 | 生成入库策略（目录与门禁） | ratified | 生成 Rust 固定写入受管理目录（约定 `src/generated/`），每个受管理文件带生成器版本与格式版本标记；用户手写内容位于不被生成器写入的目录（约定 `src/handwritten/`）；相同输入、目标与生成器版本必须产出字节相同的输出；CI 需要一条「重新生成后无 diff」的门禁。 |
| U1 | 升级策略与选项 | ratified | 两条升级轴分别固定：(a) 工程格式只做前向迁移，按版本号逐步升级并记录迁移结果，不提供降级写入，旧设计器打开新格式时只读拒绝；(b) rust-widgets 依赖固定到具体 git 修订（当前 c957fdec7f30cc1a526b7c898c0f44b458ef4a57，见探针报告），升级流程为改修订、重跑契约探针、更新支持矩阵证据、再记录影响。 |

### 备选与拒绝理由

| 编号 | 备选 | 拒绝理由 |
| --- | --- | --- |
| Q1 | 每个控件一个 .rs | 文件数与模块噪声随控件数量线性增长，编译单元碎片化，diff 与错误定位反而变差。 |
| Q1 | 全工程输出到单个 .rs | 任何改动都造成整文件重写与合并冲突，错误只能定位到一个巨型文件，增量编译收益消失。 |
| Q2 | 生成物不入库，构建时由生成器产出 | 构建依赖设计器在场，评审看不到生成 diff，CI 无法在无设计器环境复现；生成器故障会直接变成构建故障。 |
| Q2 | 生成物入库但不标受管理区域 | 无法区分机器写入与用户修改，回写时会覆盖用户文本，违反 §12.5.1 生成区保护与原则 #6。 |
| Q3 | 允许在文档中写入任意 Rust 表达式片段 | 文档变成代码：无法做类型校验与能力预检，迁移与源映射失去稳定单元，安全与可审查性下降。 |
| Q3 | 只支持事件到属性更新，不支持命令 | 提交、导航一类常见交互没有表达方式，会迫使首版就用表达式兜底；白皮书 §17.7 已允许已声明命令。 |
| Q4 | 按 rust-widgets 控件名直接生成构造调用 | 属性面板与生成器必须推断构造器签名与可设属性，等于维护一份会漂移的平行实现。 |
| Q4 | 支持动态插件加载第三方控件 | 需要同时解决 ABI 稳定性、版本匹配、权限与崩溃隔离，首版无法给出可验证的边界。 |
| Q5 | 首版只支持单窗口单页面 | 真实应用几乎都是多页，后续引入会同时改动格式与生成布局，代价比一开始就留出页面边界更高。 |
| Q5 | 每个窗口作为独立工程 | 样式、资源、命令与注册表需要跨工程同步，直接破坏单一事实来源。 |
| Q6 | 不写版本字段，按字段存在性探测 | 无法区分「用户没设」与「旧格式没有这个字段」，迁移会静默丢字段或写错默认值。 |
| Q6 | 打开即静默升级并在保存时覆盖 | 用户无法察觉数据已被改写，也没有回滚点；一旦迁移判断错误就丢失原始数据。 |
| F1 | 单一巨型 JSON 存整个工程 | 页面级 diff 与局部校验失效，单页解析错误会波及整工程，且并发编辑合并代价高。 |
| F1 | 自定义二进制或数据库存储 | 不可审查、不便 diff 与合并，与 §17.3「可审查的设计源文件」目标冲突。 |
| F1 | 把控件树、布局与事件写进 CSS | CSS 只负责外观；§17.3 已明确排除，混写会让类型校验与源映射失去稳定单元。 |
| F2 | 构建期写入 OUT_DIR | 构建依赖设计器，实现与评审都不透明，且生成结果无法被 review 或 diff。 |
| F2 | 生成物与手写文件同目录混排，仅靠注释标记边界 | 边界只存在于注释里，一旦标记被手工删除或改写就会覆盖用户内容，缺少结构性护栏。 |
| U1 | 依赖使用 semver 范围而非固定修订 | 库仍在演进，范围会让同一份源码在不同时间构建出不同行为，已验证的契约结论会静默失效。 |
| U1 | 跟踪上游分支或最新提交 | 构建不可复现，探针与矩阵证据无法指向确定版本。 |
| U1 | 格式支持降级写入旧版本 | 降级意味着丢弃新格式数据或伪造默认值，属于静默数据损坏，直接违反 §17.9。 |
| C1 | 文档直接存 Rust 构造代码片段 | 不可校验、不可迁移，属性面板无法反向驱动，等价于把用户代码当数据。 |
| C1 | 自研面向控件的 DSL | 多出一套需要长期维护、解析并经编译验证的语法，与「复用运行时契约」冲突。 |
| C1 | 直接用 rust-widgets 的声明式视图宏作为持久格式 | 声明式视图特性尚未提供稳定 ID、逐节点位置与迁移能力，作为持久格式会立刻缺三件事；记录为「未来可评估」，不作为首版依赖。 |

### 兼容影响与复核触发

| 编号 | 兼容影响 | 复核触发 |
| --- | --- | --- |
| Q1 | 生成模块路径成为稳定契约：页面重命名或移动属于破坏性变更，必须走迁移并重新生成；页面与模块一一对应，不允许把两个页面合并进一个模块来规避冲突。 | T15.01/T15.07 在 T00.07 的基准工程上测到页面级模块带来无法接受的编译或 diff 代价时。 |
| Q2 | 生成器版本或格式版本变化会造成大面积 diff，提交信息必须写明生成器/格式版本；CI 需要一条「重新生成后工作区无 diff」的检查（归属 T16.11），否则入库的生成物会与生成器漂移。 | 生成输出进入稳定期（P4 之后）或生成文件体积造成可核实的仓库成本时，重新评估是否改为导出式提交。 |
| Q3 | 事件签名与命令清单必须来自能力/命令注册表，连线保存引用而不是名字字符串；注册表删除或改名条目属于破坏性变更，需要迁移条目而不是静默丢弃连线。 | T00.06 的旅程走查或 T13.03/T13.04 落地时出现必须以表达式才能表达的交互，且该交互属于首版范围。 |
| Q4 | 控件描述新增必填字段时，旧工程缺少描述，必须走迁移补描述或报告缺失，不得用默认值悄悄补齐；注册表条目是控件可用性的唯一权威。 | 出现外部控件作者需求，且 ABI、版本匹配与崩溃隔离策略可验证之后。 |
| Q5 | 页面 ID 与启动入口字段属于格式 v1，页面类型的增加需要迁移；导航动作引用页面 ID，删除页面必须报告悬空引用而不是静默删除。 | 出现需要并行打开、各自独立生命周期窗口的场景，且当前单入口模型无法表达时。 |
| Q6 | 每次格式变更都要附带一个带版本号的迁移步骤与可重复测试；「未知版本拒绝写入」是格式 v1 的行为约束，不是可配置项。 | 无（长期约束）；随格式版本增加而扩充迁移步骤清单。 |
| F1 | 路径解析规则（相对工程根、越界拒绝）与未知字段保留策略属于格式 v1 的行为；字段增删必须通过格式版本与迁移表达，不得靠「读不到就用默认」实现。 | T02.01 落地时以真实 schema 细化本策略（细分不等于推翻本条目）。 |
| F2 | 目录约定与版本标记是生成器的稳定接口；改变生成区路径或标记格式需要迁移与全量重生成，并会让手写区引用路径失效。 | T15.01/T15.07 落地时若真实工程需要把生成物放到 package 之外的布局（例如多 package workspace），重新评估目录约定。 |
| U1 | 依赖修订写入 Cargo.lock 与探针报告，两者必须一致（已有漂移测试）；更换修订后，未重跑探针的结论按过期处理，不得继续引用。格式迁移步骤一旦发布即为兼容契约，修改需新增迁移版本。 | 上游发布带兼容承诺的稳定版本时；或探针出现缺口需要上游修订时。 |
| C1 | 属性 schema 是文档与生成器之间的契约，变更需要版本化迁移；注册表是可用性权威，生成器不得在注册表之外推断控件属性。 | 声明式视图特性成熟到能承担文档格式（含稳定 ID、逐节点位置与迁移）时，重新评估是否以它作为另一条表达路径。 |

## 怎么改一条决策

1. 改 [`decisions.json`](decisions.json)，不要只改本文件：本文件的表格由检查脚本对照 JSON。
2. 若该条是白皮书 §17.7 的悬置问题，同时改白皮书的结论表（摘要、状态两列必须与 JSON 一致）。
3. 新决策必须写明备选与拒绝理由；没有备选的"决策"只是偏好，会被检查拒绝。
4. 状态从 `provisional` 变为 `ratified`（或反向）时，必须同时更新白皮书 §17.7 的状态列。
   状态为 `provisional` 的条目在依赖它的第一项实现落地前可被项目方推翻；推翻时先改 JSON，
   再改本文件与白皮书，不允许只改一处。
5. 删除一条决策不是修改方式：旧结论改为被新条目取代，并写明兼容影响和迁移路径。

## 未覆盖项与责任人

- **实现侧未覆盖**：本任务只登记决策，没有任何生成器、迁移器或控件注册表被实现。依赖这些
  决策的落地任务见「影响任务」列（T02.01、T15.01、T13.03、T12.04、T25.03 等）。
- **只有趋势、没有测量**：Q1 与 Q2 的"代价更小"来自结构性推理（页面边界、可审查 diff），
  不是基准数据。真实代价必须在 T00.07 的基准工程上测量；测量结果推翻推理时按复核触发改进。
- **责任人**：决策条目由实现方按上文证据提请登记并负责维护一致性；`openDecisions` 中的
  条目只能由项目方给出取值（见该表的归属列）。
- **未验证就写下来的部分**：U1 提到的"重跑探针后结论才继续有效"依赖 T00.01 已建立的探针
  与漂移测试，那部分是**已验证**的；但"升级流程整条走过一遍"还没有发生过，因此 U1 的流程
  是登记的策略，不是已执行的记录。
