# 设计器项目原则

> 本文是设计器项目的长期约束与评审准则，依据 [`whitepaper.md`](whitepaper.md) 整理。
> 白皮书仍标记为草案；本文不把白皮书中尚未决定的选项冒充为既定产品决策。
> 本文面向设计器宿主、文档模型、预览、生成器及其代码视图，不替代 rust-widgets
> 自身的实现规范。

## 一、产品边界与设计依据

1. **先明确产品是什么**：本项目是运行在桌面宿主上的可视化 UI 设计器，消费 JSON
   结构与 CSS 样式，面向 rust-widgets 生成可编译的 Rust UI 代码；它不是目标应用的
   运行时，也不要求在 mini 或 embedded 设备上运行。
2. **区分宿主与生成目标**：设计器宿主始终是桌面环境；desktop、tablet、mobile、
   mini、embedded 是输出目标 profile。不得把生成目标的限制误当成设计器自身的运行限制。
3. **以白皮书已定约束为准**：白皮书中的目标、架构和硬约束作为设计依据；标为“尚未
   确定”或“建议”的事项，在作出实现依赖前必须先形成明确决策并同步白皮书。
4. **只做设计器需要的能力**：代码编辑器、终端或其他组件服务于设计、生成、诊断闭环，
   不以复刻通用 IDE 或堆叠控件数量为目标。

## 二、文档模型与预览

5. **结构与外观分离**：JSON 表达控件结构、属性及层级关系；CSS 表达外观。不得把布局
   结构塞进 CSS，也不得用 CSS 选择器取代文档模型中的结构关系。
6. **文档模型是唯一事实来源**：画布、对象树、属性面板、预览、生成器和代码映射均从同一
   有效模型派生；不得维护彼此可独立修改、会漂移的状态副本。
7. **反馈快速且不依赖构建**：结构或样式的有效修改应尽快更新开发期预览；模式 1 的预览
   更新不得为每次修改启动 `cargo` 编译。
8. **预览必须诚实**：明确显示当前 profile、窗口尺寸及预览与真实目标的差异。目标不支持的
   控件、属性或行为须在设计阶段给出诊断，不得用模拟成功掩盖目标构建失败。
9. **无效编辑不得污染有效模型**：JSON、CSS 或属性值解析/校验失败时，保留用户正在编辑
   的文本并指出错误位置；不得覆盖最近一次有效模型、回退到空文档或静默忽略输入。
10. **用户操作形成完整事务**：节点使用稳定 ID；添加、删除、移动、属性修改等操作应作为
    可审阅、可撤销的变更提交。一次操作失败不得留下半完成状态；相关引用受影响时须告知。

## 三、profile 与生成

11. **保留两种产物模式**：
    - 模式 1：开发期使用 JSON + CSS 运行时加载，以快速反馈为目标，仅适用于
      desktop/tablet/mobile。
    - 模式 2：生成 Rust 源码，需重新编译，适用于全部 profile；mini 和 embedded
      必须使用此模式。
    不得为了单一模式而牺牲另一模式各自解决的问题。
12. **目标能力以实际契约为准**：控件、属性、事件及资源可用性应由目标 profile 的能力
    描述/注册表查询；不得在设计器另维护会漂移的名称清单，也不得仅凭名称推断构造器存在。
13. **生成前完成目标约束检查**：按目标查询控件可用性；在生成期解析并内联 CSS；使用
    rust-widgets 的 `Layout` 契约计算静态布局；检查目标容量。无法满足约束时必须阻断
    生成并说明原因，严禁静默丢弃控件或属性。
14. **布局不得分叉**：设计器预览和生成结果必须复用 rust-widgets 的布局语义，不得自行
    实现一套相似但独立的布局算法；尺寸/位置交互无法表达为当前布局约束时应明确提示，
    不得悄悄改成绝对坐标布局。
15. **生成物必须干净、可编译**：生成的 Rust 应能按所选目标实际构建，不要求设计器运行时
    参与交付；mini/embedded 产物不得依赖 JSON/CSS 运行时或目标 profile 中不存在的能力。
16. **生成保持确定且增量**：固定输入、目标及生成器版本应产生稳定输出；输出顺序、格式化
    和节点到源码位置的映射应可复现。仅改动必要区域，不得无理由全量重写生成物。
17. **事件必须有类型契约**：供属性面板、连线、JSON 持久化和生成器消费的事件描述必须包含
    载荷类型等可校验信息；事件名称合法不代表它已接线或一定触发，状态不得伪装成成功。

## 四、编辑、合并与 AI 协作

18. **代码视图是设计器视图，不是通用 IDE**：优先实现能解释、检查和定位本设计器生成物的
    能力。语言服务、文件系统、工程管理、进程管理及外部工具集成属于宿主，不塞进只负责
    文本呈现和编辑的 widget。
19. **保护生成区域**：生成区只读；仅显式声明为可编辑的手写区域允许直接修改。JSON/CSS/
    Rust 编辑产生的模型差异须经校验和合并；无法识别或发生冲突时应展示差异并允许取消，
    不得覆盖用户文本或静默丢弃变更。
20. **AI 是可选参与者**：不启用 AI 时，人工设计、预览、生成和构建流程仍须完整可用。
    若接入 agent，其输出应是可审阅、可回滚的结构化变更集；权限仲裁、确认和文件落盘由
    确定性宿主逻辑控制，不能交给模型自行决定。
21. **区分视图与系统能力**：设计器 widget 负责呈现与局部交互；工程状态、持久化、LSP、
    构建进程、agent 网络调用和文件写入由宿主统一管理。不得在视图组件中重复实现宿主系统。

## 五、可靠性与工程质量

22. **失败必须显式可诊断**：解析、校验、资源加载、能力查询、生成、构建、启动和取消均
    应呈现可区分的状态及上下文。禁止用空内容、过期结果、硬编码能力值或成功形状的默认值
    掩盖失败。
23. **成本随可见工作量增长**：每帧绘制成本应与视口相关，而非与整个文档长度相关；一次
    编辑的工作量应与改动范围相关，而非每次扫描或克隆整篇文档。大型文档须使用缓存、
    增量更新和可见的分级降级。
24. **用目标构建验证兼容性**：profile 兼容性须通过对应目标的实际构建或测试验证，验证命令
    应与项目 CI 的 feature/profile 组合一致。模拟、静态清单或宿主预览不能替代目标构建证据。
25. **每项结论附可复核证据**：修复或能力声明应由相关测试、构建、运行结果或代码路径支持；
    说明验证覆盖了什么以及未覆盖什么。不得声称未经验证的支持，也不得为通过验证而删除、
    忽略失败测试。
26. **优先完整闭环而非占位**：新增能力应贯通文档模型、界面、校验、生成/运行和测试中
    适用的各环节。不得留下空函数、仅有日志的实现、无消费者的迁移代码或没有可观察行为的
    “假修复”。
27. **保持文档与实现一致**：设计变更、profile 支持范围、限制和验证结果应同步到相关文档；
    白皮书中的现状数据和“已具备”陈述必须注明证据或明确标为计划/建议。

## 六、仍需决策的事项

以下事项在白皮书中仍属悬置问题或建议，不由本原则擅自定案：生成输出粒度、生成物是否入库、
事件连线可调用的目标、自定义控件范围、多窗口/页面模型及具体格式迁移策略。实现若依赖其中
任一选择，应先记录决策，再更新白皮书和相关验收标准。

## 七、继承的 rust-widgets 实现规则

> 本节保留上游 [`rust-widgets/docs/plans/principle.md`](https://github.com/mikewolfli/rust-widgets/blob/main/docs/plans/principle.md)
> 中与设计器集成、所依赖控件库及其目标 profile 有关的约束。凡涉及库内实现的规则，
> **仅在修改或评审 rust-widgets 对应实现时适用**；不要求设计器宿主复制库内机制。
> 括号中的编号对应上游原则编号，便于追溯。上游于 2026-10-13 修订了 #21（向前兼容）
> 并新增 #102–#106（验证预算、宿主限制与状态口径）；修改或评审 rust-widgets 实现时
> 以最新上游原则为准，本节摘要不替代上游原文。

### Rust 实现与 API 约束

28. **零成本抽象优先**（上游 #28）：能用 enum、trait 或泛型清楚表达的问题，优先使用静态
    分发；确有插件、异步或运行时异构需求时可用动态分发，不为模仿其他 UI 框架而引入开销。
29. **尽可能在类型层表达约束**（上游 #29、#34）：样式、布局、事件路由等优先利用类型系统
    检查；可能失败的属性设置须采用显式错误结果，不得静默忽略非法值。
30. **内存管理遵循 Rust 所有权**（上游 #30）：不用手动 `alloc/free` 模式；根据共享和生命周期
    需求选择所有权、`Box`、`Rc`、`Arc` 或适用于目标的静态分配方案。
31. **用类型化数据表达多态**（上游 #31）：避免 `void*` 与手动类型标记；适合的场景使用
    Rust enum 与模式匹配。
32. **API 优先使用具名参数/Builder**（上游 #32）：避免以无类型、难扩展的参数簇表达复杂配置；
    简单且稳定的操作不为套用模式而强行引入 Builder。
33. **事件处理优先保留类型与可读性**（上游 #33）：避免难以审计的裸函数指针回调；选择
    trait、闭包或类型化事件机制时，以现有库契约和实际所有权需求为准。
34. **向前兼容**（上游 #21，2026-10-13 修订）：公共 API 优先通过新增 API、模块或 feature
    引入变化；破坏性变更须有明确迁移理由和方案。下列情形允许破坏性变更——① 删除同一
    概念的第二条实现路径（见第 59 条）；② 用稳定身份取代位置寻址；③ 消除已具名隐患或
    新增可读能力——但须同时满足：有实测收益证据并写明边界、仓库内调用方逐处核对、
    迁移说明写明新旧形态、相关门控与测试同步更新。已发布且下游未知的接口不适用该例外；
    不以兼容为由保留无效或误导性行为。
35. **同一语义只保留一份定义**（上游 #54）：跨层共享的枚举、事件或能力描述应复用同一类型，
    不复制相同变体集合再要求调用方转换。
36. **公开 API 描述意图，不暴露内部实现机制**（上游 #52）：在控件库公开 API、handle、
    平台 trait 和 demo 中，名称描述用户要执行的动作，不泄漏 native/self-drawn 等实现选择。
37. **能力缺失不制造虚假 API 分叉**（上游 #41、#53）：公共操作应保持语义一致；平台能力差异
    通过统一能力查询与明确错误表达，不维护两套含义相同、仅因平台而分叉的签名。
38. **共享抽象须有实际收益**（上游 #51）：引入共用引擎或适配层前，先检查重复行为与成本；
    若不能消除真实重复，应保留简单实现并记录分层原因。
39. **同名异层类型与消费者须可辨认**（上游 #49）：模块文档说明各层类型职责；无消费者的
    代码不得仅因名称相似而长期保留为“备用实现”。

### 控件库与平台边界

40. **控件实现先补基础设施**（上游 #22–#27）：新增 `WidgetKind` 前确认存在对应实现或明确
    alias；避免语义/大小写重复；基础设施缺失时先补基础设施。每个 kind 到模块文件的映射应唯一、
    可审计；native FFI 必须在 platform implementation 中实际调用，IME 必须落到真实 OS API，
    不得以日志占位。
41. **平台策略由控件库封装**（上游 #4）：调用方描述所需能力，不决定原生控件或绘制承载面的
    具体机制；映射与机制选择属于控件库 platform backend。
42. **操作系统差异留在平台后端**（上游 #35–#39、#41）：修改 rust-widgets 时，上层控件、
    app、layout、render、style、theme 和 core 不得自行按 `target_os`、`target_family`、`unix`
    或 `windows` 分支，也不得导入平台原生类型；OS 相关实现集中在 platform backend，并通过
    `Platform` trait 的语义化方法提供。新增平台事实必须由后端实现或显式采用诚实的默认值
    （如 `Option::None`/`false`），不得用硬编码假值掩盖缺失实现；原生类型由后端持有。能力差异
    用统一运行时查询表达，不以 `cfg(target_os)` 声明公共函数是否存在。
43. **绑定层只做平台无关转发**（上游 #40）：C ABI、JNI 等边界可依赖绑定库，但不得内嵌 OS
    探测或平台分支；只转发到平台无关的控件库 API。
44. **架构门控表达执行环境，不替代 OS 判断**（上游 #42）：`cfg(target_arch)` 仅用于确由
    架构决定的约束；不得将同一事实再以 `target_os` 判断。
45. **平台探测必须验证真实语义**（上游 #37–#38）：不硬编码未实现的系统能力；默认值须诚实。
    以外部命令探测时，应区分“命令可启动”和“命令成功完成”等判据，并在目标环境验证。
46. **平台原生类型不泄漏到上层**（上游 #39）：原生对象由后端持有和创建；上层只依赖语义化
    trait/接口，不把原生窗口或控件句柄存进通用 widget 类型。
47. **交叉目标依赖在 Cargo target 配置中声明**（上游 #43）：先核对依赖实际版本与 feature
    名称；采用目标专属依赖配置并实跑目标构建，同时确认 CI 覆盖该 feature 组合。
48. **使用跨平台路径 API**（上游 #44）：配置、数据、缓存和临时路径采用适用的跨平台 API；
    不手拼 `.config`、`/tmp` 或路径分隔符。测试夹具等明确限定场景可例外。
49. **GPU 降级可见且遵从用户 pin**（上游 #45–#46；仅在修改 GPU/backend 选择时适用）：
    依次尝试 PRIMARY（Vulkan/Metal/DX12/WebGPU）、GL（OpenGL ES/WebGL/ANGLE）、CPU 软件回退，
    只有末级允许强制 fallback adapter；报告实际选择的 tier，非 PRIMARY 时明确告警。尊重
    `WGPU_BACKEND` 等显式选择，按 pin 过滤 adapter；pin 不可用时返回包含 pin 值的错误，不得
    静默切换。创建 instance 时须开放降级阶梯与 pin 的并集，保证各级路径仍可达。

### Profile、事件契约与互操作

50. **profile 条件使用统一别名**（上游 #47）：当 rust-widgets 需要表达“有完整 device
    profile 且非 mini/embedded”等组合能力时，复用 `build.rs` 定义并由 `cargo:rustc-check-cfg`
    声明的 cfg 别名（如 `full_widgets`），不在各处复制易漂移的合取表达式；不得用
    `not(any(mini, embedded))` 代替含义更窄的别名。
51. **目标验证命令与 CI 对齐**（上游 #48）：验证单一 profile 时使用项目规定的互斥 feature
    组合（例如 `--no-default-features --features <profile>`）；避免把默认 feature 与目标 feature
    叠加成不存在的配置。
52. **适配器显式处理单位与边界值**（上游 #50）：跨几何/绘制 trait 转换时使用明确舍入规则
    （例如 `round()` 而非截断），亚像素尺寸钳制到最小可见值，退化输入有明确定义且不 panic；
    缺少原生图元时采用精度随尺寸调整的近似绘制，并以测试验证。
53. **事件契约必须包含载荷类型**（上游 #95）：设计器消费的事件元数据不能只有事件名；声明
    的载荷类型须与实际信号类型一致，并可由自动检查逐项验证。
54. **设计器消费的能力描述必须可往返**（上游 #96）：控件、属性、事件、命令等序列化后可
    重新载入，往返语义一致；测试覆盖完整清单，并验证规范化后的序列化稳定。
55. **接线合法与接线生效是两种状态**（上游 #97）：合法事件名不等于存在订阅者或事件会触发；
    API、诊断或查询结果须能表达未接线状态，不得将其报告为成功送达。
56. **运行时事件转发由库契约支持**（上游 #98）：若连线在运行时才确定，控件库需提供统一、
    可组合的事件接线能力；不得要求宿主为每种控件和每个事件手写转发代码。
57. **镜像状态字段必须有实际用途**（上游 #99）：平台状态镜像中的字段要么作为平台读取
    不可用时的真实回退被生产代码读取，要么删除；不得保留无人读取、可能漂移的副本。
58. **设计器就绪度以可核验数据衡量**（上游 #100）：报告已类型化、可接线、不可表达的控件/
    属性/事件数量；不可表达项逐条列出原因，不以“基本完成”等印象替代。
59. **同一设计器概念不得有漂移的平行路径**（上游 #101）：JSON 事件、能力表、生成器等若
    表达相同概念，应先取证，再合并或写明职责边界，并以测试/门禁防止其中一路静默落后。

### 工程工作流与验证纪律

60. **按证据修复并扫描同类问题**（上游 #1–#3、#16、#19）：结论须有代码、测试、构建或运行
    证据；修复后检查同类路径；优先处理阻断闭环的问题；每项修复须独立验证。
61. **禁止占位、假修复和无效迁移**（上游 #5、#12–#18）：新增/迁移实现须有可观察行为、
    真实调用路径及清晰文档；完成迁移后移除失效旧路径，不以日志或空函数冒充实现。
62. **测试失败不得被掩盖**（上游 #11、#15）：不得为消除失败而跳过、忽略或删除仍然有效的
    测试；如测试目标确已删除，须同步移除其失效测试并说明原因。
63. **代码约定按修改范围执行**（上游 #6、#8–#10）：Rust 注释使用英文；每个源文件带有
    版权标识（项目统一 SPDX/版权头部）；`mod.rs` 保持模块声明/导入等薄职责；文件拆分基于
    职责而非机械行数，少于 2000 行的文件通常不因计划表而拆分，除非确有结构重组需要；
    收尾清理发现的 warnings 与 errors，并区分本次引入和既有问题。
64. **新增控件考虑目标适配**（上游 #20）：新增通用控件时评估 desktop/tablet/mobile 的
    布局与交互；不支持的目标须明确标识，不把仅桌面实现宣称为全 profile 支持。
65. **命令必须有界且验证范围适当**（上游 #55–#60）：可能阻塞的构建、测试、门禁、交叉编译
    命令设超时；优先运行覆盖本次变更的最小验证，最终验证再按风险扩大。长循环逐项报告进度，
    不串行裸跑大批门禁；超时须标为“未完成”，不能视为通过或缺陷结论。
66. **进度记录服务于当前协作流程**（上游 #7）：多阶段工作按项目约定记录完成状态；记录应
    反映真实进展，不得用虚假的完成率代替验证结果。

## 八、界面语言与本地化

67. **界面多语言，默认跟随系统**：设计器界面支持多语言，启动时默认跟随系统语言；开发
    阶段仅随宿主提供简体中文与英文语言包，其余语言按发布计划追加，不在首版冒充已支持。
    语言切换只影响界面文案与方向相关语义，不改变文档模型、资源身份或生成产物；生成应用的
    语言资源与宿主界面语言分开管理（见路线图 F24 与 T24.03/T24.04），不把换宿主语言当作
    应用资源已翻译。
