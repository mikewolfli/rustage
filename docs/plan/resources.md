## 1. 推荐结论

**最适合当前项目的方案不是下载一整套图标放进源码目录，而是：**

1. **宿主常用图标优先复用 rust-widgets 内置 Material Symbols 轮廓。**
2. **rustage 用自己的稳定语义 ID 引用图标，不让界面代码依赖文件路径或上游枚举序号。**
3. **少量产品专用图标由 rustage 管理，SVG 为编辑源，构建工具生成可验证的渲染数据。**
4. **宿主资源、用户工程资源、品牌母版、平台派生产物四者隔离。**
5. **发布宿主的核心 UI 资源内嵌；操作系统图标通过平台打包流程安装。**
6. **用户工程资源按白皮书两种产物模式与目标能力选择运行时加载、静态嵌入或外部打包；
   同一逻辑资源身份不绑定单一物理交付方式。**
7. **主题、DPI、状态、RTL、无障碍、许可证、缓存及测试是同一个闭环，不是后补事项。**

“最优”以当前库契约、可维护性、跨平台一致性和真实验收为条件；不存在不用测试即可保证
所有平台、所有图标、所有缩放下都完美的方案。本文选择低重复、低运行成本、失败可诊断的
默认路线，并区分已具备的上游通道与仍需宿主实现的资源闭环，不为未来扩展提前堆砌框架。

### 1.1 格式选择：按消费端决策，不把 ICO 与 SVG 当作替代品

ICO 与 SVG 解决不同问题。SVG 适合作为可编辑的矢量母版；ICO 是 Windows 应用/文件图标
打包格式，常包含多个尺寸的光栅图像。SVG 冷加载通常需要解析和栅格化，ICO 也不因此成为
所有控件的最快格式；真实耗时取决于解码器、缓存、尺寸和消费 API，必须按目标测量。

| 消费场景 | 首选来源/运行表示 | 原因与边界 |
|---|---|---|
| rustage 常用单色 UI glyph | rust-widgets 内置 `IconSource::Builtin` | 无资源文件读取；仍有绘制成本，不能未经测量声称零成本 |
| 少量自有静态单色 glyph | SVG 编辑源；验证后生成静态几何数据 | 绘制时不解析 SVG；仅限转换保真且满足上游几何/容量契约 |
| 用户导入的多色/照片类资源 | 保留原始工程文件；经受限解码生成目标像素或打包资源 | 像素通道仅用于实际支持它的控件；不强制转成单色轮廓，格式/尺寸/目标能力须校验 |
| Windows/macOS/Linux/鸿蒙 应用图标 | 品牌母版派生成 `.ico` / `.icns` / PNG（鸿蒙另需分层前景与背景，及适用的 SVG） | 按平台打包与安装规范交付，不拿 `.ico` 作为通用 UI 资源 |

运行时不得在绘制循环解析 SVG、读取原始文件或启动转换器。SVG 的解析/栅格化应发生在
受限导入、预生成或缓存填充阶段；是否预热、缓存何种像素尺寸由实际控件 API 和测量结果决定。

### 1.2 今天应该放在哪里

| 内容 | 推荐位置 | 是否提交 Git |
|---|---|---|
| 库已经提供的图标 | 继续留在 rust-widgets，rustage 只保存映射 | 不复制上游 SVG/路径表 |
| 宿主语义映射及自有图标清单 | `resources/host/icons/manifest.json` | 是 |
| rustage 自有 UI 图标 SVG | `resources/host/icons/custom/` | 是 |
| 额外引入的第三方 SVG 子集 | `resources/host/icons/vendor/<provider>/` | 是，来源和许可齐全 |
| 产品 logo、应用图标矢量母版 | `resources/branding/` | 是 |
| 图标许可证和来源记录 | `resources/licenses/`、清单中的 provenance | 是 |
| 用户工程图标 | 用户工程根目录的 `assets/icons/` | 由用户工程自己的 Git 管理 |
| 用户工程资源清单 | 用户工程根目录的 `assets/manifest.json` | 同上 |
| Windows/macOS/Linux/鸿蒙 图标生成结果 | `target/resources/package/<platform>/` | 默认否，进入发行包 |
| 宿主图标表（`&'static IconData`） | `src/resources/generated_host_icons.rs` | 是，由工具生成并由校验器逐字节把关 |
| 其他构建期 Rust 表与派生数据 | Cargo 的 `OUT_DIR` | 否 |
| 用户工程缩略图/转换缓存 | 用户工程的 `.rustage/cache/resources/` | 否 |
| 主题角色图例（评审用色板） | `resources/host/icons/theme.json` | 是，明确标注为建议 |
| 主题矩阵/联系表等评审图 | `target/resources/reports/` | 否，属派生产物 |
| 图标视觉基线 | `tests/baselines/icons/` | 是，审核后更新 |

宿主源目录与清单已按上表建立（2026-10-13）；`target/` 下的派生产物仍按默认不入库，
用户工程的 `assets/` 由用户工程自行管理。项目绝不能依赖 `/Users/mikewolfli/Desktop/workspace/rust-widgets`
这样的个人绝对路径才能运行；依赖以 git 修订固定（§7.5），该目录仅是核验上游实现的本地来源，
仓库内的 token 快照（`resources/host/icons/upstream-tokens.json`）保证校验与构建不需要该目录。

**为什么宿主图标表落在 `src/` 而不是 `OUT_DIR`。** 依赖的图标 API 取 `&'static IconData`，
所以自有拓扑必须在 `cargo build` 之前就是 Rust 源码。两条看似更贴合上表的路线都被排除：
在 `build.rs` 里调用 Node 会让每次构建依赖一个 crate 本身不需要的工具链，也违反"普通构建
不要求桌面工具"；在 Rust 里再写一份子集解析与 stroke 展开，则是同一份几何的第二个定义
（原则 #35）。因此该表是**提交的、可审阅的生成物**：生成器写它，校验器逐字节重建比对
（§16.3），源清单与 SVG 仍是唯一真源。`OUT_DIR` 仍适用于纯构建期产物。

### 2.2 最容易选错的三条路线

**错误一：拿任意 SVG 提取 `d`，调用 `register_icon_on_grid(..., 24)`。**

这个 API 的 grid 只解决缩放，绘制坐标仍使用：

```text
device_x = origin_x + x * size / grid
device_y = origin_y + (y + grid) * size / grid
```

普通 `viewBox="0 0 24 24"` 的源，转换后应满足 `y' = y - 24`。
不是 `y' = -y`，也不是仅修改 viewBox；曲线控制点、相对命令、变换和弧命令必须由
真正的 SVG 几何转换器处理，不能用正则替换数字。

**错误二：选择描边图标库后直接注册路径。**

很多线性图标依赖 `fill="none"`、stroke width、linecap、linejoin；
当前图标轮廓绘制是填充路径。直接提交中心线会变成错误填充或完全不可见。
要么构建时将 stroke 展开为封闭填充轮廓并验证，要么走 SVG/图片通道。
本项目因此默认复用当前 Material Symbols outlined，不混入另一套描边风格。

**错误三：把所有用户资源注册成全局静态图标。**

注册表只有 16 槽、没有工程身份隔离、不能用于大量动态资源；
持续 `Box::leak` 名称/路径会让热更新不断泄漏。用户资源应由资源解析和缓存服务管理，
不进入宿主全局注册表，也不能在关闭工程时清空整个注册表影响其他窗口。

## 3. 四层资源边界

### 3.1 宿主 UI 图标

表示 rustage 自身的保存、撤销、预览、对齐、诊断、构建等命令。
跟随宿主版本发布，通常单色、可着色，用户工程不允许覆盖。
已有上游图标只引用；自有图标只补语义缺口。

### 3.2 产品品牌与操作系统图标

包括产品 logo、启动器图标、安装包图标及将来的工程文件类型图标。
多色品牌资源保持原色，不能当成菜单单色 glyph 随文字颜色重染。
系统图标的规范、尺寸和安装位置与 GUI 控件内图标分开管理。

### 3.3 用户工程资源

是用户设计应用的内容，包括图标、照片、字体和插画。
由工程资源清单、导入事务、逻辑 ID 和目标配置管理。
不因 rustage 更新而改变用户图标，也不自动把宿主图标整套打进用户应用。
资源 ID、文件名与图标语义不嵌入界面文案；确需按语言变化的图片，应建模为显式变体，
不通过改名或替换稳定 ID 隐式切换。开发阶段宿主界面仅提供简体中文和英文语言包，默认
跟随系统语言；其回退与切换按原则及 T24.03 执行。生成应用的语言资源属于独立产品边界，
按 T24.04/T24.10 处理。RTL 镜像也是独立的图标语义/方向策略，不等于语言变体。

### 3.4 派生物和缓存

是对母版或原文件的确定性转换：轮廓表、缩略图、PNG、ICO、ICNS、目标像素数据等。
可重建、可失效，不是事实来源；不能让用户编辑缓存替代源文件。
发布派生物附工具版本、输入摘要和目标参数。

## 4. 推荐目录结构

```text
rustage/
├── resources/
│   ├── host/
│   │   └── icons/
```

## 5. 图标选型、视觉规范与来源

### 5.1 默认风格

| 类别 | 默认处理 |
|---|---|
| 常用命令、状态、导航 | 上游已有 Material Symbols outlined |
| 设计器专用概念 | 自制与既有图标视觉重量一致的单色封闭轮廓 |
| 品牌与系统应用图标 | 自有多色 SVG 母版及小尺寸光学优化 |
| 文件类型 | 首版通用文件/目录图标加文字，按需要加入少量类型 glyph |
| 控件面板 | 类型 glyph 表示类别；真实控件缩略图单独生成 |
| Git/调试状态 | 基础 glyph 配状态标记，不为每种组合画一张文件 |
| 用户应用资源 | 保留用户风格，不强制转换为宿主图标库 |

不以“下载数量最多”作为质量标准，不为每个菜单项强行安排图标。
明确的文本菜单可以没有图标；高频工具栏、状态和导航优先覆盖。
不得直接搬用其他产品的商标、产品图标或未核验授权的资源。

### 5.2 自有单色图标规范

* 编辑源默认正坐标 `viewBox="0 0 24 24"`，导出宽高明确，背景透明。
* 主体保留约 2 单位安全留白；必要的光学偏移需记录，不盲目数学居中。
* 单色 SVG 可用 `currentColor` 表达语义，转换器输出不携带主题色的几何数据。
* 轮廓优先闭合填充；含 stroke 的文件构建时展开，不依赖运行时补猜。
* 源中不含字体/文本、脚本、动画、外部 URL、嵌入位图或隐式外部样式。
* 单色 glyph 禁止渐变/滤镜；确需这些效果的内容归入品牌或插画资源。
* 允许编辑源中的 group/transform，但转换必须展开并校验，不直接丢弃。
* 不能保真转换的内容报错，不能为了通过构建静默删掉路径或效果。
* 洞、复合路径、fill-rule 必须实测。当前逐轮廓填充不是完整 SVG 填充规则承诺。
* 若轮廓有洞在当前后端不保真，应分解为可绘制几何或走图片管线；保留转换说明。
* 不简化原始第三方母版；规范化结果是单独派生物，保留来源摘要。

#### 最小线性设计语言（2026-10-13 落实）

自有 glyph 使用单一"最小线性"语言，与上游 Material Symbols outlined 的视觉重量对齐，
不用实心色块表达结构：

| 规则 | 取值 | 原因 |
|---|---|---|
| 画布与安全区 | `24` 网格，图形落在 `2..22` | 与上游同网格，四周留 2 单位呼吸 |
| 线宽 | 统一 `2`（`STROKE_WIDTH`） | 一套图标只有一个光学重量，不逐图调粗细 |
| 线端与转角 | `round` / `round` | 展开后外角是半径 1 的圆弧，内角保持尖角 |
| 作者坐标 | 中线落在整数格 | 描边边界落在整数上，小尺寸更利落 |
| 结构表达 | 开放中线，不画闭合环 | 闭合环展开后必是环状带洞轮廓，逐轮廓填充不保真 |
| 闭合外形 | 拆成两段同向开放中线，接点取相对边中点 | 接点处两段圆端头互补成完整带，接缝不可见 |
| 实心点缀 | 每图最多一个实心母题（圆点/方块/星形） | 保持轻量，同时保留 AI、状态等确需实心的语义 |
| 颜色 | 源内只写 `currentColor`，不出现具体色值 | 主题与状态换色，不换文件 |

闭合外形的拆分是"无洞轮廓"的唯一手法：按周长方向把轮廓拆成两条**同向**开放中线，
接点取两条相对边的中点。两段在接点处的圆端头彼此互补，且与相邻直边共线，
所以展开后的两个轮廓并集与一条闭合轮廓视觉等价，但每个轮廓都是单连通、无洞的。

展开规则是显式的，不是渲染期猜测：两侧按半笔宽偏移；外角插入半径等于半笔宽的圆弧，
内角取两条内偏移线的交点（与 SVG `stroke-linejoin="round"` 一致：外圆内尖），
两端加圆端头。输出为闭合多边形，所以依赖侧没有曲线展平成本，1024 点/64 轮廓的容量
可以按声明点数精确核算（`strokeToOutline`、`toUpstreamPathData`）。

### 5.3 字体与 emoji 不作为命令图标

不用 icon font、Unicode 字符或 emoji 表示保存、运行、错误等功能。
它们依赖字体覆盖、平台替换、基线和颜色字形行为，无法保证视觉一致。
无障碍名称来自命令文本/翻译键，不来自 glyph 或 Unicode 名称。

## 6. 语义 ID、清单与命令映射

### 6.1 三种身份不要混为一谈

1. **命令 ID**：例如 `file.save`，控制执行、权限、快捷键、撤销和状态。
2. **宿主图标 ID**：例如 `host/file/save`，控制视觉语义和渲染选择。
3. **工程资源 ID**：例如 `project/icons/save`，控制用户资源解析和产物追踪。

相同 glyph 可以服务多个命令，命令不因图标更换而改名。
宿主图标采用类型化 `HostIconId`，其稳定字符串由清单生成或集中映射。
不持久化 Rust enum discriminant，不将上游路径或 `IconName` 序号写进工程。

命名规则：

* 语义 ID 使用小写 ASCII、`/` 分段、段内 `-`，不含扩展名、语言或主题名。
* 原文件名用小写 kebab-case，如 `event-binding.svg`。
* 上游 token 保持其实际 snake_case，如 `folder_open`，不做模糊匹配。
* 清单中的源路径相对于清单所在目录，包内路径只用 `/`。
* 小写约束之外，还要检测大小写不敏感文件系统上的碰撞。
* 语义更名保留迁移/废弃信息，不静默复用旧 ID 表示新含义。

缺少图标是合法设计时，命令元数据显式为“无图标”；请求了图标却未解析成功是错误，

### 6.3 首批映射与补图策略

| 宿主语义 | 已核验内置 token | 策略 |
|---|---|---|
| 保存 | `save` | 直接复用 |
| 打开工程/目录 | `folder_open` | 直接复用 |
| 文件与关闭目录 | `file`、`folder` | 直接复用 |
| 撤销/重做 | `undo`、`redo` | 复用；RTL 行为单独确认 |
| 剪切/复制/粘贴 | `cut`、`copy`、`paste` | 直接复用 |

| 添加/删除/关闭 | `plus`、`trash`、`close` | 不把删除与关闭混用 |
| 信息/警告/错误 | `info`、`warning`、`error` | 颜色、轮廓、文本共同传意 |

## 7. rust-widgets 集成与真实缺口

### 7.1 单一宿主入口，多个控件适配

宿主调用者仅传递语义 ID、尺寸角色、状态和上下文，由集中入口：

```text
Command metadata
    -> HostIconId
    -> source selection / validation
    -> theme + state + scale
    -> actual control adapter
    -> rust-widgets render or image pipeline
```

“统一”指统一语义与解析，不是掩盖各控件底层接口不同。
不要把图标服务扩展成另一个渲染引擎、事件框架或资源操作系统。

| 消费入口 | 当前可用通道（`c957fdec`） | 本项目必须做的事情 |
|---|---|---|
| 独立 `Icon` 控件 | `set_icon(&str)` / `set_icon_enum(IconName)` / `set_icon_source(IconSource)` | 挂载前解析并校验，设置主题/尺寸，失败可诊断 |
| 自定义绘制内联 glyph | `draw_icon_at` / `draw_icon_named` / `validate_icon` / `paint_icon` | 检查返回及几何预检；不额外建子控件 |
| `Button` | `set_icon(Image)` / `set_icon_source(IconSource)` / `set_shared_icon_pixels(SharedIconPixels)` | 按内容类型选择几何或像素通道；验证高 DPI 与禁用状态 |
| `ToolButton` | `set_icon(PathBuf)` / `set_icon_source(IconSource)` / 共享像素 | 优先 `IconSource`；路径通道仅作便利入口并预检，不默默丢图 |
| `Action` / 菜单入口 | `icon_text` 文本 + `set_icon_source(IconSource)` | 文字菜单仍合法；需要 glyph 时走 `IconSource`，不用文本冒充 |
| 原生 OS 菜单 | 平台菜单接口 | 验证各平台是否支持图标，允许平台约定为文字，不强行模拟 |
| 窗口/任务栏/Dock | 窗口后端 + OS 包元数据 | 分开验收，不能只看通用 setter 返回值 |

### 7.2 首版如何控制注册表风险

新实现优先以 `IconSource::StaticGeometry` 提供少量自有编译期 glyph，不为绕开注册表
而扩大资源框架。只有必须使用 rust-widgets 的字符串路径注册 API 时，才适用以下约束：

* 注册表容量约束只针对注册 API，不是整个项目可用图标数或动态工程资源容量。
* 若采用注册路径，使用如 `rustage.event-binding` 的独立前缀，并检查内置/自有名称冲突。
* 仅在 GUI 初始化时注册有明确所有权的固定静态项；逐项检查注册结果。
* 初始建议预算不超过 12 项；上游注册路径的 16 项上限须按固定依赖重新验证。
* 不按窗口重复注册，不在视图卸载时调用进程级 `clear_registered_icons`；
  测试全局注册状态时串行隔离。
* 超预算时优先回到静态几何或适配目标控件，不通过提高本地常量或动态轮换 token 绕过。

### 7.3 上游图标 API 的能力与边界（基线：`c957fdec`）

上游已提供可复用的静态 glyph 和部分像素适配接缝，但不是覆盖动态工程资源、
所有控件和所有目标的通用资源 API：

* `IconSource` 只有 `Builtin(IconName)` 与 `StaticGeometry(&'static IconData)`；
  `StaticGeometry` 要求静态生命周期，不能直接承载导入后运行期拥有的几何数据。
* `IconSpec` 表达 `Builtin` 或 `Resource { id, color_mode }` 逻辑来源；
  它本身不是文件 I/O、资源加载器或已验证的 JSON 持久化 schema。项目仍须定义序列化、
  迁移、资源 ID 校验和目标解析。
* `IconColorMode` 表达 `Monochrome` / `Original` 的颜色策略，不代表所有控件都能消费
  任意多色图像，也不自动提供主题适配。
* `IconResourceResolver::resolve_icon -> Result<IconSource, String>` 只能返回上述
  `IconSource`。因此它适合解析内置图标或可提供 `'static` 的静态几何，不足以单独完成
  工程中动态导入的 SVG、位图或其像素缓存的解析。
* `SharedIconPixels` 是受 `image` 且非 `alloc_frugal` 条件约束的共享 RGBA8 像素句柄；
  当前 Button/ToolButton 有消费通道，Action 与独立 Icon 没有同等像素 setter。
  它是运行期像素复用通道，不是持久化格式、资源 resolver 或全控件统一抽象。
* `IconResourceBinding` / `IconLoadOutcome` 提供请求版本与结果状态辅助；
  不执行 I/O/解码、不拥有异步任务或文件句柄，也不能据此宣称已解决动态资源释放/
  缓存生命周期。宿主仍须负责取消任务、拒绝过期结果、缓存所有权与工程关闭清理。
* `validate_icon` / `paint_icon` 等接缝可报告部分验证/绘制失败，不替代导入安全校验、
  所有后端兼容性或真实控件验收。

因此 rustage 的采纳边界应明确如下：

1. 宿主内置图标与自有编译期单色 glyph 优先映射至 `Builtin` /
   `StaticGeometry`；静态几何不占字符串注册槽，但仍需检查上游点数、轮廓数、
   填充规则、绘制和目标 profile 限制。
2. Button/ToolButton 可在适用 feature 下使用 `SharedIconPixels`；
   Action、独立 Icon、树节点及原生菜单须逐一探测。无对应通道时应明确降级为文字/
   静态 glyph，或提出最小上游/API 扩展，不伪称共享同一图片来源。
3. 工程资源清单的 `Resource { id, color_mode }` 仅是逻辑引用候选；
   在动态拥有几何/图片的 API 和持久化 schema 完成前，不将其描述为可端到端运行。
4. 不把用户 SVG 转成 `'static` 引用，不使用内存泄漏或全局注册表伪造动态生命周期。
   可用的首版路线是在受限导入/预生成阶段产出目标格式，并由宿主拥有的缓存/适配器
   管理动态像素；具体实现须经真实控件探针和路线图任务确认。
5. 路径型控件不得以当前工作目录作为资源根。包内只读资源、经校验的应用资源目录及
   单文件打包分别验证；`include_bytes!` 不会自动使字节满足 `PathBuf` API。
6. 受限 profile 不得无条件引入图片解码或引用计数依赖，目标代码按真实 feature/
   内存约束选择静态数据或外部打包策略。

统一的是宿主命令语义与错误诊断，不是现有上游 API 尚未提供的运行时内容抽象。
完成标准是每个声称支持的消费点都用真实来源、feature 和目标完成端到端验证；
注册成功、类型可构造或 SVG 快照均不足以单独证明资源可用。

### 7.4 rustage 侧采纳决策

本节基于 `c957fdec` 的实际接口记录宿主可采纳的共同子集，不把它描述为通用资源层；
实现时仍以固定依赖中的公开 API、feature 和实际控件探针为准。

**统一命令语义和诊断；按控件能力选择内容通道。** 同一命令可映射至内置 glyph 或静态
几何，但动态图片是否可显示由消费控件的实际 API 决定：

* `IconSource` 适用于内置和静态几何通道，不承载动态像素或拥有型资源。
* `SharedIconPixels` 可减少 Button/ToolButton 间重复持有 RGBA 像素；不推导到 Action、
  独立 Icon 或原生菜单。
* 加载/绘制错误分别在宿主资源管线和上游几何/绘制接缝处理；任何一个接缝成功都不代表
  导入安全、缓存释放和各平台消费端均已验证。

#### 已由上游提供的层

1. **静态图标来源类型**：`IconSource` 区分内置 glyph 与静态几何。
2. **像素适配子集**：适用 feature 下 Button/ToolButton 可消费 `SharedIconPixels`。
3. **几何绘制/校验接缝**：相关控件可报告部分几何或后端失败；各消费点仍须分别验收。
4. **资源规格辅助类型**：`IconSpec` / resolver 提供逻辑来源描述与受限解析接缝，
   不替代项目 schema、动态图片载荷或持久化实现。

#### 刻意保留、不强行统一的层

* 原生系统菜单不保证支持图标；能力不足时明确采用文字，不伪装为跨平台一致。
* 菜单、工具栏、树节点各自的间距、对齐、选中标记与点击热区仍由控件决定。
* SVG 导入、文件监视、许可证、打包和资源权限继续由宿主负责，不塞进 glyph renderer。
* 多色 logo 不统一成文字前景色；用户图片不为了“同一个 API”被重新编码为单色轮廓。
* mini/embedded 不为桌面资源便利性承担不需要的运行时依赖。

#### rustage 采纳顺序

| 步骤 | 范围 | 验收重点 |
|---|---|---|
| 1 | 固定依赖修订，按 feature 核对各控件的 `IconSource` 与 `SharedIconPixels` 通道 | 静态几何、像素和受限构建能力均有实证 |
| 2 | 集中宿主语义映射，先接入库内置和自有静态几何 | 不占字符串注册槽；容量、绘制和状态验证通过 |
| 3 | 对 Button/ToolButton 探测像素资源，对 Action/独立 Icon 等分别记录支持与降级 | 不将有像素 setter 的控件能力推断到其他控件 |
| 4 | 按 T12.05/T12.06/T12.09 实现工程资源导入、schema、拥有型缓存/适配和目标变体 | 任务/缓存可取消且可清理；未知或缺失资源显式诊断 |
| 5 | 原生菜单、树/导航等逐个消费点按平台能力适配 | 不支持图标时采用明确文字呈现，不伪造统一图片通道 |
| 6 | 将已验证资源表示接入生成器和目标打包策略 | 两种模式身份/引用语义一致；每个目标实际构建与运行 |

**步骤状态（2026-10-13 更新三）**：步骤 1、2 已按 §7.5 与 §9.1 完成——依赖按修订固定，
60 个语义图标在固定依赖中全部可解析并全部由真实控件绘制，源轮廓数与显示尺寸下的展平容量
经依赖自身接口实测。步骤 3–6 仍未开始：`SharedIconPixels` 通道、菜单/树/原生菜单等消费入口、
工程资源导入与两种模式的生成目标都还没有消费者，按原则不为它们预设实现。

上游 `IconSpec` 不是可直接序列化的 JSON 契约。运行期类型、工程 schema 与生成目标
可以不同，但必须由项目明确定义映射、版本迁移和资源错误行为。旧 `icon_text` 保持文本
语义，不偷偷将任意文本解释为 token；旧接口是否废弃按版本策略决定。

**完成标准**是每个声称支持的消费点都使用其实际支持的内容通道，状态正确、失败可诊断、
旧行为保持，且所有声明支持的 feature/profile 组合通过验证；不要求无依据地统一 setter。

### 7.5 固定依赖（2026-10-13 更新三）

依赖以 **git 修订** 固定，不用个人目录路径：

```toml
[dependencies]

                 rev = "c957fdec7f30cc1a526b7c898c0f44b458ef4a57",

```

* 修订与 §2.1 的核验基线、`upstream-tokens.json` 记录的修订一致；`Cargo.lock` 入库，

  受限 profile 的组合不在本包声明内，升级时按 §7.3 逐控件复核。
* 本地 sibling 检出仅供核验，不是构建前提：删掉 `~/workspace/rust-widgets` 后

## 8. 源文件校验与确定性构建

### 8.1 三条处理管线

```text
A. 上游内置 token -> 固定库契约校验 -> HostIconId 映射 -> 库内置轮廓

B. 自有/额外 vendor SVG -> 来源核验 -> 严格子集校验 -> 填充曲线展平 + stroke 中线展开
   -> 坐标转换（y' = y - 24）-> 无洞与容量预检 -> 编译期静态几何，或交给独立的
   运行期图片适配/打包

C. 品牌母版 -> 小尺寸母版选择 -> 固定参数栅格化
   -> ICO / ICNS / Linux PNG + SVG -> 平台打包
```

输入白名单、转换能力与许可检查先于派生生成。转换任务无网络，不在 `build.rs`
临时下载 SVG、字体或工具。`build.rs` 仅用于宿主自有且需编译期生成的资源；
用户工程资源由工程导入/生成管线处理，不应混入宿主 Cargo 构建状态。维护者更新
vendor 是显式操作，不是普通构建副作用。

### 8.2 工具选择

* 首选复用上游已有转换、展平与图像接口，先检查可见性、feature 与实际语义。
* SVG 规范化、stroke-to-path、复杂填充转换应选成熟工具，不手写半套 SVG 解析器。
* 若无单个工具涵盖需求，组合有明确职责和固定版本的工具，记录中间结果与失败位置。
* 栅格化输出与交付管线使用固定版本和色彩参数，不能混用不同机器上默认的设计软件导出。
* 一般 `cargo build` 尽量不要求 Inkscape 等桌面软件；图标导入/更新可用离线开发工具。
* 平台编码依赖限制在打包任务；常规 Linux 开发不要求 macOS 的系统打包工具。
* 具体依赖在首个实现任务中经过小样探针选定，本文不增加未经使用的依赖。

### 8.3 生成约束

* 固定输入字节、工具版本、参数、依赖修订产生确定输出。
* 输出按稳定 ID 排序，不依赖目录遍历顺序、时间戳、绝对路径或随机数。
* 字节摘要覆盖内容；缓存 key 另覆盖转换器版本、目标尺寸、状态和色彩参数。
* `build.rs` 使用精确的输入变化声明，不能每次构建无条件重跑全部转换。
* build script 只写 `OUT_DIR`，不改源 SVG、清单、已审核基线或工作树。
* 生成失败保留最后有效源，移除未完成候选，不将空表作为成功输出。
* 更新源、清单和引用采用临时候选 + 完整校验 + 日志化的逻辑事务。文件系统通常不能
  原子提交多个文件；优先写入不可变/版本化新资源，再逐文件发布并最后切换清单/提交标记。
  保留旧版本直至确认提交；崩溃恢复依日志完成或回滚，恢复完成前阻止读取不一致工程。
* 发布任务清理其专属 staging 而不是全局缓存或用户工程。
* 发布验证可以在独立目录重新生成比较摘要，禁止为“通过”自动更新基线。

规范化数据的检查至少包括：

1. 矩形与坐标范围、有限数、非零尺寸、透明背景。
2. 完整源特性清单；不能仅提取 `<path>` 而丢失其他可见元素。
3. 源图与派生图的实际渲染比较，特别是洞、交叉、弧线和光学居中。
4. 所有计划显示尺寸下的展平结果，包括 1024 点/64 轮廓的容量限制。自有 glyph 的
   `stroke` 中线与填充曲线在构建期已展平为多边形，因此这里的点数是精确值，不是估算。
5. 静态几何容量；仅使用旧注册 API 时才检查注册容量、名称合法性及 token 冲突。
6. 路径表、清单、许可、派生物的一一追踪。

## 9. 主题、状态、缩放与 RTL

### 9.1 不为每种状态复制一份 SVG

同一单色 glyph 使用主题语义色，建议角色为：

```text
icon-default
icon-muted
icon-accent
icon-on-accent
icon-disabled
icon-success
icon-warning
icon-danger
```

角色名是宿主设计建议，实施时映射到现有主题能力，不冒充上游已定义字段。

**八角色到真实主题的映射（2026-10-13 落实）。** 映射写在 `src/resources/icons.rs` 的
`IconRole::color_in`，取值只来自依赖自己的主题字段，宿主不自带第二份调色板：

| 角色 | 依赖主题字段 | 读取表面 |
|---|---|---|
| `icon-default` | `colors.foreground` | `background` |
| `icon-muted` | `colors.secondary` | `background` |
| `icon-accent` | `colors.primary` | `background` |
| `icon-on-accent` | `colors.primary.contrast_color()` | `primary` |
| `icon-disabled` | `colors.disabled` | `background` |
| `icon-success` | `colors.success` | `background` |
| `icon-warning` | `colors.warning` | `background` |
| `icon-danger` | `colors.error` | `background` |

两条规则写在实现里而不是写死在色值里：

* 主题 token 是为**语义**选的，不是为对比度选的。实测轻色板中 `warning` 对 `background`
  只有 1.43:1、`primary` 2.74:1，直接画就是近似不可见。除 `disabled` 外，各角色取到 token 后
  再经依赖自带的 `Color::legible_on(surface, 3.0)`（图形对象阈值，也是依赖自己给非文字指示器用的
  比例）向黑或白靠拢；本来达标的角色因此保持主题原色不动。`icon-disabled` 刻意不参与：
  禁用图形本就应该后退，强行拉到 3:1 会让不可操作的控件看起来可操作。
* 高对比模式是**强制配色对**，不是着色。依赖会用它替换每个控件解析出的背景与文字色，而本层的
  角色色是显式赋给控件的，如果不处理就会反过来压过用户选择；因此有强制配色对时所有角色都取
  该配对的前景色（`HighContrastMode::forced_pair`）。
* 轻/暗两套、八角色的实际取值由测试逐个断言：对比度达标、彼此可区分、切主题后确实改变。


轻/暗主题切换更换颜色与相关图片缓存，不读取另一份 `save-dark.svg`。
只有真实的轮廓变体或多色资源才允许单独源文件，并在清单显式关联。

**换色不换文件的落实与校验（2026-10-13）**

* 每个 glyph 只有一个源文件，源内只有 `currentColor`；校验拒绝按状态或主题命名的源文件名
  （`save-dark.svg`、`icon-hover.svg` 一类），因为那必然是重复的图形文件。
* `resources/host/icons/theme.json` 记录八个角色在轻/暗主题下的**评审用**色板，
  状态为 `proposed-pending-approval`：它只服务生成的主题矩阵图，不冒充产品主题取值，
  在 T05.02/T24.02 接入真实主题后被替换。
* `target/resources/reports/icon-theme-matrix.png` 把同一份源文件画遍 8 角色 × 2 主题
  （16 行 × 19 列），是"随主题变化"的可视证据；单元格映射与机制说明在同名 `.json`。
* 评审图只证明图形是单色且可换色，不证明任何控件已经取到主题色，也不构成品牌或主题批准。

| 状态 | 呈现规则 |
|---|---|
| 普通 | 默认前景，符合所在背景 |
| hover | 优先改变按钮背景/边框，不必换 glyph |
| pressed | 跟随真实交互状态，不仅改变图标颜色 |
| disabled | 使用可辨但非主导的样式，禁用原因可查询 |
| checked/selected | 选中底色、边框或标记共同表达 |
| warning/error/success | 颜色 + 形状 + 文本/读屏语义 |
| running/busy | 有真实任务状态；动画可关，非无限“假忙” |

`Icon` 已有去饱和/半 alpha 的禁用绘制。宿主不要再叠一次透明度；
其它控件行为分别测试。高对比主题不能只复用半透明灰，需按真实后端能力验证。
必要时补上游样式接缝，不能用“高对比支持”文案掩盖控件固定算法的限制。

### 9.2 逻辑尺寸与设备像素

推荐尺寸角色：

| 使用场景 | 逻辑尺寸 |
|---|---|
| 状态标记、小树节点 | 12–14 |
| 菜单、工程树、常规行内 | 16 |
| 密集工具栏 | 20 |
| 主工具栏、常规图标按钮 | 24 |
| 大入口/欢迎页 | 32 |

这是视觉角色，不是要求所有同类场景强制一个尺寸。图标画幅与点击热区分开：
16 的 glyph 可以放在更大的键盘/指针可访问控件里，不能把点击区也缩到 16。

* 实际栅格尺寸按逻辑尺寸乘宿主有效 scale，经统一规则舍入。
* 验证 100%、125%、150%、200%、300%，以及跨不同 DPI 显示器移动窗口。
* 矢量数据免去多份分辨率源文件，但不免除像素对齐与小尺寸视觉测试。
* 16 等小尺寸失去细节时可以有显式光学变体；不可对所有图标机械缩小复杂 24 母版。
* 当前 resvg 通道的 intrinsic-size 图片不能直接被放大后宣传为高 DPI 矢量清晰。
* 图片适配在所需实际像素尺寸生成/缓存；品牌资源保持比例和透明边缘。
* 不在绘制循环解析 SVG、执行转换器、访问磁盘或做文件摘要。

### 9.3 RTL 是逐语义决策

导航前进/后退、展开方向等可以镜像，但必须结合控件行为和 locale direction。
保存、搜索、logo、数字、Git 分支以及数据/时间轴方向不默认镜像。
清单 `rtl_mirror` 是输入规则，不意味着当前绘制 API 已有镜像参数。
当前无镜像接缝时使用成对内置 token 或构建期变体，避免宿主和控件各镜像一次。
测试至少覆盖一个 RTL 布局与中文/英文，检查布局方向、箭头和命令语义一致。

## 10. 无障碍与信息表达

* 纯图标按钮必须有真实可访问名称、键盘焦点和可发现的命令说明。
* tooltip 是补充，不替代读屏名称或键盘访问；触屏/键盘不能依赖 hover。
* 图标旁已有完整标签时，图标作为装饰，避免读屏重复播报。
* 状态不能仅靠红/绿区别：错误/警告使用不同轮廓，并保留文字和状态语义。
* 焦点环属于控件边界，不画在图标文件中；缩放和裁剪不能吃掉焦点环。
* 动画尊重减少动态效果偏好；静态状态仍能表达任务正在运行。
* 建议采用非文本关键图形对相邻背景至少 3:1 的对比目标；普通文字按相应文字标准检查。
  禁用项按适用规范处理，不伪造所有状态统一达标；品牌/装饰与功能图形分开分类。
* 可访问树中名称/role/state 存在，还不等于辅助技术端能用；三平台分别实测。


这是建议的资源子结构，`ui/` 与 `src/` 不替代白皮书尚待决定的完整工程格式。
导入外部文件时复制到工程受管目录，记录来源；不默认保留指向用户下载目录的绝对引用。
必须保留外部链接的高级场景另有权限与可移植性诊断，不进入默认发布路径。

工程清单建议示例：

```json
{
  "schema_version": 1,
  "resources": [
    {
      "id": "project/icons/save",
      "path": "icons/save.svg",
      "media_type": "image/svg+xml",
      "role": "monochrome-icon",
      "packaging": "auto",
      "provenance": {
        "provider": "project-author",
        "license": "MIT"
      }
    }
  ]
}
```

许可值仅作格式示例，不能为用户自动声明其图片是 MIT。
实施时还需实际内容摘要、尺寸、使用节点、引用位置和目标转换结果；未知许可允许编辑预览，
但进入发布流程前须明确补齐或经审阅确认其发行权限。

### 11.2 逻辑 ID 不等于物理路径

`project/icons/save` 不随 `icons/save.svg` 移到新目录而变化。
改物理路径只更新清单，改逻辑 ID 则形成引用迁移事务，预览受影响节点并可撤销。
内容去重也不能合并两个不同的用户语义 ID；只在字节/派生缓存层共享。

使用上游 `ResourceId` 归一化时还需宿主规则：

* 只接受 schema 允许的相对路径，拒绝 OS 绝对路径、盘符、URI、NUL、`..` 和非法段。
* 库会剥离前导 `/` 和 `./`，因此 `ResourceId::parse` 成功**不是**安全路径验证成功。
* 实际文件访问需检查符号链接和规范化后边界，防止相对路径指向工程外。
* 清单路径校验和实际文件读取一起做边界保证，不能只比较字符串前缀。
* `contains` / `get` 失败要保留来源与读取原因，宿主不能只留下“没图”。
* 多来源同名默认报歧义；工程/扩展覆盖若开放，应先解析显式优先级，再交付唯一来源。

### 11.3 导入、修改与热更新事务

```text
选择文件
 -> 权限与边界检查
 -> 有界格式检测/解析
 -> 候选原文件和来源记录
 -> 候选转换与预览
 -> 用户确认（如需转换/覆盖）
 -> 写入新版本资源与事务日志
 -> 发布资源/清单/引用变更，最后写提交标记
 -> 精确失效并更新预览
```

文件系统通常不提供跨多个资源文件、清单和项目引用的原子提交；这里的“事务”是可恢复的
逻辑一致性保证，不应宣传成多文件原子性。优先采用不可变或版本化资源路径，分阶段校验并
记录可恢复日志，逐文件原子替换（仅在底层文件系统保证时）后最后发布清单/提交标记。
崩溃后依据日志完成或回滚；提交确认前保留旧版本，恢复期间不让预览读取半提交状态。

失败保留旧有效资源和用户编辑内容，问题面板指出文件、资源 ID、阶段和原因。
外部修改先在候选数据上校验，通过才替换；错误候选不得破坏最近一次有效预览。
删除资源先查询反向引用，允许取消、替换或显式保留缺失状态，不自动删除引用节点。
关闭工程取消归属任务并释放缓存，不影响别的工程与宿主 UI。

## 12. 生成模式与受限目标

| 目标/模式 | 推荐资源策略 | 必须验证的限制 |
|---|---|---|
| desktop/tablet/mobile 模式 1 | 工程逻辑 ID + 工程资源运行期加载/解码策略 | profile API、目标解码、主题、加载失败和包内定位 |
| desktop/tablet/mobile 模式 2 | 资源按白皮书及工程选择嵌入或外部打包 | 无设计器依赖；资源身份与模式 1 相同，产物边界明确 |
| mini/embedded 模式 2 | 仅生成目标确实支持的静态几何/像素数据或外部资源 | feature、内存、格式、容量、链接与设备验证 |
| mini/embedded 模式 1 | 不提供 | 不绕过既有两种产物边界 |

重要边界：

* 不在受限产物中无条件引用 `rust_widgets::asset`、resvg 或 `Image`。
* 生成器先查选定 profile 的实际公共 API 与渲染能力，不凭宿主构建成功判断可用。
* 上游 `EmbeddedSource` 内部持有/返回 `Vec<u8>`，不能将它描述成零拷贝静态资源表。
* 需要无堆或受限内存的目标，生成与目标兼容的静态切片和访问代码，
  而不是把 desktop 的 resolver 带进去。可复用语义和格式，不强求相同 Rust 类型。
* 不支持的 SVG 特性可在宿主生成阶段按批准规则转换；目标端不运行转换器。
* 目标转换改变视觉或色彩时，说明差异并要求确认；无法满足容量则阻断，不静默缩小。
* 收集从入口可达的资源引用及显式动态白名单，避免全量打包宿主与用户素材。
* 业务代码动态引用无法静态分析时，要求显式声明或完整包策略；不错误裁剪。
* 生成报告列出逻辑 ID、源摘要、派生摘要、体积、目标格式、许可及未支持项。
* 模式 1/2 的同一资源身份要有实际端到端比较测试，而非仅清单字符串相同。
* 模式与目标支持的资源策略由白皮书和目标任务确认；本文不把“外部/嵌入/静态”
  写成所有平台均已可用，也不默示任一模式必须采用单文件或特定缓存格式。

## 13. 平台应用图标与打包

### 13.1 Windows

* 从品牌母版生成多尺寸 ICO：建议包含 16、20、24、32、40、48、64、128、256 像素。
* 至少验证小尺寸帧与 256 的大尺寸编码被目标系统正确读取。
* 应用图标进 PE 资源，安装器、快捷方式、文件关联引用打包产物。
* 窗口大/小图标入口另行设置并验证，不能只依赖 EXE 图标。
* 应用身份、快捷方式及任务栏组合策略按最终打包形态确认。
* 验收 Explorer、快捷方式、任务栏、窗口标题栏及 Alt-Tab，而非只检查 ICO 文件存在。

### 13.2 macOS

* 从 1024 级品牌母版生成 `.iconset` 再得到 ICNS。
* 传统 iconset 覆盖 16、32、128、256、512 的 1x/2x，最大实际像素 1024。
* 安装到 `.app/Contents/Resources/` 并由对应 Info.plist 图标配置引用。
* 最终 macOS 版本若采用新的图标/外观机制，按最低支持版本核验适用规则，
  不把单一年代的模板宣称为所有系统的最终规范。
* 验证 Finder、Dock、应用切换器及打包后启动；公证/签名流程包含资源。
* logo 不重复加入系统已经提供的圆角、背景或材质，留白由品牌规范定义。

### 13.3 Linux

* 按 hicolor 布局准备 16、24、32、48、64、128、256、512 PNG；
  需要时提供更大尺寸，并安装可缩放 SVG 到 `scalable/apps/`。
* `.desktop` 的 `Icon` 使用与安装文件 basename 一致的稳定名称，不带绝对开发路径。
* reverse-DNS 应用 ID 必须基于项目实际控制的命名空间确定；本文不虚构域名。
* 桌面项、图标文件与 Wayland app_id / X11 身份匹配，避免任务栏重复或显示通用图标。
* 发行形态分别定义 deb/rpm/AppImage/Flatpak 等适用布局，不保证一套路径覆盖所有包。
* 使用用户级安装时更新相关缓存的行为按系统工具与权限执行，失败可诊断。
* 验证至少 GNOME 与 KDE 的实际启动器/任务栏；窗口图标是否由桌面项解析也需确认。

### 13.4 鸿蒙桌面（HarmonyOS / OpenHarmony，2in1）

本节的路径与字段按 OpenHarmony 官方文档与真实 DevEco 工程核对，来源记在
`packaging/harmonyos/app.json` 的 `sources`；具体数值（分层图标 1024、启动页图标取
512）来自实测与母版规格，不是猜测。

* 应用级清单 `AppScope/app.json5`：`bundleName`、`vendor`、`versionCode`（整数）、
  `versionName`、`icon`、`label`；`minAPIVersion`/`targetAPIVersion`/`apiReleaseType`
  由平台在编译期**自动生成**，手写值会被忽略，因此模板里刻意不出现这三个字段。
* 最低支持版本写在工程级 `build-profile.json5` 的 `compatibleSdkVersion`；签名材料
  绝不入库，只记录到发布任务。
* 模块级清单 `entry/src/main/module.json5`：`type` 为 `entry`，`deviceTypes` 声明
  `2in1`（PC/桌面形态）；入口 UIAbility 的 `skills` 需含
  `entity.system.home` 与 `ohos.want.action.home`，否则桌面图标点击进入的是应用详情页。
* 分层图标：`AppScope/resources/base/media/` 下 `background.png` 与 `foreground.png`
  各 1024×1024，并由同目录 `layered_image.json`（`layered-image.background/foreground`）
  声明；`AppScope` 资源在打包时合入模块并覆盖同名模块资源，所以只声明一次。
* 启动页图标 `startWindowIcon` 与启动页底色 `startWindowBackground` 是两项**不可缺省**
  的 UIAbility 字段；底色是 `$color:` 资源，因此深色适配靠
  `resources/dark/element/color.json` 覆盖同名值，而不是第二份清单。
* 应用标识必须同时满足各平台约束：鸿蒙 bundle name 为三段以上、仅字母数字与下划线、
  7~128 字节、且**不允许连字符**，因此共享的反域名标识不能带 `-`。
* `versionCode` 由 `package.version` 按 `packaging/harmonyos/app.json` 声明的方案派生，
  与 `versionName` 不会脱节；方案无法表示的版本直接报错，不做静默截断。
* 单层图标在平台上是合法形态；本仓库选择分层图标，因为它是 2in1 上的常规形态，
  并且要求前景/背景分开的母版，这正好与 §2.2/§5.2 的分层留白规则一致。
* ArkTS 入口代码（`EntryAbility`、`pages`）属于宿主应用，不放进资源树；本目录只提供
  清单与资源层。Rust 侧候选三元组为 `aarch64-unknown-linux-ohos`，
  但"固定版本的 winit/wgpu 能否在 2in1 上以原生模块方式承载"**未验证**，
  在做出任何支持声明前需要先做小样。
* 验收至少覆盖：真机桌面分层图标、明暗启动页底色、字符串资源解析、应用列表中的包身份，
  以及干净机器离线安装；同时与 §13.5 的共同要求一并检查。

### 13.5 平台共同要求

* 应用图标只由品牌母版和显式小尺寸母版派生，不手工修每个平台的每个 PNG。
* 首次设计通过尺寸矩阵审阅，允许 16/32 的光学差异，不以纯缩放保证小尺寸质量。
* 工程文件类型图标只在启用真实文件关联功能时加入，不能提前宣称关联已支持。
* 整个包复制到无源码、无 sibling rust-widgets、无网络的干净环境验收。
* 系统缓存可能延迟刷新，测试记录安装/升级步骤；不靠手动清缓存掩盖身份错误。
* 打包成功不等于 UI 图标加载成功，二者分别验收。

## 14. 缓存、性能与资源预算

### 14.1 优先复用已有缓存

先复用库的解码与内容缓存，不另造相同的图片缓存。
宿主只补语义解析、转换结果和未覆盖的主题/DPI派生缓存。
当前内置几何绘制仍有展平成本，不未经测量宣称“一次解析、之后零成本”。

图片/派生缓存 key 建议包含：

```text
source digest
+ pipeline version
+ render backend / pixel format
+ actual pixel size
+ resolved color(s) and color space
+ visual state when it changes pixels
+ optical variant
```

纯几何缓存不包含无关的命令权限或翻译；路径变了但内容相同可共享解码。
主题切换失效着色像素而非原始几何，DPI 切换失效相关像素尺寸而非全部工程。
缓存缺失可重新生成，源缺失不能伪装为缓存 miss 成功。

**本层的实际做法（2026-10-13 更新三）**：`src/resources/` 没有另建缓存。自有 glyph 走
静态几何通道，绘制时由依赖展平，宿主缓存的东西只有"角色到墨色"的解析结果，而它按下标量
存在控件上：主题变化由管理器信号置一个待刷新标记，`ToolbarSample::apply_theme` 重算并重新
赋色。这是"共享抽象须有实际收益"的直接应用——在出现真正的像素消费者（Button 的
`SharedIconPixels`、工程导入的拥有型图片）之前，建一个没人查的缓存只会是第二处真源。

### 14.2 建议初始预算

以下是待测量调整的门禁目标，不是现有性能数据：

| 项目 | 初始目标 |
|---|---|
| 宿主自定义全局注册数 | 若采用旧字符串注册 API，建议 <= 12；上游实际容量须在固定依赖复核 |
| 单个自有 glyph 源 SVG | <= 32 KiB，例外须审阅 |
| 单个自有 glyph 几何复杂度 | 在实际尺寸下成功展平，且不超过库当前容量 |
| 新增自有静态 glyph 数据总量 | <= 256 KiB，不计既有依赖和品牌系统图标 |
| 宿主新增图标/图片适配缓存 | 默认上限 16 MiB，需与已有库缓存核对实际总量 |
| 普通绘制循环 | 0 文件读取、0 SVG 解析、0 外部转换进程 |
| 常用可见图标 | 初始化/首次显示预热，避免一排按钮首次同时阻塞 |
| 故障诊断 | 同资源同版本合并呈现，不每帧重复刷屏 |

这些初值覆盖小型 glyph，不用来限制用户所有图片。
用户资源转换单独设置任务内存/并发/超时预算，超限提示分辨率、格式及可操作建议。

已测得的**构建期几何规模**（2026-10-13，来自 `target/resources/generated/host-icons.geometry.json`；
这是源级计数，不是渲染性能数据）：19 个自有 glyph 展开后合计 79 个轮廓、2396 个点，
单图最多 9 个轮廓、293 个点，源声明点数合计 362；产物中不含曲线命令。

**该计数已由依赖侧实测确认**（2026-10-13 更新三）：crate 的测试用固定依赖的
`validate_icon` 检查每个自有 glyph 的轮廓数与网格，再用 `paint_icon` 在 16/20/24/32/48 px
真实绘制，任何超出 1024 点/64 轮廓预算的尺寸都会以 `InvalidGeometry` 失败而不是被截断。
因此"留有量级余量"是可复现的断言，不再只是估算。绘制耗时与缓存命中仍未测量；
本层也没有另建像素缓存（见 §14.1）。

性能报告固定机器、后端、OS、DPI、资源版本、冷/热缓存状态和工作负载。
记录冷启动、首次图标显示、主题切换、DPI切换和长时间打开/关闭工程的缓存曲线。
微基准与真实工作台测量分开，不拿小表查找耗时证明整帧达标。

## 15. 安全、许可与供应链

### 15.1 非可信资源输入

* 格式按内容检测，扩展名只是提示。
* SVG 禁止脚本、foreignObject、外部引用、外部样式、DTD/实体展开及隐式网络访问。
* 拒绝内嵌可执行内容；非可信 SVG 的栅格化禁止外部资源与系统字体加载。
  若支持用户字体，必须由独立字体管线导入、校验并按目标能力交付，不能由 SVG 隐式引用。
* 位图限制编码大小、宽高、解码像素总量；校验乘法溢出，不仅检查压缩文件大小。
* SVG/SVGZ 限制输入、解压后大小、节点/路径复杂度、任务时间和输出大小。
* 不因上游存在 64 MiB SVGZ 解压上限就认为导入安全或内存峰值受同一数值限制。
* 建议 UI 图标导入默认上限：源文件 1 MiB、输出边长 4096、输出像素 16 Mi；
  自有宿主 glyph 仍受更严格的 32 KiB 规范。一般工程图片采用单独预算。
* 超限拒绝并解释，不静默降采样；用户批准转换也不得绕过安全硬上限。
* 复杂/非可信解码与转换放受预算的工作进程，取消可终止；进程隔离本身不等于沙箱。
* 解码器升级与供应链审查按项目发布门禁执行，不能仅因“纯 Rust”免检。

### 15.2 来源和许可

来源记录至少保存：

```text
provider / sanitized source URL (no credentials or secret query parameters) / exact revision or version
original relative path / original SHA-256
SPDX license expression / license file / applicable NOTICE
modification description / conversion tool + version + parameters
derived digest / rustage semantic ID(s)
```

* 上游内置 Material Symbols 的 Apache-2.0 声明随发行物分发；
  rust-widgets 和 rustage 的 MIT 不能替代图标数据许可。
* 额外 vendor 子集保存原始许可与适用 NOTICE，转换/修改记录留痕。
* 自有 SVG 核实作者和贡献权限后才标 MIT，商标使用权单独看待。
* 用户工程保留自己的来源声明，生成应用只携带实际使用的第三方资源声明。
* 没有许可证的网络图片不视为“可自由使用”；缺失来源不自动填写开源许可。
* 来源 URL 仅记录稳定、去敏的定位信息；token、凭据、私有签名参数等不得写入清单、
  日志、生成报告或版本控制。
* 发布包生成第三方清单/SBOM，图标和字体都纳入，不只统计 Cargo crate。
* 若生成应用引用宿主自有图标，必须是明确导出的资源能力与授权，不是复制运行缓存。

## 16. 验证矩阵与发布验收

### 16.1 自动检查

| 检查域 | 必须覆盖的正/负用例 |
|---|---|
| 清单 | 合法项、重复 ID、未知字段/源类型、未知上游 token、缺失文件、大小写碰撞 |
| 路径 | `..`、绝对路径、盘符、URI、符号链接越界、移动与权限拒绝 |
| 图标通道 | 静态几何容量/无效坐标；仅旧注册 API 覆盖空名、非法路径、容量、冲突与重复初始化 |
| SVG 转换 | 正坐标变负坐标、stroke、transform、洞、fill-rule、弧、超复杂、外部依赖 |
| 失败反馈 | 几何校验/绘制失败、图片无法解码、缓存写入拒绝、目标 API 不可用 |
| 状态 | hover/pressed/checked/disabled 与命令状态一致，不改变点击行为 |
| 生命周期 | 多窗口、多工程、热更新、取消、关闭后释放、不泄漏静态字符串 |
| 身份 | 路径移动不改 ID、ID 更名迁移、来源歧义、内容去重不改语义 |
| 生成 | 模式 1/2 同身份、引用裁剪、动态白名单、受限目标不拉入 desktop 资源模块 |
| 打包 | 单可执行/应用包、无开发树、无网络、许可齐全、系统图标真正可见 |
| 生成的图标表 | 表与清单/SVG 一致；手改、漏生成、只改一处（角色或几何）都被拒绝 |
| 控件绘制 | 60 个图标全部经真实控件绘制；源轮廓数、各显示尺寸下的展平容量、空槽拒绝 |
| 主题与无障碍 | 八角色对比度达标且彼此可区分；切主题改变墨色；强制配色对压过角色色 |

仍有未覆盖项，缺的仍是缺的：

* 真实窗口承载、窗口级 DPI 缩放与原生 DPI 切换（需要显示会话）。
* hover/pressed/checked 等交互中的绘制（需要输入事件驱动）。
* Button 图片适配（`SharedIconPixels`）通道、菜单、工程树等其余消费入口。
* RTL 项与 logo/非镜像项。

为每个宿主图标生成联系表，展示：

* 12/16/20/24/32 逻辑尺寸及实际像素尺寸。
* 亮/暗/高对比背景。
* 普通、禁用、选中、错误等适用状态。
* 100%/125%/150%/200%/300% 缩放。
* 静态轮廓、Button 图片适配、ToolButton、菜单和工程树的真实消费入口。
* RTL 适用项，以及 logo/非镜像项。

母版参考图、派生资源图、实际 rust-widgets 后端图分别保留，SVG 输出快照不能代替
真实软件/GPU/原生后端截图。PNG、ICO、ICNS 编码也不能仅用 GUI 内显示成功验收。

比较规则：

* 固定后端与环境才能作严格基线比较，跨后端抗锯齿差异分开记录。
* 几何位置、空白/缺图、方向、颜色角色可作结构断言。
* 像素差异采用经校准的阈值与差异图；不随意用一个全局容差掩盖局部缺图。
* 非整数 scale 下要看实际清晰度，不只验证输出尺寸正确。
* 人工审核是小尺寸可辨识和光学平衡的必要补充，不能由文件大小检查替代。

### 16.3 发布最低门禁

1. 清单中所有被宿主请求的图标可解析，无未知 token、无超容量、无缺图。
2. 主题切换、DPI变化、多窗口状态更新正确且没有重复禁用着色。
3. 无障碍名称、焦点与状态在三平台实际消费链可验证。
4. 非法资源不进入有效模型，诊断能定位且用户可恢复。
5. 用户工程资源与宿主资源互不覆盖，两种产物身份一致。
6. 所宣称支持的目标实际构建并运行，受限目标容量报告通过。
7. 三桌面发行包在干净环境显示正确系统图标，许可和来源随包分发。
8. 可复现输出检查通过；未验证平台/后端明确标为未验证，不能扩大支持声明。

### 17.1 第一个实施变更应尽量小而完整

## 18. 日常维护流程与最终放置原则

### 新增一个宿主图标

```text
确认命令语义
 -> 查询固定版本上游词汇
 -> 能复用则只加映射（当前 60 项中 41 项如此）
 -> 确需补图则按 §5.2 最小线性语言画 stroke 中线 + 记录来源许可
 -> node tools/resources/check-resources.mjs    # 子集、安全区、无洞、容量、清单覆盖
 -> node tools/resources/generate-resources.mjs # 展开、坐标转换、评审图、重写图标表
 -> cargo test                                  # 固定依赖里的轮廓/容量/绘制/主题断言
 -> cargo run -- --render-icons tests/baselines/icons   # 真实控件重渲染基线
 -> 审核视觉 diff（`tests/baselines/icons/` 四个 SVG 与两张评审图）
 -> 需要时把新 ID 加进 src/app/shell/toolbar.rs 的样例计划
```

`generate-resources.mjs` 会重写 `src/resources/generated_host_icons.rs`；提交它之前先看
生成报告里的 `host-icon-table` 阶段（记录了多少条、写了还是未变）。校验器会逐字节重建该文件，
所以"改了清单忘了生成"和"手改了生成文件"都会在 `check-resources.mjs` 直接失败。

* 新 glyph 一律先写中线：闭合外形拆成两段同向开放中线（§5.2），不要手写展平后的多边形。
* 出现在非默认角色或状态时，不改源文件；改调用点或主题角色。
* 不要再添加"按主题/状态命名"的源文件，校验会直接拒绝。
* 生成文件 `src/resources/generated_host_icons.rs` 只能由生成器改写；不要手改，也不要在
  `build.rs` 里重造一份（理由见 §4.2）。

### 更新一套第三方图标来源

显式变更来源版本和摘要，生成变更报告，检查新增/删除 token、风格、许可、派生差异、
注册容量和平台回归。正常应用启动不下载资源，正常构建不拉取浮动最新版本。

### 删除或更名

先查命令与文档引用；稳定 ID 必要时保留迁移表；移除死资源和无用派生物；
确认用户应用没有被宿主升级改变内容。不得随意更新视觉基线来掩盖删错图标。

**最终规则可以浓缩成四句话：**

* **库内置图标留在库里；rustage 只引用和验证。**
* **宿主补充图标源与许可放 `resources/`，静态派生物走确定性构建；动态加载另按 API 验证。**
* **用户资源放用户工程 `assets/`，稳定 ID 经清单解析，绝不混进宿主图标注册表。**
* **系统图标由 `resources/branding/` 母版生成，按平台安装并在真实系统验证。**
