## 三、上游建议：多行高亮状态在公共接口上不可判定

**现象（可复现）**：`CodeEditor` 为每行保留「入口状态」缓存，该缓存由**绘制路径**
（`prepare_visible_line_cache` → `ensure_line_states`）推进，并记录已证明到的位置
（`walked_lines`）。绘制尚未到达的行，公共访问器一律读回 `LineState::Clean`（`Default`）。

同一时刻，`line_state` 与 `tokens_on_line` 给出的答案并不一致：

- `set_text("/* open\nstill\n*/\n…")` 后，`line_state(1)` 返回 `Clean`；
- `tokens_on_line(1)` 以未证明的 `Clean` 入口状态对该行分词，因此得不到 `/* */` 的续行状态。

**为什么算问题**：`line_state` 的文档写明了「若词法器已到达该行」这一前置条件，因此单看该
访问器并不违约。问题在于类型无法表达第三种事实——`LineState` 没有「未知」变体，也没有
`is_state_known` 之类的谓词，于是调用方**无法区分「该行不在多行结构中」与「该行尚未被词法
分析」**。这正是原则 #22 禁止的「用成功形状的默认值掩盖失败」。`tokens_on_line` 的文档称
其为按需计算，但其结果会随绘制历史变化（已缓存的行正确、未缓存的行按 `Clean` 计算），同一
次查询在不同时机返回不同答案。

**影响面**：设计器需要任意行的语法状态——折叠、缩进推断、结构大纲、以及「这行是否在注释
里」这类判断，都会问到不在屏幕上的行。绘制路径只能覆盖可见窗口及其余量。

**建议（任一即可）**：

1. 为 `LineState` 增加 `Unknown` 变体，或为 `CodeEditor` 增加
   `line_state_is_known(line) -> bool`；或
2. 提供一个公共的「推进入口状态链到该行」入口（现为 `pub(crate) ensure_line_states`），
   使调用方能显式付出代价以获得确定答案。

**rustage 侧绕行（已记录，不阻塞）**：把高亮状态查询限制在绘制路径已覆盖的行；对屏幕外的
行不做「是否处于多行结构」的判断，或按「状态未知」处理。该约定写入
[第四次开发记录](../log/log-20261013-4.md) 的 T00.02 小节。

## 六、上游建议：`quit()` 无法从别的线程结束事件循环，且没有主线程调度入口

**现象**：宿主要给基线会话加一个"到点自动退出"（冒烟测试必须能结束，否则挂住的进程不是证据）。
在 watcher 线程里按 `exit_after` 调用 `rust_widgets::quit()`，进程**不会退出**：`[NSApplication run]`
一直不返回，实测 `--launch --exit-after-ms 500` 超过 60 秒仍在运行。

**原因（上游代码已写明）**：`src/platform/macos/platform_impl.rs` 的 `quit()` 在非主线程时
`log::debug!("[macos] quit skipped: not on the AppKit main thread")` 并直接返回；同一文件的
`run()` 注释指出 `-[NSApplication run]` "does not return until the app stops"。于是"从别的线程请求
退出"这条路径在当前公开 API 上不存在。

**影响**：任何不想用 GUI 回调驱动生命周期的宿主（冒烟测试、CI、脚本化演示）都无法干净地结束会话，
只能 `std::process::exit`，这会让"干净退出"与"强制结束"在日志与退出码上无法区分。

**建议（任一即可）**：

1. 提供 `quit_from_any_thread()`：内部把停止请求派发到主线程（`performSelectorOnMainThread` 或
   等价物），并返回一个结果说明是"已派发"还是"无法派发"；
2. 提供 `schedule_on_main(after: Duration, f: impl FnOnce())`，让宿主能在主线程上安排周期性工作
   （自动退出、心跳、状态栏刷新都会用到）；canvas 内部已有重复 `NSTimer`，把它暴露为公共接缝即可；
3. 或让 `quit()` 在非主线程时返回 `false`（现在是"静默跳过"），使调用方不必读日志才知道退出请求
   没有生效。

**rustage 侧绕行（已采用并写入记录）**：交互路径（`--launch` 不带 `--exit-after-ms`）等待窗口关闭，
由主线程返回并打印报告；有界冒烟路径（带 `--exit-after-ms`）在到点时由 watcher 线程记录一条
`WARN`（说明"因为固定修订的 `quit()` 仅限主线程，故结束进程"）后 `std::process::exit`，并把这种
结束方式在报告类型上单独记为 `LoopEnd::HostEnded`，不伪装成干净退出。若上游采纳建议 1 或 2，
rustage 会改回在循环内请求退出，并把该差异记录在决策与日志中。

### 8.1 桌面后端不提供系统文件对话框，自绘 `FileDialog` 也没有文件列表

**现象（可复现）**：`rust_widgets::create_file_dialog(0, 0, 0, 640, 420)` 返回 `0`，即该修订自己文档化的
"未创建控件"。源码与此一致：`src/platform/{macos,linux,windows}/platform_impl.rs` 均未 override
`create_file_dialog`（`src/platform/macos/status.md` 的表格明确写着
`Dialogs (NSAlert / NSOpenPanel) | ⛔ Removed`），只有 `mobile.rs`/`android` 有实现；
`src/control_backend/native.rs:65` 把 `file_dialog` 路由到 `get_platform().create_file_dialog(..)`，
于是落到 trait 默认实现（返回 `0`）。

自绘的 `FileDialog`（`src/widget/dialog/file_dialog.rs`）是一个**框**：标题、模式、起始目录、
名称过滤器、选择状态，加 `files_selected`/`file_selected`/`current_changed`/`accepted`/`rejected` 信号；
它**没有文件列表**——`current_changed` 的文档直接写明 "the dialog has no file list of its own, so
nothing here moves a cursor: a host that owns the list reports movement through
[`FileDialog::set_current_file`]"。

**影响**：宿主既打不开操作系统自己的选择器，也无法只靠库得到一个可浏览的选择器。设计器的
"选择文件"要么由宿主补上列表与浏览（rustage 记为 F26 的界面工作，T01.02 不冒充已完成），
要么等上游补真实对话框。

**建议（任一即可）**：① 在三个桌面后端实现真实对话框（`NSOpenPanel`/`GtkFileChooser`/`IFileDialog`）
并让 `create_file_dialog` 真正创建它；② 或提供宿主级 API：`open_path`/`save_path`/`select_directory`
直接返回 `Option<PathBuf>` 一类结果（含取消），而不是只返回控件 id；③ 并补一个能力位（见 8.5），
让宿主能在开工程前知道"这台机器能不能弹系统对话框"。

### 8.2 已挂载的自绘 `FileDialog` 无法被宿主写入选择

**现象**：`selected_file` 的 `set` 明确返回 `ReadOnlyProperty`（"the property contract deliberately
offers no write path for it"）；`command()` 只接受 `open`（= `accept`）与 `set_mode`/`set_directory`
（后两者直接返回 `OutOfRange`，让调用方走属性路径）。写入选择只能靠 `&mut FileDialog` 的
`select_file`/`set_current_file`，而 `runtime::register(Box<dyn Widget>)` 之后宿主只拿得到
`ObjectId`，`runtime::with_widget_mut` 给出的是 `&mut dyn Widget`——`Widget` 没有
`as_any`/`as_any_mut`，无法下转型回 `FileDialog`。

**本机实测（2026-10-14）**：在 `register` 之前 `select_file("/tmp/example.txt")`，挂载后用
`runtime::dispatch_event(id, &Event::key_press(13, 0))` 触发 Enter，`files_selected` 确实收到该路径；
挂载之后没有公共路径可以再改选择。

**影响**：宿主自有的文件列表在用户点了一行之后无法把该行交给已挂载的框，只能"先设置选择、再挂载"。
这把"列表归属宿主"的设计变成了只能单向使用。

**建议（任一即可）**：① 增加以 `ObjectId` 寻址的命令或可写属性（带载荷的 `select_file`，
或可写的 `selected_files`）；② 给 `Widget` 加 `as_any_mut`，让宿主能通过注册表借用具体类型。

### 8.3 没有把 URL/文件交给系统处理器的 API

**现象**：全库检索没有 `open_url`/`launch_default_handler`；`web` 模块是内嵌视图与导航
（`web_view`/`navigation`/`history`），不是交给系统处理器。实测宿主侧行为：`xdg-open` 会把以 `-`
开头的目标当成自己的选项——`xdg-open -- /path` 与 `xdg-open -` 都返回 "unexpected option" 且退出码 1，
所以"加 `--` 转义"不是出路，宿主必须自己拒绝选项形状的目标。

**影响**：每个宿主都要自己按 `target_os` 拼 `open`/`xdg-open`/`cmd /C start` 并各自处理参数注入与
"命令可启动≠命令成功完成"的区分，平台策略被复制到库外，与原则 #41 的方向相反。

**建议**：提供 `Platform::open_external(target) -> Result<(), OpenError>`（内部按后端分派，
并区分"已开始/退出码/找不到处理器"），或至少导出本平台处理器程序的查询。

### 8.4 `AssetWatcher` 不报告删除/重命名，事件类型也不可匹配

**现象**：`src/asset/watcher.rs` 的 notify 回调只对 `EventKind::Modify(_) | EventKind::Create(_)`
产出 `FileChanged`，`Remove`/`Rename` 被丢弃（文档只承诺 "modified or created"，代码与文档一致，
所以这是能力缺口而不是文档错误）。另一个可匹配性问题：`AssetEvent::FileChanged { kind: notify::EventKind, .. }`
暴露了 `notify` 的类型，但 `notify` 没有被 re-export；消费者（rustage 的依赖表里没有 `notify`）
只能把 `kind` 当不透明值打印度假字符串，想区分 Create/Modify 就得自己再引入一份 `notify`
（与原则 #35"同一语义只保留一份定义"冲突）。

**影响**：roadmap T03.05 需要"外部修改/删除/重建"检测，当前 watcher 无法提供删除与重建的事实；
rustage 现在把 `kind` 原样记录为文本并明确声明不区分创建/修改（见 `host::watch` 的模块文档）。

**建议**：① 让 watcher 转发 `Remove`/`Rename`（或提供可配置的事件集合）；② 把事件类型换成库自己的
`ChangeKind { Created, Modified, Removed, Renamed }` 并 re-export。

### 8.5 能力查询回答不了"有没有文件对话框/剪贴板/外部打开"

**现象**：`platform::capabilities()` 只有五个标志：`dpi_scaling`、`ime`、`accessibility`、
`native_menu`、`typed_widget_trigger`。文件对话框是否存在只能靠"调用 `create_file_dialog` 看返回值是否为 0"
来推断；剪贴板是否有原生实现只能靠 `platform_clipboard()` 是否为 `None` 或"写一次试试"；
外部打开根本没有 API 可问。本机实测 `platform_clipboard()` 为 `None`。

**影响**：宿主无法在打开工程之前给出准确的能力清单，只能在动作失败时才知道不可用，
与原则 #12/#37"能力差异用统一运行时查询表达，不以 `cfg` 或试错表达"不符。

**建议**：在 `PlatformCapabilities` 增加 `file_dialog`、`clipboard`、`open_external` 等标志并由各后端如实填写
（`capabilities()` 已是现成的查询通道，`default_capabilities_for` 的诚实默认值机制也已就位）。

### 8.6 剪贴板文本读取把"没有文本"与"不是文本"合并成空串

**现象**：`rust_widgets::get_clipboard_text() -> String` 的文档写明：剪贴板为空、内容不是文本、
或没有原生实现时都返回 `""`。rich 后端 `platform_clipboard() -> Option<&dyn RichClipboardBackend>`
的 `get_contents() -> Option<ClipboardContent>` 可以区分，但没有 rich 后端时（本机即是，返回 `None`）
区分是不可能的。

**影响**：宿主无法可靠实现"粘贴时提示剪贴板里是图片/文件"，只能把两者合并并在文档里写明合并点
（rustage `host::clipboard` 现状）。

**建议**：提供 `clipboard_text() -> Option<String>`（`None` = 无文本或非文本），或让文本访问器返回
带原因的结果类型。

### 8.7 观察（不请求改动）：库内没有接受取消信号的入口

**现象**：库内没有任何长操作接受取消标记——`run()` 只能等应用停止（见本文第六节），
编辑、布局、生成等入口也没有"中途放弃"的参数；宿主想在用户按下取消后停止一件已经进入库内的工作，
没有可用的接缝。

**影响**：rustage 的 T01.03 执行器只能取消**宿主自己拥有**的工作（宿主写的 job 轮询 `CancelToken`），
无法取消一个已经在库内跑的长调用。于是"取消"的边界必须在宿主侧就划定：长调用要么拆成可中断的片段，
要么只能如实记为 `Abandoned`（宿主停止等待、结果丢弃），本轮采用后者。

**不请求改动**：固定修订上还没有需要取消的库内长操作；这条记录是为了让将来第一个这样的操作
（例如批量生成或大文档布局）有明确的落点，而不是让每个宿主各自发明一套取消传递方式。
若届时采纳，建议形态是：长入口接受 `&CancelToken` 一类标记并在安全点返回 `Err(Cancelled)`，
或提供分片/迭代式入口由宿主驱动。

### 8.8 观察（不请求改动）：库内自行启动的进程不在宿主的会话归属范围内

**现象**：`src/platform/os_probes.rs:232` 的 `run_spooler` 用 `Command::new(program)` 启动打印
spooler，超时处理是 `child.kill()` —— 只结束**直接子进程**，没有为子进程建立独立进程组，
也没有任何会话/归属标记。

**影响**：rustage 的 T01.04 用"本会话为子进程创建的进程组"作为唯一清理判据（不扫进程表、不匹配
程序名），因此库内启动的这类进程：
1. 不在宿主创建的组里，宿主的整组清理**够不到**它们（这是刻意的——够不到比误杀好）；
2. 若 spooler 自己再派生子进程（真实打印链路如 `lp`/`lpr` 可能会），库内超时只杀直接子进程，
   后代可能继续存活，并且没有任何地方报告这一点。

**不请求改动**：打印路径不在设计器的关键链路上，且当前库的用法是"一个短命令、按超时收尸"。
记录在案是为了两件事：一是让宿主的"仅清理本会话拥有进程"有明确的**边界声明**（不包含库内进程），
二是将来若库内出现更长的进程树，有明确的落点。若采纳，建议形态是：库内启动子进程时也
`process_group(0)` 建组，超时按组清理；或提供一个库级进程注册表，让宿主把这类进程纳入统一的
会话归属与清理。
