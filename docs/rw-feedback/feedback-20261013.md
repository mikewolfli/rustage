## 结论

21 项契约探针（layout 3、generation 4、event 3、unbind 3、editing 8）在该固定修订上运行：
**20 项按设计行为通过，1 项记录为编辑接口的可判定性建议**。该建议不阻塞设计器（主机侧有明确
绕行方案），故不请求紧急上游改动，但建议在后续修订中处理。

## 三、上游建议：多行高亮状态在公共接口上不可判定

**现象（可复现）**：`CodeEditor` 为每行保留「入口状态」缓存，该缓存由**绘制路径**
（`prepare_visible_line_cache` → `ensure_line_states`）推进，并记录已证明到的位置
（`walked_lines`）。绘制尚未到达的行，公共访问器一律读回 `LineState::Clean`（`Default`）。

同一时刻，`line_state` 与 `tokens_on_line` 给出的答案并不一致：

- `set_text("/* open\nstill\n*/\n…")` 后，`line_state(1)` 返回 `Clean`；
- `tokens_on_line(1)` 以未证明的 `Clean` 入口状态对该行分词，因此得不到 `/* */` 的续行状态。

**为什么算问题**：`line_state` 的文档写明了「若词法器已到达该行」这一前置条件，因此单看该
访问器并不违约。问题在于类型无法表达第三种事实——`LineState` 没有「未知」变体，也没有
`is_state_known` 之类的谓词，于是调用方**无法区分「该行不在多行结构中」与「该行尚未被词法
分析」**。这正是原则 #22 禁止的「用成功形状的默认值掩盖失败」。`tokens_on_line` 的文档称
其为按需计算，但其结果会随绘制历史变化（已缓存的行正确、未缓存的行按 `Clean` 计算），同一
次查询在不同时机返回不同答案。

**影响面**：设计器需要任意行的语法状态——折叠、缩进推断、结构大纲、以及「这行是否在注释
里」这类判断，都会问到不在屏幕上的行。绘制路径只能覆盖可见窗口及其余量。

**建议（任一即可）**：

1. 为 `LineState` 增加 `Unknown` 变体，或为 `CodeEditor` 增加
   `line_state_is_known(line) -> bool`；或
2. 提供一个公共的「推进入口状态链到该行」入口（现为 `pub(crate) ensure_line_states`），
   使调用方能显式付出代价以获得确定答案。

**rustage 侧绕行（已记录，不阻塞）**：把高亮状态查询限制在绘制路径已覆盖的行；对屏幕外的
行不做「是否处于多行结构」的判断，或按「状态未知」处理。该约定写入
[第四次开发记录](../log/log-20261013-4.md) 的 T00.02 小节。

## 五、已核验契约（T01.01，宿主启动；2026-10-14 追加）

固定修订 `c957fdec7f30cc1a526b7c898c0f44b458ef4a57`（desktop profile），在本机
macOS 15.7.3 / Apple M4 上实跑（命令与输出见
[第四次开发记录](../log/log-20261013-4.md) 的 T01.01 小节）：

| 契约 | 观测 |
|---|---|
| `platform::backend_name()` | `cocoa` |
| `platform::runtime_gui_mode()` | `NativeInteractive`（不是预览/桩后端） |
| `widget::runtime::register(Box<Window>)` | 返回窗口 id（本轮为 `6000285942072475648`），窗口几何 1280×800 被接受 |
| `rust_widgets::init()` + `run()` | 真实进入 `[NSApplication run]`；无返回即在其中 |

不是桩后端，所以"启动了窗口"这句话在这里有依据。

## 六、上游建议：`quit()` 无法从别的线程结束事件循环，且没有主线程调度入口

**现象**：宿主要给基线会话加一个"到点自动退出"（冒烟测试必须能结束，否则挂住的进程不是证据）。
在 watcher 线程里按 `exit_after` 调用 `rust_widgets::quit()`，进程**不会退出**：`[NSApplication run]`
一直不返回，实测 `--launch --exit-after-ms 500` 超过 60 秒仍在运行。

**原因（上游代码已写明）**：`src/platform/macos/platform_impl.rs` 的 `quit()` 在非主线程时
`log::debug!("[macos] quit skipped: not on the AppKit main thread")` 并直接返回；同一文件的
`run()` 注释指出 `-[NSApplication run]` "does not return until the app stops"。于是"从别的线程请求
退出"这条路径在当前公开 API 上不存在。

**影响**：任何不想用 GUI 回调驱动生命周期的宿主（冒烟测试、CI、脚本化演示）都无法干净地结束会话，
只能 `std::process::exit`，这会让"干净退出"与"强制结束"在日志与退出码上无法区分。

**建议（任一即可）**：

1. 提供 `quit_from_any_thread()`：内部把停止请求派发到主线程（`performSelectorOnMainThread` 或
   等价物），并返回一个结果说明是"已派发"还是"无法派发"；
2. 提供 `schedule_on_main(after: Duration, f: impl FnOnce())`，让宿主能在主线程上安排周期性工作
   （自动退出、心跳、状态栏刷新都会用到）；canvas 内部已有重复 `NSTimer`，把它暴露为公共接缝即可；
3. 或让 `quit()` 在非主线程时返回 `false`（现在是"静默跳过"），使调用方不必读日志才知道退出请求
   没有生效。

**rustage 侧绕行（已采用并写入记录）**：交互路径（`--launch` 不带 `--exit-after-ms`）等待窗口关闭，
由主线程返回并打印报告；有界冒烟路径（带 `--exit-after-ms`）在到点时由 watcher 线程记录一条
`WARN`（说明"因为固定修订的 `quit()` 仅限主线程，故结束进程"）后 `std::process::exit`，并把这种
结束方式在报告类型上单独记为 `LoopEnd::HostEnded`，不伪装成干净退出。若上游采纳建议 1 或 2，
rustage 会改回在循环内请求退出，并把该差异记录在决策与日志中。
